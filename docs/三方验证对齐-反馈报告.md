## 二、共同发现（高优先级修复）

### 问题1：城市变更不推送（高）

**三方一致的分析：**
- 根因：`ingest.py:199-203` 的 diff 字段清单不包含 cities
- cities 在指纹中（:42），变更会触发 job_updated，但 diff 为空
- 库里 cities 存为 JSON 字符串，新数据是 list，直接比较永远不等
- 修复需要：① 在 diff 清单加 cities；② 反序列化后再比较

**A 的补充发现：** 修复复杂度被低估，还需考虑：
- 空列表 vs None 的语义
- diff 中 list 变化的展示格式

**决策：** 采纳 A 的补充，修复时一并处理。

---

### 问题2：重复 id 半截数据（高）

**三方一致的机制：**
1. try-except 只包 fetch()，不包写入循环（`ingest.py:97-103`）
2. INSERT 撞 IntegrityError 后异常抛出，事务留在内存
3. CLI catch 后 continue，下一源的 commit 把半截数据一起提交
4. 结果：残留半批 jobs/snapshots，run 状态永远 running

**B 的引用：** db.py 多处注释印证"这个雷已经踩过至少三次"

**决策：** 报告的根治方案正确——事务边界收拢到 `ingest.sync()`，优先级最高。

---

### 问题3：腾讯 recruit_type 兜底（高）

**三方一致的违规：**
- `tencent_join.py:47-52` 认不出时兜底 "campus"
- 违反 SPEC §6:142 硬规则："认不出就写 None，不许兜底"
- 飞书适配器有正确实现（`feishu.py:79-99`），认不出返回 None
- 飞书有同类 bug 修复记录和回归测试

**B 的补充：** 兜底还连带把 grad_year 设成 "26"（`GRAD_WINDOW`），影响两个字段。

**A 的发现：** 腾讯的 `_recruit_type()` 零测试覆盖

**决策：** 修复时同时补测试，参照飞书的测试结构。

**过 plan 时改掉的一句（2026-08-07）：** 上面原来写的是「造成双重错误」，
并据此认为要改两处。实测 `GRAD_WINDOW` 全仓只有定义（`:44`）和取值（`:129`）
两处引用，取值处写的是 `GRAD_WINDOW.get(rtype)`，`.get(None)` 返回 `None` ——
**改 `_recruit_type` 一处，grad_year 自己就跟着对了**。
B 说的连带影响是真的（两个字段都错），但推出来的「双重修复」是多写的一步。

---

### 问题4：腾讯分页截断（中）

**三方一致：**
- 腾讯：`if not batch` 直接 break（`tencent_join.py:99-102`）
- 飞书：`if not batch` 抛 RuntimeError（`feishu.py:306-312`）
- 40% 关闭守卫能兜住大截断，但 30% 会穿过去

**决策：** 把飞书那三行逻辑抄到腾讯，优先级高（虽然报告定为"中"）。

---

### 问题5：届别窗口换季（中）

**三方一致：**
- grad_year 不在指纹字段（`ingest.py:36-47`）
- 腾讯的届别是 `GRAD_WINDOW` 常量推导（`tencent_join.py:44`），注释说"每季要核对"
- 换季改常量后，存量岗位走"只更新 last_seen_at"分支（`ingest.py:226-228`），grad_year 永远旧值

**决策：** 要么加进指纹，要么换季时批量更新。报告未给出明确方案，需要在 plan 005 里设计。

---

### 问题6：sync all 一源坏掉（中）

**三方一致：**
- 路由失败（`cli.py:67`）：`raise typer.Exit(1)` 退出进程
- 抓取失败（`cli.py:73`）：`continue` 处理下一源
- 三行之差，行为相反

**B 的复现方法：** 在 sources 表故意写错 system，运行 sync all

**决策：** 路由失败改 continue，与抓取失败对齐。

---

### 问题7：dry-run / execute 不一致（低）

**三方一致的两处不一致：**

**7a. apply --dry-run 落盘**
- `cli.py:387` 在判断 dry_run 之前就调用 `db.record_prefill()`
- SPEC §7:161 硬约束："dry-run 全程不落盘"
- 但 SPEC §7:216 又说"出现 running 就是...或 dry-run 泄漏了"，说明这个问题已知

**7b. execute 异常不一致**
- unknown token：`SESSIONS.take()` 抛 TokenError（`tencent_join.py:157`，无 catch）
- expired/consumed/drifted：第二次 take 捕获后返回 blocked（`tencent_join.py:169-181`）

**决策：** 报告建议"在文档中明确区分两种 dry-run 语义"合理。7a 可能是有意留痕（报告原文），7b 需要统一异常处理。优先级低，但应修。

3. **问题7b 实际可触发**：报告说"单进程 CLI 触发不了"，但进程重启后调用 execute 就能触发 → **采纳**，修复时考虑

### 主 agent（我）独有发现

对齐当天：无。两个 subagent 的验证覆盖了报告里的七个问题。

   存库存未排序的 `j.cities`（`:183`/`:212`）。diff 比较不 sorted 会出现
   「指纹说没变、diff 说变了」。

但没有一方把 payload 从生产端跟到消费端。

**这条已经改进了验证清单：** `_VERIFICATION_CHECKLIST.md` 的「一致性」维度

1. **SPEC 与代码的同步滞后**：SPEC.md 多处描述与代码不一致（问题 7a），说明规则执行不够严格

## 六、对反馈报告的最终评价

**准确性：** 报告写的七条全部成立 —— 代码位置准确，根因分析到位，没有一条误报  
**严重度：** 七条内部的高/中/低划分合理，与实际影响匹配

是两句话**，当天的对齐把它们混着写了：原文那句「反馈报告完全准确」，
读起来像后者。

**优点：**
1. 引用具体行号和代码片段
2. 问题 1 指出根因（JSON 字符串 vs list）
3. 问题 3 准确引用 SPEC §6 和飞书的正确实现
4. 问题 6 精准定位"三行之差"

**可改进（非必须）：**
1. 问题 5 可补充修复方案（指纹 vs 批量更新）
