# 文档结构

三层，**职责不混用**。改东西之前先想清楚该动哪一层。

| 层 | 文件 | 职责 | 硬要求 |
|---|---|---|---|
| **方案文档** | [SPEC.md](SPEC.md) | 当前已确认的产品与技术事实 | **必须与实现一致**。每条能被 §9 的命令验证 |
| **Wiki** | [WIKI.md](WIKI.md) | 需求背景、决策及原因、替代方案、调研、实验、复盘、版本变化 | **不作为实现依据**。已证伪的条目**标注保留，不删** |
| **知识库** | [kb/](kb/README.md) | 只放允许 Agent 检索引用的业务事实 | 每份带来源/版本/生效时间/权限范围/更新负责人；**未审核的 Wiki 内容不许进** |

## 什么变了该更新哪一层

| 发生了什么 | 更新哪里 |
|---|---|
| 方案或实现变化 | **优先** `SPEC.md`（再看要不要连带改 kb）|
| 做了个决策、跑了个实验 | `WIKI.md` |
| Agent 能用的业务事实变了 | `kb/` 对应文件，**并涨版本号** |
| 要改代码 | **先写方案** `plans/NNN-*.md`（见根目录 `CLAUDE.md`）|

## 为什么 Wiki 和知识库对「错了的结论」处置相反

Wiki 里躺着七八条已证伪但保留原文的结论（「飞书没有校招」「校招接口找不到」…）。
留着是对的：删了就没法验证后来的结论是不是编的。
但 **Agent 检索到它们就会照着错的答**，所以知识库里的错条目是**删除**，
同时在 `WIKI.md §3.2` 记一行「曾经写的 / 实际 / 错在哪」。
