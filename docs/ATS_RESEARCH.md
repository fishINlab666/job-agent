# 采集方案调研：按公司做，还是按 ATS 做

> 评审提的问题：「大厂通常是自建的，用一套适配层来适配不同自建系统看似合理，
> 但是大部分中厂可能用的都是北森、moka 之类的招聘系统，所以他们的采集逻辑很可能
> 是一致的，用 ats 会更省事一些，不过这点我不确定，你可以让 cc 多调研一些公司的
> 页面特征后再决定。」
>
> 这篇是那次调研的结论。**方向对，但主力厂商猜错了**，而且猜错的那家不在我原来的表里。

调研时间 2026-08。工具 `scripts/probe_ats.py`，原始数据 `data/ats_probe*.json`。
下面每个数字都能用那个脚本复现，不能复现的地方都标了「未验证」。

## 一句话结论

按 ATS 做适配层是对的。**厂商的开放平台 API 走不了，但租户招聘页自己调的接口能走**——
飞书那个已实测（免鉴权 JSON，2265 条一次翻完，见结论三）；**投递那一侧只能填真实表单**。
国内先接**飞书招聘**和**北森**，两家各有一个实测核实的真实租户页。
Moka 到现在还是 0 个真实租户——唯一一次命中是块墓碑页（HTTP 200，内容写着「已关停」）。

> 这份结论改过一次。第一版写的是「北森和 Moka 一个真实租户页都没抓到」，
> 那是探测脚本卡死 + 把墓碑页算成活入口两个 bug 叠出来的结果，见下面「七次口径错」。

## 结论一：大厂自建，10/10

探了 10 家大厂的招聘入口，没有一家出现第三方 ATS 的痕迹：

| 公司 | 入口 | 判定 |
|---|---|---|
| 腾讯校招 | join.qq.com | 自建（域名已注册进表） |
| 腾讯社招 | careers.tencent.com | 自建（域名已注册进表） |
| 阿里 | talent.alibaba.com | 无任何厂商线索 |
| 字节 | jobs.bytedance.com | 自建（页面上的 `feishucdn.com` 是自家 CDN，见「判错范围」） |
| 美团 | zhaopin.meituan.com | 无任何厂商线索 |
| 百度 | talent.baidu.com | 无任何厂商线索 |
| 京东 | campus.jd.com | 无任何厂商线索 |
| 网易 | campus.163.com | 无任何厂商线索 |
| 小米 | hr.xiaomi.com | 无任何厂商线索 |
| 华为 | career.huawei.com | 无任何厂商线索 |

站外资源域名全是自家 CDN（`g.alicdn.com`、`s3plus.meituan.net`、
`cdn.bcebos.com`、`storage.360buyimg.com`、`hdslb.com`），没有一个指向**第三方** ATS。

「自家」这个词要较真一次：字节那页引的是 `lf-package-cn.feishucdn.com`，
从字符串上看是个厂商 CDN，但飞书是字节自己的产品，所以它跟上面几个是同一类东西。
判归属不能只看域名长什么样，得看域名归谁——这一条踩过，见下面「判错范围」。

**所以大厂这块跑不掉：一家一个适配器。** 这部分成本是硬的，只能靠优先级控制——
先接投递量最大的几家，剩下的排后面。

## 结论二：中厂确实在第三方 ATS 上，但抓到的是飞书招聘

唯一一条完整证据链，全程没有猜测参与：

```
campus.xiaopeng.com  --302-->  xiaopeng.jobs.feishu.cn
页面自称：加入小鹏汽车
```

顺着 `<tenant>.jobs.feishu.cn` 这个格式验证「一个适配器摊到多家」，
12 个候选租户名里 4 个是活的：

| 租户 | 页面自称 | 归属对得上吗 |
|---|---|---|
| xiaopeng | 加入小鹏汽车 | 对 |
| nio | NIO蔚来-社会招聘 | 对 |
| luckin | 加入狂浪俱乐部 | **不对**（不是瑞幸） |
| horizon | 加入汉森 | **不对**（不是地平线） |

剩下 8 个（lixiang / heytea / popmart / zuoyebang / …）全部 404 + 0 字节。
另外拿 `qwerasdfzxcv0000.jobs.feishu.cn` 做过反向对照，也是 404——
说明**没有泛域名兜底**，上面 4 个是真实存在的租户，不是任意子域名都返回 200。

这四条落在同一个 `route_key` 前缀 `feishu:*` 上，同一套页面结构、同一份采集逻辑，
**4 家公司 1 个适配器**。评审说的杠杆是真的，而且能量化。

### 北森抓到一个真实租户，Moka 到现在还是 0 个

北森这条是跟着公司自己的入口跳出来的，和小鹏那条同一个路子：

```
job.youzan.com  --302-->  youzan.zhiye.com
页面自称：有赞招聘
静态资源：tcdn.bstatics.com、acdn.bstatics.com/ux/beisen-common/
图片：  stcms.beisen.com     ← 已核实的北森域名
i18n：  i18n.italent.cn      ← 已核实的北森域名
```

`zhiye.com` 原来不在表里，所以这页第一次探到时只命中页面标记，判成 `markup` 级、
不可路由。现在它进了北森的 `domains`，`youzan.zhiye.com` 直接出 `beisen:youzan`。

**它能进 `domains` 靠的是反向对照，不是页面里有 beisen 串。**
`zhiye.com` 有通配 DNS + 兜底响应，非租户子域名一律返回 **200**：

| 子域名 | 状态 | 字节 | sha | 标题 |
|---|---|---|---|---|
| `youzan` | 200 | 28715 | `928911ac` | 有赞招聘 |
| `qwerasdfzxcv0000` | 200 | 1228 | `d40106ef` | Not Found |
| `nonexistent-tenant-xyz99` | 200 | 1228 | `d40106ef` | Not Found |
| `xiaopeng` | 200 | 1228 | `d40106ef` | Not Found |

三个非租户返回**字节完全相同**的软 404（都跳 `/404?errorpath=/`）。所以在这个域上
200 本身什么都不证明，只有内容不同才算——**跟飞书正好相反**，飞书的假租户是干净的
404 + 0 字节。同一套判据换个厂商就失效，这就是每家都得单独做对照的原因。

跟字节那次误判的区别也在这儿：**资源链路落在厂商已核实的域名上**。
字节全程在自家 CDN，只是页面里提到了 beisen 这个词。

口径要说准：核实的是**这些页面由北森的前端和资源链路提供**，不是「zhiye.com 归北森
所有」。白标/代理从外部排除不了，但对采集解析来说前者才是操作性事实。
`Vendor.notes` 按这个口径写，`tests/test_ats.py::TestBeisenTenantDomain` 钉住。

**Moka 那条是墓碑。** `campus.tuya.com` 返回 200、7558 字节、命中 mokahr 标记，
标题是「当前网页已关停」。它只能证明涂鸦**曾经**用过 Moka，算不上一个在用的租户。

**所以「大部分中厂用北森/moka」这句话，还是既没证实也没证伪。**
36 个候选里活着的入口 8~10 个（区间的来源见结论四），命中第三方 ATS 的 **2 个**
（飞书 1、北森 1）。分子在四轮探测里一次没动过——会动的是 B站 那两个入口，
而它们两个都不命中 ATS。所以这里该用区间的是分母，不是分子。
真实占比要靠用户实际投递时积累的样本回答，不是现在能拍板的。

## 结论三：厂商**开放平台**的 API 是关的，租户前端自己调的接口不一定

Moka 开放平台走 OAuth 2.0，凭证线下发给测评/视频面试类合作方，
没有公开的岗位查询端点，也没有免鉴权入口，租户用 `appId` 标识。
北森、大易同样没有公开的岗位读取 API。

**但「厂商开放平台 API」和「租户招聘页自己调的接口」是两件事**，
这一节原来把它们合成一句「不能指望结构化接口」，
于是一个能省掉整个浏览器链路的事实被自己的结论盖住了。

前者要签约拿凭证；后者是公开页面的一部分——浏览器能免登录调，
我们也能。本质仍然是「解析公开前端」，只是解析对象是 XHR 而不是 HTML。

**飞书招聘的那个接口已实测通**（2026-08，见 `docs/plans/002-飞书招聘采集.md` §3）：

```
POST https://<tenant>.jobs.feishu.cn/api/v1/search/job/posts
     {"keyword":"","limit":200,"offset":0}
  → {"code":0,"data":{"count":2265,"job_post_list":[...]}}
```

免鉴权，只要 `Referer`。xiaopeng 1646 条、nio 2265 条，翻页拿全量，
id 不重复，**不用 Playwright**。所以「至少三分之一的入口必须跑浏览器」（结论四）
这个判断在飞书这一片是可以绕开的——前提是那家公司的岗位在这个口子里。

覆盖面要说准：这个接口**只有社招和实习**（`recruit_type.parent.name` 恒为「社招」），
校招门户（`<tenant>.jobs.feishu.cn/campus`）是另一个页面，接口没找到。
所以对校招来说，这条路现在还是关的。

Moka / 北森 / 大易的租户前端接口**没探过**，不能照着飞书推——
每家都得单独实测，理由和 `domains` 那件事一样：厂商级的结论套不到产品级。

**这一条决定了架构的两个点：**

1. 采集**优先探租户前端的 XHR**，探不到才退回解析 HTML / 跑浏览器。
   顺序反过来会白跑一整套浏览器链路（飞书这次就是）。
2. 投递这一侧的判断**不变**：没有「提交简历」的 API 可调，只能靠 Playwright 填真实表单。
   于是 `prepare()` / `execute(confirm_token)` 那道人工确认闸门是**承重的**——
   它挡的是浏览器自动化直接点「提交」，不是一个可以回滚的 API 调用。
   **采集能走接口，不代表投递也能。**

## 结论四：至少三分之一的岗位入口必须跑浏览器

有 SPA 根节点、正文不足 800 字的页面，服务端没渲染岗位数据。
这类只能上 Playwright，`httpx` 拿到的 HTML 里什么都没有。
成本差一个量级，所以这个信号要在适配器里显式标出来，别让采集默认走重路径。

分母是**活着的公司入口**（不含厂商官网）。这个数在不同批次之间会动，所以给区间：

| | 活着的入口 | 要跑 JS |
|---|---|---|
| 大厂（16 个候选） | 10 | 3 —— 阿里、百度、京东 |
| 中厂（36 个候选） | 8 ~ 10 | 3 ~ 5 —— 蔚来、小红书 ×2，B站 ×2 |
| 合计 | 18 ~ 20 | **6 ~ 8**（5 ~ 6 家公司） |

**区间的来源就一个：B站 那两个入口时通时不通。** 连着跑三轮是 8/36，
换个时段再跑就回到 10/36，两个入口都判了要 JS。大厂那 10 个每轮都一样。

所以这个比例的下界是 6/18 ≈ 33%，上界 8/20 = 40%，**取哪一轮都在三分之一以上**——
这才是能往下游传的结论。真正要传的是「有多少入口要走重路径」这个量级，
不是某一轮的分子分母。

> 而且 33% 这个下界本身是被低估的：会掉的恰好是 B站 这种重前端站，
> 也就是最可能要 JS 的那一类。掉的不是随机样本。

> 这个数我改过四次，四次错法不同，留个记录：
> ① 「3/16」——分母把 6 个厂商官网（Moka/北森/Workday 那些）也算进去了，
> 而厂商官网根本不是岗位列表。
> ② 分子写「5 家」——实际数的是行数，小红书和 B站 各有两个候选 URL 都活着。
> ③ 分母用了单轮的 10，而那一轮里有两个入口下一轮就没了。
> ④ 改成 6/18 并写了「连跑三轮完全一致 → 稳定」——**三轮一致只说明那三轮一致**，
> 换个时段就回到 10。把「短期可复现」写成了「稳定」，这是拿采样窗口当结论。
> 前三次错在口径，第四次错在**把一个会动的量当成了点估计**。
> 治法不是再钉一个快照，是报区间加上界下界的来源。
> 脚本那行汇总同时打入口数和公司数（`5 个入口（3 家公司）`），
> 因为这两个数回答的是不同问题：要写几个适配器看公司数，要跑几次浏览器看入口数。

## WAF：有些站不是不在，是不接我这个客户端

B站 那两个入口连续三轮探不通，`error` 写的是
`ConnectTimeout: _ssl.c:1015: The handshake operation timed out`，
另有一轮回了 **412，用时 1.5 秒**。412 不是「连不上」——那是有人看了一眼就把我打回来了。

同一台机器、同一时刻、同一个 UA，`curl` 两个 URL 都是 200：

```
httpx  → ConnectTimeout（TLS 握手超时）／一次 412
curl   → HTTP 200
```

**再换个时段跑，这两个入口自己回来了**，`httpx` 直接 200，还判出了要跑 JS。
这一条比上面的 curl 对比更硬：不解析的主机不会自己复活，
会时通时不通的只能是**中间那层在按某种规则做判决**。
所以「探不通」在这两行上从来不是关于 B站 的事实。

排查过程留一下，因为结论取决于排掉了什么：

- **不是请求头**：把 httpx 的头精简到裸客户端，照样失败；给 curl 换成 httpx 的默认 UA，照样 200。
- **不是 IPv6**：这条其实是被 DNS 排掉的，那个域名**没有 AAAA 记录**，
  也就是根本没走过 v6。`curl -4` 和 `curl -6` 都是 200。
- **剩下的是 TLS 指纹 / WAF 规则**。httpx 和 curl 的握手参数不一样，
  这是两者唯一还有差别的地方。

**没验的部分说清楚**：我没定位到具体是哪一项触发的（JA3/JA4、cipher 顺序、ALPN 都有可能），
也没拿 `curl_cffi` 或真浏览器再确认一遍。所以这一节能立的结论只到
「**我这个客户端被挡了，那两个站是活的**」，不到「是 X 导致的」。

这件事对产品有两层影响，而且第二层比第一层更容易漏。

**一、采集必须上浏览器，这是第二个独立的理由。** 结论四说的是页面要跑 JS 才有内容，
那是拿到 HTML **之后**的问题；这里是**连 HTML 都拿不到**，卡在 TLS 层。
就算某个站的岗位列表是服务端渲染的、`httpx` 完全解析得动，它也可能压根不让 `httpx` 连上。
两个理由指向同一个动作，但堵在链路的不同位置，所以省掉浏览器的那条路比看起来更窄。

**二、被挡和不存在，在输出里长得一模一样。** 两种情况 `error` 都是 `ConnectTimeout`，
都落进「探不通」那一堆，然后被读成「这家没有招聘入口 → 大概自建」。
这跟 `starved` 是同一个形状的错：**把一件关于我自己客户端的事，写成了一件关于那家公司的事。**
`starved` 当时单独立了字段，这次先把 412 这类「明确的拒绝」标出来
（见 `probe_one` 里的 `blocked`），但握手超时那种**脚本自己分不出来**——
它得靠换一个客户端复测才能定性，这一步现在是手工的。

`blocked` 这一档在两轮真实探测里都没触发过（`blocked 0`），所以它是靠
`tests/test_probe_buckets.py` 钉的：四个拒绝状态码逐个立案、404 反向钉一次
（不许把「入口不存在」洗成「可能是被挡的」，不然那 23 个构造出来的
`campus.<公司>.com` 会全被洗白）。还有一条专门盯输出那一行——
`report()` 里 `blocked` 的分支必须排在 `elif p.ok` 前面，否则 412 会被打成
「入口不存在 412」：字段立对了、打出来还是错的，等于白立。
这个 bug 就是加完字段之后当场踩的。

所以「探不通」这个桶到今天至少有三个来源，只有第一个是关于公司的：

| 现象 | 是关于谁的 | 脚本能不能自己分出来 |
|---|---|---|
| 主机不解析 / 不提供 HTTPS | 那家公司 | 能 |
| 连接池饥饿 | 我本机的调度 | 能（`starved`） |
| 客户端被 WAF 挡 | 我的 HTTP 客户端 | 412 这类能（`blocked`）；握手超时不能 |

## 三种「自信地判错」，都是实测踩出来的

调研里最有价值的产出不是上面的表，是这三个失败模式。判不出来（unknown）是安全的，
人工看一眼就补了；判出一个**错答案**才是要命的，它会静默生效。

### 判错厂商：字节被判成北森

字节自建招聘页里有这些串：

```
"FeatureDailyExamUseBeisen"   "BeisenExamAccount"
"ats.common.organization_display_optimization"   "ats.interview.coding_asset_write_sup"
```

它自建 ATS（`ats.*` 是自家灰度开关命名），只是**接了北森的在线考试**。
`dom_hints` 里放裸词 `beisen` 就会把它判成北森，然后拿北森的采集逻辑去打一个
根本不是北森的页面。

同类：`www.lever.co` 的营销页同时命中 `workday` 和 `greenhouse`（同行对比），
`leverage` 命中 `lever`。

**修法**：`dom_hints` 只收带点号的域名片段/资源前缀，或厂商自造词
（`ats.COINED_HINTS` 白名单）。裸品牌词一律不许进，`tests/test_ats.py`
里逐个点名钉死。另外页面标记命中只标 `MARKUP`，**不可路由**——
这条分级是主闸门，字节那次误命中就是被它挡住没造成路由错误的。

### 判错租户：几十家公司挤进同一条 route_key

`join.qq.com` 取出 `tenant="join"`，`boards.greenhouse.io` 取出 `tenant="boards"`。
两个都是厂商自己的主机名。后者更坏：所有 greenhouse 公司的 `route_key`
都变成 `greenhouse:boards`，共用一个适配器条目，且从外部看不出错在哪。

**修法**：`_GENERIC_SUBDOMAINS` 挡功能域名；`self_built` 厂商直接不取租户
（天生只有一个租户）；只有核实过格式的厂商才配 `tenant_seg`。
取不到就返回 `None`——猜一个错的租户比留空难查得多。

### 判错范围：把厂商的整个品牌域名当成 ATS

这一条是 2026-08 最后一轮复查抓到的，性质比上面两条都严重，因为它错在 **domain 级**
——那一级是可路由的，会直接被采集/代投拿去跑。

`feishu` 的 `domains` 里原来有一个裸 `feishu.cn`，于是：

```
abcde.feishu.cn/docx/HxKtdM2f0oL1s      ← 一篇飞书文档
  → system=feishu  tenant=abcde  confidence=domain  routable=True
```

也就是把一篇文档判成「abcde 这家公司的招聘入口」，还顺手编出了租户名。
毛病在于**飞书是一整套办公套件**（文档、表格、IM、日历），招聘只是其中一个产品，
`feishu.cn` 底下绝大多数子域名跟招聘毫无关系。ATS 只在 `<tenant>.jobs.feishu.cn`。

同一个入口上还有第二个错，方向相反——把**第一方**依赖读成第三方采用：

```
jobs.bytedance.com  页面里有 lf-package-cn.feishucdn.com
  → 汇总报「命中第三方 ATS」
```

而飞书本来就是字节自己的产品。字节自建招聘页挂着自家的 CDN，这是第一方依赖，
不是「采用了别人家的 ATS」。`feishucdn.com` 是字节全线产品共用的 CDN，
不是招聘专用的，所以它连立案都不够格。

**修法**：`domains` 收窄到 `("jobs.feishu.cn",)`，`dom_hints` 同样只留这一个，
`feishucdn.com` 整条拿掉。后缀匹配照样吃 `xiaopeng.jobs.feishu.cn`，
实测那两家真租户一个没丢。代价是 `www.feishu.cn` 官网不再命中，这是有意的：
官网不是岗位源，`Vendor.notes` 里写明了。
`tests/test_ats.py::TestFeishuScopeIsJobsOnly` 把三条非招聘的飞书 URL 逐个钉死。

**这三条合起来是一条规则**：判据的粒度必须跟**产品**对齐，不能跟**厂商**对齐。
品牌词（`beisen`）、品牌域名（`feishu.cn`）、品牌 CDN（`feishucdn.com`）
都是厂商级的，而我们要认的是「这家公司在用某厂商的**招聘系统**」。
差这一级，命中的就不是同一件事。

### 还有七次是我自己的口径错

调研过程里我的探测/汇总脚本报过七次假数字，都修了。记在这里是因为它们是**同一类错**，
而且一路都在换着花样重现——前六次都是「把一个不该算的东西算进了分子」：

- **把厂商官网算成用户**：第一版报「7 家公司只需要 6 个适配器」，
  其中 6 家是厂商自己的官网。现在 `vendor_site` 单独归到「对照组」。
- **把 404 算成命中**：`probe_one` 只要拿到 HTTP 响应就置 `ok=True`，
  于是 11 个编出来的假租户名（全部 404 + 0 字节）被汇总成「12 家公司命中 feishu」。
  现在分 `ok`（有响应）和 `alive`（2xx + 有正文），只有后者算证据。
- **把墓碑页算成活入口**：`alive` 的定义是 `2xx + 正文 > 500 字节`，
  而 `zhiye.com` 的兜底软 404 是 **200 + 1228 字节**，比门槛高，会被算成一个活着的
  租户页。实测这一条让「租户页命中第三方 ATS」多报了 1 家（涂鸦那个「当前网页已关停」
  的 Moka 页）。现在 `alive` 只管 HTTP 层，内容层另立 `tombstone`，
  证据口径是 `alive and not tombstone`。
  修完这一档从 3 掉到 2——**我原来在正文里写的那个 3 是错的**。
- **把「没探到」算成「探不通」**：连接池饥饿的目标吃 `PoolTimeout`，被归进
  「连不上」那一档。「连不上」是关于那个站的结论，饥饿是关于本机调度的，
  混在一起会读成「这些公司自建」。现在单独立 `starved`，串行补探一轮，
  补完还饥饿就在汇总里显眼地点名、不计入任何一档。
- **把 markup 级线索算成 domain 级证据**：汇总那一行「租户页命中第三方 ATS：N」
  是按 `system != unknown` 数的，没看置信度。表里明明写着「domain 才能路由，
  markup 只够立案」，汇总却拿一条自己都不敢照着跑的线索去报占比。
  实测代价就是上面那条字节的误报。现在 `saas` 只收 `confidence == DOMAIN`，
  markup 级的另起一行 `leads`，明确写「不计入上面的占比」。
- **把行数算成家数**：「N 家的岗位列表要跑 JS」实际数的是探测行数，
  而候选表里一家公司常有多个候选 URL（`小红书` 和 `小红书-join` 都活着）。
  5 个入口只有 3 家公司。现在两个数一起打（`5 个入口（3 家公司）`），
  因为它们回答的是不同问题：要写几个适配器看家数，要跑几次浏览器看入口数。

第七次错法不一样，值得单列：**把一个会动的量写成了点估计**。
结论四那个比例我按「连跑三轮完全一致」判定它稳定，还把「稳定」写进了正文。
三轮一致只说明那三轮一致——换个时段 B站 那两个入口自己回来了，分母从 18 变成 20。
前六次是分子分母的成分不对，这次成分全对，错在**拿采样窗口当结论**：
可复现是可复现了，但复现窗口只有几分钟，而我按它下了一个不带时间限定的判断。
治法不是再多跑几轮钉一个新快照，是报区间、并写清上下界差在哪一行上
（现在写的是 6~8 / 18~20，差的就是 B站 那两个入口）。

后五条都是这次为了核实中厂数据重跑探测时才暴露的，说明这类错不会自己消失。
它们表面上各不相同，底下是同一句话：**汇总的那个数字必须和它声称的那件事同一个粒度**，
时间也是一个粒度。
「有响应」不等于「有内容」，「本机排不上队」不等于「那个站连不上」，
「页面上有个串」不等于「这家在用这个系统」，「一行」不等于「一家」，
「这三轮」不等于「一直」。
每次都是我少加了一道限定，而错出来的数**看着都很正常**——
这也是为什么这一节比上面那两个失败模式更值得留着：判错厂商会被 MARKUP 闸门挡住，
口径错没有闸门，它直接变成结论。

顺带一条同源的毛病，不算数字错但一样是自己盖自己：`saas` 非空就无条件打一句
「这就是按 ATS 建适配层的杠杆」。中厂那轮是 2 家公司 2 个适配器，1:1，没有杠杆。
现在只有 `len(saas) > len(vendors)` 才说杠杆，否则明说「这一轮没摊开，不证明杠杆」。

### 附带修掉一个死锁：`pool=None`

上一条的第一版修法是 `httpx.Timeout(..., pool=None)`——「等连接池永不超时」。
方向就错了：它把一次会上报的失败换成了死等。36 个目标跑到 23 个卡住，0% CPU，
挂了 38 分钟一动不动，`data/ats_probe_midsize.json` 始终是修复前的旧文件。

一开始我猜是外面那层 `sed | head -40` 把管道读端关了。**猜错了**——去掉管道重跑照样卡。
`PYTHONFAULTHANDLER=1` + `kill -ABRT` 打出所有线程栈才看到真相：

```
httpcore/_sync/connection_pool.py:35  wait_for_connection
httpcore/_synchronization.py:290      wait          ← 无限等
```

现在 pool 超时是有限值（`timeout * 4`），饥饿如实上报，由 `starved` 接住再补探。
**「永不超时」不是容错，是把一个能看见的错误换成一个看不见的挂起。**

## 采集设计：按 ATS 系统注册，不按公司

```
适配器注册表的键 = route_key = "<ats>:<tenant>"，自建的就是 "<ats>"

feishu:xiaopeng ┐
feishu:nio      ├─ 同一份采集/投递逻辑，只有租户配置不同
feishu:luckin   ┘
tencent_join    ── 自建，单独一份
```

注册表的键是**系统**，租户是实例参数：`_ADAPTERS["feishu"]` 只有一个类，
`feishu:xiaopeng` / `feishu:nio` / `feishu:luckin` 三条 route_key 共用它。
route_key 标识的是一个**源**，不是一个类。

加一家公司的边际成本≈一行 `sources` 记录。按公司建适配器等于把同一份逻辑抄几十遍，
然后每家分别坏一次。

反过来也成立：**多租户系统的系统名本身不是一个合法的源**。光说 `feishu` 不说租户，
同步谁？所以 `sync --source all` 只能自动带上自建的键（`system == source_key`），
多租户的必须来自库里配好的 `sources` 行。

识别按置信度分两级，这是整套设计里最要紧的一条：

| 信号 | 置信度 | 能不能直接路由 |
|---|---|---|
| 域名命中 | `DOMAIN` | 能 |
| 页面标记命中 | `MARKUP` | **不能**，只当线索，人工核实后升级 |
| 都没命中 | `UNKNOWN` | 不能 |

### 落地：`jobagent/routing.py`

上面那套键的选法落在 `routing.py`。在这之前 `ats.py` 建好了却没人用，`cli.py` 里
两张表还是 `{source_key: cls}`——正是评审质疑的「一家公司一个适配器」。现在两张表
移到 `routing.py`，登记动作在 `adapters/` 和 `submitters/` 的包初始化里（谁提供实现
谁登记；写在 cli 里的话，外面那层 MCP server 就得记着再写一遍，漏一次的表现是
「这家投不了」而不是报错）。

`resolve()` 按可靠性从高到低试，前面的赢——越往后越像猜：

| 顺序 | 依据 | 说明 |
|---|---|---|
| 1 | `jobs.apply_system` | 采集时就判定好写进库的，最可信 |
| 2 | `apply_url` 域名命中 | 只认 `DOMAIN` 级 |
| 3 | `sources.system` | 人工配的 |
| 4 | `source_key` | 老式注册，自建的一直是这么来的 |

`_build()` 上有五道拒绝。共同点是**这些情况不报错，只是投到别人家公司去**：

| 拦什么 | 不拦会怎样 |
|---|---|
| 认不出系统 | 空跑 |
| 两处租户证据对不上 | 投错公司 |
| 识别出了但实现没写 | 报错信息本身是对的 |
| 多租户系统的类不收 `tenant` | 拿别的租户的页面填表 |
| 多租户系统没取到租户值 | 同上 |

租户那两条是这次新加的，因为我第一版把 `sources.tenant` 排在 URL 前面。**从链接里
取到的是证据**（`xiaopeng.jobs.feishu.cn` 那个 xiaopeng 已实测核实，页面自称「加入
小鹏汽车」），`sources.tenant` 是**人工配的**。两个都有且不一样时，说明有一处是错的
（配置过期、复制粘贴串行），而下一步是不可逆的投递——所以不许挑一个接着用。
**证据优先，分歧当故障。** `resolve()` 只记录（给人看的地方也要显示得出来），
`_build()` 才拒绝。

取租户前还得先确认链接确实落在这家厂商域名上：`ats.tenant_from_url` 不校验归属，
只管抠第一段子域名，拿一个无关链接去问会从 `acme.example.com` 里凭空造出租户 `acme`。

`sources.tenant` 这一列存在的理由就是取不到的情况：公司自有域名（`campus.xiaopeng.com`
这种 CNAME 过去的）抠不出租户，北森/Moka 的租户页格式还没实测、可能根本不在 URL 里。
它的 upsert 用 `COALESCE(excluded.tenant, sources.tenant)`——自建适配器没有 `tenant`
属性，传进来是 NULL，直接覆盖就把人工配好的值擦掉了，表现是「本来能投的公司忽然投不了」。

还修了一个同类的错话：查表前必须先确保实现包被 import 过，否则表是空的，报出来的是
「识别出是 X，但还没写代投器」——一句听着很确定的错话，真实情况是「写了，只是没加载」。
两个包分开懒加载：代投依赖 playwright，采集不依赖，合成一个函数的话光查采集器也会把
playwright 拽进来。

顺带修掉一个一直没被发现的 bug：`TencentJoinAdapter.system` 原来写的是 `"self_built"`。
那是一类系统的形容词，不是某个系统的 key——按它去注册表里找永远找不到，而且所有自建
公司会挤在同一个键上。自建系统的 `system` 就是它自己。

`tests/test_routing.py` 28 个用例钉这两类事：一类是上面的实测结论，一类是**不许悄悄
发生**的事。另外三条不变式：注册的系统必须在 `ats.VENDORS` 里（否则那个类永远查不到，
是死代码）、多租户实现必须接 `tenant`、`cls.system` 必须等于它的注册键。

## 怎么复现 / 怎么往下推

```bash
# 大厂 + 厂商官网对照组
uv run python scripts/probe_ats.py

# 中厂候选（构造的 URL，探不通是预期结果）
uv run python scripts/probe_ats.py --urls-file data/probe_targets_midsize.txt \
    --out data/ats_probe_midsize.json --concurrency 10 --timeout 8

# SPA 页面要抓 XHR 域名才看得出后面是谁
uv run python scripts/probe_ats.py --render

# 上面每个结论对应的测试
uv run pytest tests/test_ats.py tests/test_routing.py tests/test_probe_buckets.py -q
```

> 前缀是 `uv run`，跟 README 一致。裸 `python` 在这个仓库跑不起来——
> 环境里根本没有这个名字（只有 `python3`，而它看不见 `.venv` 里的 httpx）。
> 开头写着「下面每个数字都能用那个脚本复现」，那这行命令本身就得是能跑的，
> 否则第一步就断了。

**找真实租户页的唯一可靠路径是跟着公司自己的入口跳转。**
猜租户 slug 不行——12 个猜 4 个活，其中 2 个还是别人家的。
搜索引擎也不行：北森/Moka 的租户页不做 SEO，搜不到（这也正是必须实测的原因）。

## 待办 / 未定

- **没有加多租户源的入口**：`sources` 表目前只有 `ingest.sync()` → `register_source()`
  一个写入口，而它要先有适配器才跑得起来。所以 `feishu:nio` 这样一条源现在只能手写
  SQL 插进去。没先做是因为多租户适配器还没写，做了也没东西可服务；等第一个飞书
  适配器落地时一起补一个 `source add`。
- **Moka、大易的租户页格式**：未实测，`Vendor.notes` 里都标了。
  拿到一个真实租户 URL 之后再写 `fetch()`，现在写等于编。
  北森有一个了（`youzan.zhiye.com`），但 **n=1**，一个样本推不出岗位列表的 DOM 结构，
  所以 `fetch()` 照样没写——能路由不等于能解析，这两件事分开推进。
- **中厂 ATS 真实占比**：未知。飞书抓到 4 家，北森 1 家，Moka 0 家，
  样本远不够下结论。而且分母本身也不干净：36 个候选里 23~25 个没探通（见下条），
  这些公司用什么系统完全不知道，不是「不用 ATS」。
- **`data/probe_targets_midsize.txt` 里那 23 个探不通的，是真的没有**：
  `curl` 拿同样的 UA 逐个复现，23 个也是 `http=000`——那些主机名确实不解析/不提供
  HTTPS（`campus.<公司>.com` 这个格式本来就是我构造的，探不通是预期结果）。
  这不代表那些公司自建，只代表这次没探到。
  这一档曾经是 25：多出来的 2 个是 B站 的两个入口，**那是我的客户端被挡了，
  不是站没了**，后来自己又通了，见「WAF」那节。所以这个数会在 23~25 之间动，
  动的那 2 个不属于这一档。
- **海外 ATS**（Workday / Greenhouse / Lever / SuccessFactors / Taleo）：
  域名和租户格式已核实，但校招用不上，优先级最低。
