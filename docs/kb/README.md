# Agent 知识库

> **这个目录的职责：只收允许 Agent 检索和引用的业务资料。**
>
> 与另两层的分工：
> - `docs/SPEC.md` —— 当前实现的事实，必须与代码一致
> - `docs/WIKI.md` —— 过程：背景、决策、调研、实验、复盘（**可能过时**）
> - `docs/kb/` —— **Agent 能直接引用的业务事实**（本目录）

## 硬规则：Wiki 内容不许直接进知识库

**未经审核的 Wiki 条目不得进入本目录。** 理由不是流程洁癖：Wiki 里躺着
七八条**已证伪但保留原文**的结论（「飞书没有校招」「校招接口找不到」
「源站分类按租户互斥」…）。这些条目留在 Wiki 是对的——删了就没法验证后来的
结论是不是编的——但 **Agent 检索到它们就会照着错的答**。

所以本目录的每份文件必须带完整头信息，缺一项就不算入库：

```markdown
---
来源: <具体到命令或文件行号，不许写「实测」两个字了事>
版本: v<N>
生效时间: YYYY-MM-DD
权限范围: 公开 / 仅本人 / 含个人信息
更新负责人: <谁>
审核状态: 已审核
---
```

## 审核标准（四条全过才收）

1. **可复现**：附一条能跑的命令，跑得出文件里写的数。跑不过 = 不收。
2. **有口径**：任何计数带测量日期；任何区间带样本来源（哪几个租户/门户）。
3. **不含待查**：`WIKI.md §3.3` 里的东西一条都不许进来。「不知道它是什么」
   进了知识库就会变成「Agent 觉得它知道」。
4. **权限清楚**：含个人信息（`profile.yaml` 里的东西）的条目标 `含个人信息`，
   且不许写进会外发的内容。

## 更新时机

**当可供 Agent 使用的业务事实变化时更新，并涨一个版本号。**
典型触发：接口口径变了、新增一家已核实的公司、某条结论被证伪。

被证伪的条目**从本目录删除**（不是标注保留——那是 Wiki 的做法），
同时在 `WIKI.md §3.2` 记一行「曾经写的 / 实际 / 错在哪」。
两个目录的处置方式不同是有意的：Wiki 要留证据，知识库要防误答。
