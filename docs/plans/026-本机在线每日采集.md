# 方案：电脑在线时每天成功采集一次

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` and follow the tasks in order.

**Goal:** 在不付费、不依赖云端的前提下，将三个固定采集时段收敛为“Mac 当天首次具备唤醒和联网条件时采集，完整成功后当天不再重复”。

**Architecture:** 复用现有五源观察、独立官网候选、本机通知、文件锁和 LaunchAgent 安装/回滚能力。新增一个登录时和每个整点/半点触发的轻量入口；`StartCalendarInterval` 让休眠期间错过的时刻在唤醒后合并补触发。入口先在同一数据库锁内检查当天是否已有完整五源快照，已完成则立即退出，未完成才运行采集。不新建并行采集链，不修改岗位事实模型。

**Tech Stack:** Python 3.13、SQLite、Typer、macOS launchd/LaunchAgent、pytest、uv。

## 一、产品设计

### 1. 为什么现在做

现有本机观察只在 09:30、14:30、20:30 触发。Mac 在这些时间休眠或断网时，即使当天
其他时间开机联网，也不会利用这次机会。云端采集技术试运行已证明会碰到免费资源
上限；用户明确不付费。继续追加云端基础设施会偏离“不漏掉当天的采集机会”这个产品问题。

### 2. 用户会看到什么

```text
Mac 登录、唤醒补触发，或醒着时每个整点/半点检查
  → 今天已有完整五源快照：立即结束，不重复抓取
  → 今天尚未完成：尝试同步五家公司
  → 断网或任一源失败：留下失败事实，下一次检查重试
  → 五源完整：记为今日采集完成，发通知；官网候选另作验收证据
  → 当天后续检查全部变成轻量 no-op
```

屏幕可以锁定；只要 Mac 没有休眠且已联网，后台任务可以执行。使用电池不会阻止。
如果当天整天都没有可用机会，系统不在第二天伪造昨天快照；第二天重新记当天。

### 3. 哪些是已核实的，哪些是假设

| 事实 | 怎么核实的 |
|---|---|
| 既有三个 LaunchAgent 均已加载 | `launchctl print gui/$UID/<label>` |
| 现有三个时段只会补触发其中一个错过的时刻，不会在其他在线机会主动重试 | `scheduler.build_payload()` 只有每日一个 `StartCalendarInterval`，`RunAtLoad=False` |
| `StartInterval` 在休眠期间到点会丢失，`StartCalendarInterval` 的错过事件会在唤醒后合并触发 | 本机 `man 5 launchd.plist` 的 StartInterval / StartCalendarInterval 语义 |
| 数据库已保存每轮状态、五源结果和官网候选 | `observation_batches`、`observation_sources`、`observation_truth_candidates` |
| 同一数据库已有跨进程文件锁 | `observation.exclusive_run()` |
| 云端定时任务未启用 | `launchctl` 显示 `cloud-check` 未加载；GitHub Workflow 仅手工试运行 |

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|
| 登录 + 整点/半点 calendar 触发能覆盖当天的开机联网窗口 | 唤醒后网络恢复晚于补触发时，第一次可能失败 | `RunAtLoad` + `StartCalendarInterval=[Minute 0, Minute 30]`，失败留痕后等下一个 calendar 机会 |
| 日历日每天一次比只限工作日更不易漏变化 | 周末会多一次公开请求 | 首周观察耗时与失败率；不改变安全边界 |
| calendar 错过事件在本机唤醒后能触发新入口 | 真机行为与手册或测试 adapter 不同 | 安装后做一次真实休眠/唤醒验收，核对进程 exit status、日志和同一生产 DB |

## 二、具体实现

### 4. 数据长什么样，空值怎么办

不新建数据表。当天完成由已有事实推导，不写第二份“daily status”：

```text
observation_batches: observed_date + status=ok + finished_at 非空 + trigger in (scheduled, flexible)
observation_sources: 该 batch 恰好有五个批准 source_key，status 全为 ok，run_id 全非 NULL
observation_truth_candidates: 独立保存官网候选，供人工真值验收，不参与“今天是否需要重抓”的判断
```

| 字段 | 有值时 | 取不到时 | 空值和不匹配分开了吗 |
|---|---|---|---|
| `observed_date` | ISO 日期 | 批次不合法，不参与完成判定 | 是 |
| `run_id` | 可回溯底层采集 | `NULL` 时 source 不能算完整 | 是 |
| candidate `official_ids_json` | 完整、可为空的官网岗位清单 | 取数失败为 `NULL` + `status=failed` | 是；官网权威空清单不等于网络失败 |
| notification `error` | 本机通知失败原因 | 成功/策略跳过时 `NULL` | 是；通知失败不撤销已完成采集 |

### 5. 硬约束在哪里

- “今天是否已完成”、“本轮采集”和“本轮候选生成”在同一个 `exclusive_run()` 锁内，两个定时触发不能同时越过检查。
- 只有批次和五个批准来源全部 `ok`、都绑定真实 `run_id` 才认定当天采集完成；任一来源失败/半成品才允许后续机会重抓。
- 官网候选失败或与刚完成的快照不同会明确通知并阻止真值确认，但不会重新抓取五家公司。招聘门户在两次独立读取之间出现正常上架/下架时，不能把这种时间漂移误判成采集失败。
- 通知与采集完成分开：数据完整后不因本机通知失败重抓岗位；失败通知保留可观测状态，不自动重发。
- 新 LaunchAgent 用直接 Python argv，不经 shell；plist 权限保持 `0600`。
- 调度切换的固定锁顺序是：先获得生产 DB 的 `exclusive_run()`，再获得 scheduler 锁。旧采集正在运行时零 LaunchAgent 变更。
- 切换是补偿式替换，不宣称文件系统和 launchctl 具备跨系统原子事务。它先把旧三任务/新任务的文件与 loaded 状态写入 0600 cutover marker，再卸载旧任务、写入/加载新任务；其他 installer 看到 marker 必须停止。首次 RunAtLoad 验收成功后删除 marker；失败时重新按固定锁顺序取得双锁并按 marker 恢复，恢复也失败则抛 `SchedulerRollbackError` 并保留 marker/现场。
- 新任务首次真实运行验收前保留旧三 plist 作为回滚载体，但它们必须全部 unloaded；老 `schedule-install` 在 flexible 已加载时也必须拒绝。
- 切换命令必须先从数据库证明：以 `through_date` 当天（周末则上一个周五）为 streak 终点，往前恰好有 3 个连续周一至周五完整五源日；未来行不计，更旧的历史 streak 不能代签，不再要求切换日额外跑满旧三时段。官网人工核对独立保留，不能用切换成功代签无漏报验收。第一版不引入中国法定节假日数据，沿用项目的周一至周五口径。
- 本地灵活调度、旧三时段调度和 `cloud-check` 三类安装器双向互斥。唯一迁移例外是 `install_flexible` 可以接管“只有旧三任务、每个 loaded 任务都有可恢复 plist”的精确现场；缺任务、混合 loaded、loaded 无 plist、cutover marker 未收口均 BLOCK。flexible 幂等只接受“它是唯一 loaded 类，且 plist 字节等于候选”。旧 `install()`、`install_cloud_check()` 发现 flexible 或 marker 时始终零更改停止。不自动删除云配置或远程资源。
- 部署前只读核验 GitHub 默认分支所有 enabled Workflow 无 `on.schedule`、Cloudflare exact Worker `jobagent-public-observation` live schedules 为空、本机 `cloud-check` 未加载。GitHub 使用固定仓库 `fishINlab666/job-agent` 的 REST 元数据和默认分支 Workflow 原始字节；Cloudflare 使用官方 schedules GET 或登录后台同一 exact Worker 的 Cron Triggers 可见 readback。`active / unauthorized / query failed / ambiguous / 只看本地配置` 一律停止，不自动删除。

### 6. 判据的粒度

- “已完成”按日历日 + 一个完整 batch，不按触发次数。
- “五源完整”比较精确 `source_key` 集合，不只比数量。
- “官网候选完整”比较精确 `source_key` 集合 + `captured` 状态，并把每份候选的岗位 ID 集合与对应 `run_id` 的 snapshots 集合逐字比较；数量相同但 ID 不同也不能签真值，但不撤销已经完成的五源采集。
- “三天试运行”按连续工作日检查；切换后的日常采集按每个日历日检查，包括周末。
- “本日通知”汇总当日所有新模式尝试的已持久化变化；通知结果不改写采集事实。
- “每日官网人工确认”在旧模式是 3 轮 × 5 源，在 flexible 模式是当日首个完整 batch × 5 源；两者共用 `record_truth()`，不新写第二套证据表。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| 每日成功次数 | 第一个完整 batch | 每个日历日最多 1 | 日期变化时重置 |
| 检查次数 | LaunchAgent 触发 | 在线时约每 30 分钟 1 次 | 会，休眠时不运行 |
| 三天进度 | 截至当天连续完整工作日 | 固定 3 | 只在切换前使用 |
| 当天岗位变化 | 完整 batch 的四类真实事件 | 不设分母 | 会，按实际快照变化 |

### 8. 这次明确不做什么

- 不再调试或扩容 Cloudflare/GitHub 采集链；免费技术试运行记录保留，但定时保持关闭。
- 不删除 Cloudflare D1、Worker、GitHub secret 或历史运行；删除是另一个破坏性边界。
- 不改岗位解析、归一化、匹配、分类、通知筛选或真实投递。
- 不用“网络已联通”独立探针代替真实采集；采集本身成功才是有效机会。
- 不把三天采集成功冒充为官网人工真值验收；既有 `observation_truth_evidence` 仍须独立确认。
- 不新建网页面板；仍使用日志、数据库和本机通知。

## 四、复盘（实现完回填）

### 11. 方案和实现差在哪

- 2026-08-27 生产预检发现蔚来在独立候选读取期间发生一进一出：两次各自完整 962 条，但 ID 集合相差两条。由此把 `completed_daily_collection()` 收口为“五源同步完成”，候选逐字比较只留在 `official_truth` 真值审核；采集完整性没有降低，也不再因正常时间漂移反复抓取。
- 计划要求 daily 完成判据复用官网审核，本次抽取为 `validate_candidate_snapshot()`，旧 15 格和新 5 格共同调用，没有保留两份校验规则。
- 切换恢复按 Gate 建议增加 0600 marker 与 `schedule-flexible-recover`。这是处理 kill/断电的必要恢复入口，不是新的采集链；正常用户流程不会调用。
- 当前只完成代码候选和测试，尚未修改真实 LaunchAgent；实际 release SHA、线上定时只读检查和真机唤醒验收必须在第 3 天回填。

### 12. 实现中踩到的坑

- `test_completed_daily_collection_is_not_invalidated_by_later_truth_drift`：数量相同但 ID 不同不能签官网真值；同时，两次独立读取间的一进一出也不能撤销已完成的五源采集。
- `test_flexible_daily_review_uses_changes_from_earlier_attempts`：重试成功的零变化不能掩盖当天早先已持久化的变化，通知按日聚合。
- `test_flexible_recover_rejects_tampered_plist_path`：恢复 marker 只能指向固定四个 LaunchAgent plist，不能接受任意路径。
- `test_flexible_recover_does_not_overwrite_a_job_that_cannot_stop`：任务停不下来时保留现场，不能继续覆盖 loaded plist。
