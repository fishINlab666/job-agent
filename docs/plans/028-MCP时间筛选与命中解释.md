## 一、产品设计

### 1. 为什么现在做

Codex 已经接通五个严格只读 MCP 工具，但真实使用第一次就发现两个会影响判断的问题：

1. `job_changes(since=...)` 接受带时区的 ISO 时间，却把原字符串直接交给 SQLite
   做文本比较。同一个时刻写成 `+08:00` 返回 1 条，写成 `Z` 返回 158 条，
   会把旧事件混进“这个时间之后”。
2. `explain_match` 对不命中和信息不全能给具体原因，对确定命中只说“命中”并给一个
   没有分解的分数。用户无法核对是岗位族、届别、城市还是关键词让它排到前面。

不先修这两项就继续收集“第五/第六工具反馈”，会把现有工具的错误和真正的能力缺口混在一起。

### 2. 用户会看到什么

```text
用户用北京时间或 UTC 查询同一时间窗口
    → 系统返回完全相同的岗位变动集合

用户问“为什么这条适合我”
    → 系统列出通过的硬筛选维度
    → 再列出关键词、城市和招聘类型分别加了多少优先级分
    → 明确总分只是排序优先级，不是录用概率
```

### 3. 已核实与假设

| 事实 | 怎么核实的 |
|---|---|
| 运行包与远端 `main` 均为 `5a8a329…`，注册表只有五个工具 | GitHub main / PR #54 只读查询；Codex `ALL_TOOLS` 与真实 MCP 调用 |
| `since=2026-08-26T20:36:47+08:00` 返回 1 条 | Codex 实调 `job_changes(limit=200)` |
| 等价的 `since=2026-08-26T12:36:47Z` 返回 158 条 | 同上；两次事件 ID 集不同 |
| 命中岗位返回 `reason="命中"` 和未分解的 `score` | Codex 实调 `explain_match` |
| `matched=true` 的岗位已经按 `match.score` 降序，不是单纯按时间 | `queries.open_jobs` → `match.filter_jobs` → `partition` 源码与真实分数序列 |

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|
| SQLite `julianday()` 能把 `Z` 与显式 offset 转成同一时间轴 | 等价时刻仍会筛出不同事件 | 在临时库插入边界前后事件，用两个 offset 跑同一查询并逐字比较 ID |
| 分数分解可以作为现有 `score()` 的唯一计算来源 | 展示分解与排序总分可能漂移 | `score(job, intent) == score_breakdown(...)["total"]` 的回归测试 |
| 只返回 intent 白名单相关的匹配理由不会泄露 identity | 姓名、电话等可能进入对话 | 复用现有 profile 哨兵测试，并对新增返回字段做全文扫描 |

## 二、具体实现

### 4. 数据形状与空值

| 字段 | 有值时 | 取不到时 | 空值与不匹配是否分开 |
|---|---|---|---|
| `since` | 带时区 ISO 时间；按真实时间轴比较 | `None` = 不加时间筛选 | 是；非法/无时区继续报错 |
| `matched_on` | 通过的硬筛选维度文案列表 | 没设硬筛选时为空列表 | 是；空不代表不命中，`state` 仍是唯一结论 |
| `score_breakdown.boost_keywords` | 命中的加分词与分数 | `matched=[]`、`points=0` | 是 |
| `score_breakdown.cities` | 明确命中城市或通配城市及分数 | `matched=[]`、`points=0` | 是 |
| `score_breakdown.recruit_type` | `campus` 时 3 分 | 其他类型 0 分 | 是 |
| `score_breakdown.total` | 三类分数之和 | 最低为 0 | 不适用 |

`score_breakdown` 只解释轻量排序分；岗位族、届别等是“能不能进入候选”的硬筛选，
放在 `matched_on`，两者不得混成同一种概率分。

### 5. 硬约束

- MCP 注册表仍精确为五个工具；不增加第六工具。
- 所有查询继续使用 SQLite `mode=ro`；不引入 mark/readback 等写状态。
- 画像仍只通过 `INTENT_KEYS` 白名单；新增解释不得读取或返回 identity、教育、经历、截图。
- `state` 仍只有 `hit / miss / unknown`，新增字段不能把 unknown 洗成 hit。

### 6. 判据粒度

- 时间筛选按**时间轴上的瞬间**比较，不按 ISO 字符串字典序，也不按“日期看起来一样”比较。
- 命中解释按**匹配维度**列证据；排序解释按**计分因子**列分数。
- `reason` 是给人看的摘要，`matched_on` / `score_breakdown` 是稳定的结构化证据。

### 7. 数字口径

| 数字 | 分子/含义 | 分母 | 会不会变 |
|---|---|---|---|
| `points` | 对应单一计分因子的整数贡献 | 无 | 随岗位和画像变化 |
| `total` | 全部计分因子 points 之和 | 无 | 随岗位和画像变化 |
| 事件条数 | `since` 所代表瞬间之后、符合 kind 的最近 `limit` 条 | 该时间窗事件全集 | 数据采集后会变 |

分数不是录用概率、不是投递成功率，也不是匹配置信度；只用于同一画像下的展示排序。

### 8. 明确不做

- 不开发第六工具；真实高频缺口尚未达到立项阈值。
- 不把 `applications`、浏览器体检、同步或投递接进 MCP。
- 不重新设计匹配规则、权重或岗位族分类；只解释现有规则。
- 不迁移数据库时间格式；查询层兼容现有带 offset 文本。
- 不修改真实数据库、画像、Codex 配置或定时采集。

## 四、复盘（实现完成后回填）

### 11. 方案和实现差在哪

- 时间修复按计划使用 SQLite `julianday()`；同时把事件排序改为同一时间轴，避免
  不同 offset 的事件继续按字符串顺序排错。独立审查发现 MCP 跨 kind 合并还有
  第二次字符串排序，最终改为复用查询层的时间轴解析函数。
- Python 接受的紧凑 ISO / week-date 不一定能被 SQLite 直接解析；最终在 MCP 入口
  统一规范成 UTC 扩展格式，避免“参数合法但正常返回 0 条”。
- 分数明细最初只给明确城市；RED 补测后发现通配城市会显示 `matched=[]`，最终把
  `全国/不限/远程` 的实际命中值也放进明细，分数仍保持原来的 1 分。
- 硬筛解释最初另写 `hit_evidence()`，漏掉了排除词并形成第二套规则；最终把证据
  直接放进 `classify()` 的 `Verdict`，判断与解释在同一处生成。
- MCP 边界测试第一次用了默认测试画像，先得到 `unknown`；改成用例自带完整 intent，
  才精确验证新增字段有没有穿过真实协议。

### 12. 实现中踩到的坑

- 不能只断言 `reason != "命中"`：那样把文案换长一点也能假绿。测试必须同时核对
  `matched_on`、三类计分明细和 `score == total`。
- 不能用缺画像的 MCP fixture 验 hit 输出；缺画像本来就应当是 `unknown`，这不是实现
  缺陷。测试现在显式构造最小完整画像。
- 查询 Module 绿不等于真实 MCP 绿：MCP 还会跨事件类型合并、排序、截断，必须再有
  一条走真实协议的混合 offset 用例。

### 13. 如果重来，方案里该提前写上哪句话

“结构化解释必须由判定本身产出，不能平行重算；时间语义必须从参数校验一路覆盖到
最终跨类型聚合。边界测试要先证明输入确实能产生目标状态，不能让另一个合法前置
失败抢先成为 RED。”
