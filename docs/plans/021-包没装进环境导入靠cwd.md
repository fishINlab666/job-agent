## 一、产品设计

### 1. 为什么现在做

不做的后果**已经发生了一次，而且我差点把它归错因**。

014 的最后一环是「把 MCP server 也挂到 Claude Desktop 的对话侧」。我当时挂着的
下一步是「往 `Claude-3p/claude_desktop_config.json` 里补 `mcpServers`」。那一步
会失败 —— Desktop 启 stdio server 的 cwd 不是仓库根，`-m jobagent.mcp_server`
会直接 `ModuleNotFoundError`。而失败的表现是**「配了但对话里看不见工具」**，
跟 014 §11 ⑦ 那次（配进了 App 不读的目录）长得一模一样。

上一次我把那个表现归因成「目录不对」，花了二十来次工具调用才查出来。这一次
如果先改配置，我大概会归因成「这个构建不支持用户配的 server」，然后写进方案，
然后它就成了一条**没人再验的错误结论**。

现在 Claude Code 侧能用，靠的是一个巧合：`claude mcp add -s local` 注册的 server，
客户端启它的时候 cwd 正好是项目目录。这个巧合没写在任何地方，也没有任何东西守着。

第二个后果是 `[project.scripts]` 那个入口点。`docs/MCP_SETUP.md:9` 写着
「想投递还是走 `jobagent prepare`」—— 照着敲得到 `command not found`。

### 2. 用户会看到什么

```
现在：
  在 job-agent 目录里开会话 → 问「蔚来还有几个开放岗位」 → 工具起得来 ✓
  在别的目录里开会话       → 同一句话           → 工具起不来，且看不出为什么 ✗
  照 MCP_SETUP.md 敲 jobagent prepare          → command not found ✗

改完：
  任何目录开会话 → 问同一句话 → 工具起得来
  敲 jobagent prepare → 走到两阶段闸门的第一阶段（prepare，不提交）
```

对**不懂技术的人**说这件事：这个项目的代码一直没有真的「安装」到环境里，只是
「你站在它的文件夹里，所以它能找到自己」。换个文件夹就找不到了。

## 二、具体实现

### 4. 数据长什么样，空值怎么办

这次不产出数据，但有一个「取不到值」要交代：**包在两个地方都可能被找到**
（site-packages 的 editable 指针、cwd 的隐式 `sys.path` 条目），而它们可能指向
不同的副本。

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| `importlib.util.find_spec("jobagent").origin` | 绝对路径 | `find_spec` 返回 `None` | 是 —— `None` 是「找不到」，路径不对是「找到了错的」，测试分两条断言 |
| `shutil.which("jobagent")` | venv/bin 下的绝对路径 | `None` | 是 —— `None` 是「没装」，指向 venv 外是「装到别处了」 |

> 这一栏本来想留空，但「找到了错的副本」正是 editable 安装的典型故障：
> 仓库根的 cwd 条目和 site-packages 的指针同时在，测试跑的是前者，
> 而 MCP server（cwd 在别处）跑的是后者。两者不一致的话，
> **测试全绿而 server 行为不同** —— 所以测试要断言 `origin` 就在这个仓库里。

### 5. 硬约束在哪一行

这次没有不可撤销后果，全是软约束级别的改动。但有一条要写死：

**装成可安装包**不许改变 MCP 层的只读边界。`[project.scripts]` 复活之后
`jobagent prepare` 变成真能敲的命令，而 `prepare` 是两阶段闸门的第一阶段
（只准备、不提交）。`execute` 仍然只在人逐字段看过并明确点头之后才跑 ——
这条约束在 `jobagent/submitters/` 里，这次一行都不碰。

### 6. 判据的粒度

「包装好了」这个判断有三级，差一级验的就不是同一件事：

| 级别 | 判据 | 差在哪 |
|---|---|---|
| 文件级 | `pyproject.toml` 里有 `[build-system]` | **最弱**，这是我的动作，不是环境的反应 |
| 环境级 | site-packages 里有 editable 指针 | 装了，但没证明能用 |
| 行为级 | **从仓库外的 cwd** `import jobagent` 成功、且 `origin` 指回本仓库 | 这一级才是要的 |

判据取**行为级**，而且必须带 cwd 变化 —— 在仓库根跑 `import jobagent` 成功是
现状就成立的，取值域是常数，等于没判据。

### 7. 数字的口径

这次不产出比率型数字。唯一的数是测试条数，按仓库规矩只写在 `README.md` 的
现状栏、紧挨着产出它的命令。

### 8. 这次明确不做什么

- **不去验 Claude Desktop 对话侧到底支不支持用户配的 server。** 因为现在验等于编：
  在包没装进环境之前，那条路一定失败，而失败的表现和「不支持」一模一样。
  修完之后这个假设变成无关项（cwd 不再影响结果），届时再单独验。
- **不改 `~/.claude.json` 的注册 scope。** 014 §11 ⑥ 选 `local` 的理由（`project`
  scope 会把机器专属的 venv 路径写进仓库根的 `.mcp.json`，别人 clone 下来就是坏的）
  仍然成立。装成可安装包之后 `user` scope 才**有可能**是对的，但那是另一件事。
- **不删 `pythonpath = ["."]`。** 留着不会错，删了要重验全量。省下来的那点整洁
  换不来这个风险。
- **不动 `[project.optional-dependencies] mcp`。** 那个分组的理由（20 个包 CLI
  一个都用不上）没变。

## 三、怎么验

### 9. 验证命令

**A. 从仓库外导入（这次的核心判据）**

```bash
cd /tmp && "$OLDPWD/.venv/bin/python" -c "import jobagent, importlib.util as u; print(u.find_spec('jobagent').origin)"
```

改前：`ModuleNotFoundError`。改后：打出仓库内的绝对路径。

**B. 入口点真的存在**

```bash
uv run jobagent --help
```

改前：uv 会去装一个叫 job-agent 的 PyPI 包或直接报找不到。改后：打出 CLI 帮助。

**C. MCP server 从任意 cwd 起得来（带对照组）**

```bash
cd /tmp && uv run --project /Users/wujingyu/Desktop/AI/projects-jobs/job-agent python /tmp/mcp_probe.py /tmp
```

判据是 6 个工具全在 + `list_jobs` 返回 `total>0`。对照组是同一条命令把 cwd 参数
换成仓库根 —— 两边都该绿，**只有仓库外那边改前是红的**。

**D. editable 而不是快照**

```bash
uv run python -c "import jobagent, pathlib; print(pathlib.Path(jobagent.__file__).resolve())"
```

打出来必须是仓库里的 `jobagent/__init__.py`，不是 site-packages 里的副本。

**E. 全量 + 新守卫**

```bash
PYTHONDONTWRITEBYTECODE=1 uv run pytest -q -p no:cacheprovider
```

**F. 逐条改坏验红**

```bash
PYTHONDONTWRITEBYTECODE=1 uv run python scripts/mutate_021.py
```

### 10. 测试钉的是哪几条

| 结论 | 测试 | 做一半会红的那条 |
|---|---|---|
| 包能从仓库外导入 | `test_importable_from_a_foreign_cwd` —— 起子进程，`cwd=tmp_path`，不带 `PYTHONPATH` | 同一条：只加 `[build-system]` 而没 `uv sync`，它就红 |
| 导入到的是本仓库这份，不是别处的副本 | `test_import_resolves_into_this_repo` 断言 `origin` 在仓库树内 | 装成非 editable（快照副本）时红 |
| `[project.scripts]` 声明的入口点真的存在 | `test_declared_console_script_exists` —— 读 `pyproject.toml` 的声明，逐个 `shutil.which` | 只装包不生成脚本时红 |
| 文档里出现的 `jobagent <子命令>` 都是真子命令 | `test_docs_bare_jobagent_commands_exist` | 复活入口点但子命令名写错时红 |
| MCP server 的模块能被 `-m` 找到 | `test_mcp_server_module_spec_found_from_foreign_cwd` | 同上 |

**关于「做一半」**：这次最像的半成品是「加了 `[build-system]` 但 `uv.lock` 没更新」
—— 别人 clone 下来 `uv sync` 装的还是虚拟项目。`uv.lock` 里那行 `source` 从
`virtual` 变 `editable`，所以加一条读 lock 的断言：`test_lock_records_project_as_editable`。

> 这一条是**文件级判据**（§6 里最弱的那一级），单独放它不够。它的作用不是证明
> 能用，是证明**别人也能用** —— 行为级判据只能证明我这台机器的 venv 现在是对的。

**关于反向用例**：`test_declared_console_script_exists` 要能查出「声明了但没装」，
也要能查出「装了但 `pyproject` 里没声明」（后者说明有人手工塞了脚本）。两个方向
各一条断言。
