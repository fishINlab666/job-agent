## 一、产品设计

### 1. 为什么现在做

`mcp_server.py` 把自己描述为“形状上做不到投递、`SESSIONS` 这一层压根不碰”，但运行时注册表仍暴露 `check_form_selectors`。该工具接受模型提供的 `user_data_dir`，经 `routing.get_submitter()` 启动带招聘站登录态的真实浏览器；Feishu/Tencent 的 `prepare(fill_fields=False)` 仍会 mint token 并短暂写入 `SESSIONS`。

2026-08-19 又确认本机 Claude 同时从项目配置和 Desktop 配置启动两组该 server。继续等待 CI 才处理，会延长一个已实际加载的登录态/真实浏览器能力。本 Plan 只做最小注销，不重构浏览器体检。

### 2. 用户会看到什么

临时隔离期间，Claude 看不到 `job-agent` MCP；CLI 查询与 `cli checkup` 不受影响。

#32 随 PR #1 进入并验证于 `main` 后，重新连接一个获批 clean checkout 时，客户端只能看到五个本地只读工具：

```text
list_jobs
explain_match
list_sources
list_sync_runs
job_changes
```

客户端不能再调用 `check_form_selectors`，也不能从任何 MCP tool schema 传入登录态目录、cookie 或浏览器 profile。若用户需要检查真实表单选择器，继续在 CLI 中人工执行 `checkup`；该动作不进入 MCP。

## 二、具体实现

### 4. 数据长什么样，空值怎么办

本 Plan 不新增持久化数据、数据库列或外部 payload。

| 字段 / 状态 | 有值时 | 取不到时 | 语义是否分开 |
|---|---|---|---|
| MCP registry tool name | 必须属于五工具精确白名单 | 缺工具即注册表变化，测试失败 | 是；缺失与额外工具都失败 |
| tool input property | 只允许该只读工具的业务筛选字段 | schema 无该字段 | 是；`user_data_dir` 等敏感字段是禁止态，不是 optional |
| base/candidate JUnit | 解析为 failed/error nodeid 集合 | 文件缺失或 XML 无法解析 | 是；解析失败直接 Gate BLOCK |
| Claude server process | 记录旧 app/后代 PID；重开后所有新 app 后代和全局 argv token 均不得含 `jobagent.mcp_server` | 结构化 `ps` 或客户端列表无法取得就是 unknown，不是 0 | 是；需连续三次观测且两客户端 registry 均无条目 |
| required check | W0-01 后才有 | 本轮明确为 absent | 是；absent 叫 manual-gate，不伪称 CI passed |

### 5. 硬约束在哪一行

安全 seam 是 `mcp_server.mcp` 的真实注册表：模型只能调用注册进去的工具。删除工具 Implementation 后同时增加四层守卫：

1. 注册表全集必须恰为五个名字。
2. 红阶段先以 AST/注册表断言阻断，绝不调用旧 handler；同一测试只有在确认定义、注册项和 `routing` bridge 都已消失后，才通过真实 MCP Client 调旧名字并断言协议层 `is_error`。
3. 所有注册工具 input schema 的属性不得出现登录态/浏览器路径字段。
4. `mcp_server.py` 的 import graph 不得再跨到 `routing`/Submitter seam。

提示词、docstring、`readOnlyHint` 或“工具名以 check 开头”都不是安全保证，不能代替以上硬约束。

### 6. 判据的粒度

- 判据粒度是**运行时注册表成员资格**，不是工具名动词。
- `check_form_selectors` 即使没有写数据库，也属于**带登录态的外部交互**，不能计入严格本地只读工具。
- CLI `checkup` 与 MCP tool 是两个 Interface：本轮只删 MCP Interface，保留 CLI Implementation。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| MCP 工具数 | 运行时 registry 返回的 tool object | 同一 registry 全集 | 当前目标固定为 5；新增工具必须另审 |
| 临时配置条目数 | 两个获批配置 scope 中名为 `job-agent` 的 object | 两个固定 scope | 隔离期固定为 0 |
| server 进程数 | command 含 `jobagent.mcp_server` 的实际进程 | 本机进程表 | 会动；每次恢复/重启都重读 |
| 新增失败数 | candidate failed/error nodeid 减 base 集合 | 同环境、同命令的两份 JUnit | 候选变化即重跑；必须为 0 |

### 8. 这次明确不做什么

- 不给 MCP 体检增加安全目录 key，因为当前目标是立即关闭暴露，不是设计新浏览器 Interface。
- 不改 Submitter、`routing.py`、`SESSIONS` 或 token 生命周期；它们属于 CLI 投递/体检 Implementation。
- 不修改数据库、投递状态机、岗位身份或画像语义。
- 不新增 CI/workflow/Ruleset；它们由 W0-01 / Plan 022 处理。
- 不编辑 Issue #32 正文来伪装问题已经修复。
- 不把 Issue #32 原文的“修法建议”当成已批准方案；开实现分支前，只能追加一条绑定获批 Plan SHA 的状态评论，说明路线 A 改为完整注销。评论是单独 GitHub 写，本轮不授权。
- 不提交 Claude 配置、用户名、登录目录、cookie、截图、真实画像或本机 process dump。
- 不修改未跟踪的 `AGENT_HANDOFF.md`；其完整收口仍归 W0-06。
- 不自动恢复 MCP 配置；恢复是 #32 进入 main 后的新审批。
- 不从后续叠加栈复制 `docs/MCP_SETUP.md`。它由 PR #15 首次引入；W0-03 到 PR #15 时必须先展示一个只把该文档当前工具清单同步为五工具的精确兼容补丁并单独批准，随后才允许继续该层 candidate Gate，禁止临场顺手修改。

        if isinstance(value, dict):

                yield str(key).lower()
                yield from keys(nested)
