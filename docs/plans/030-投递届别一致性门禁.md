## 一、产品设计

### 1. 为什么现在做

发现侧的岗位匹配使用 `profile.yaml.intent.grad_years`，投递侧填表使用
`profile.yaml.education[*].end`。两份值可以互相矛盾：系统仍会把岗位解释为“命中”，
而 `apply` 会拿另一届的表单资料打开浏览器并开始填表。

最终提交虽然仍有人工确认，但用户不应该到表单页才发现自己根本不符合届别要求。
不做的后果是：

1. 推荐结果看似可投，实际资格不符；
2. 真实姓名、手机、简历可能已经被填进对方页面；
3. 数据库提前留下 `reserved` / `blocked` 投递痕迹；
4. 用户把问题误判成表单自动化故障，而根因其实是资格不匹配。

### 2. 用户会看到什么

明确不匹配：

```text
用户运行 apply <岗位编号>
  → 系统读取岗位届别和画像里的真实毕业年份
  → 届别不相交
  → 屏幕显示“这份资料的毕业届别不符合岗位要求”
  → 停止；不创建投递记录、不启动浏览器、不填写或上传资料
```

明确匹配或岗位明确不限届别：

```text
届别门禁通过 → 继续现有额度/防重闸门 → 预填 → 人工确认 → 才能提交
```

信息不足：

```text
岗位没写届别，或画像没有可解析的毕业年份
  → 屏幕先显示“届别需要人工核对”
  → 在打开浏览器前询问“仍要预填吗？”，默认答案为“不”
  → 回车或选“不”：停止，零路由、零占位、零浏览器、零资料填写
  → 只有明确选“是”才允许预填；最终提交仍必须再次人工确认
```

“信息不足”不能被显示成“确定符合”，也不能在用户没有明确同意时上传资料。
明确社招岗位不要求校招届别，显示为“不适用”并继续原流程。

### 3. 哪些是已核实的，哪些是我猜的

| 事实 | 怎么核实的 |
|---|---|
| `FormProfile.grad_term` 当前会把任意至少两位的纯数字截尾；`20270/123/0000` 会错误变成 `70/23/00` | 两位独立 reviewer 只读实测；这是本轮要修的生产端缺口 |
| 岗位届别已有三态解析：`None` 未知、`[]` 不限、列表为明确届别 | `jobagent/normalize.py::parse_grad_years` 及现有测试 |
| 匹配层在结构化届别缺失时才回退到标题里的“XX届” | `jobagent/match.py::classify` |
| `apply` 当前在画像加载后直接路由，再进入 `reserve_application` | `jobagent/cli.py::apply` |
| 浏览器只在 submitter 的 `prepare()` 内启动 | `tests/test_apply_quota.py::no_browser` 和两个真实 submitter |
| 生产画像与一个已选岗位出现过届别矛盾 | 只读 Review Gate 实测；公开方案不记录用户具体年份或其他个人信息 |
| 两份现有数据库的非空结构化届别只有 `26`、`27`、`不限` | 对 `data/jobagent.db` 与 `data/jobagent-5.db` 只读 `GROUP BY grad_year`；未读取画像或个人信息 |

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|
| 未知届别由用户在预填前单独决定，默认停止，兼顾隐私和无法结构化的岗位 | 用户明确继续的未知岗位仍可能不适合 | CLI 集成测试钉住默认 N 的零副作用与显式 Y 后才允许路由/预填；最终提交仍受第二道人工闸门保护 |
| 只有结构化 `grad_year` 足以支持自动硬判；标题是自由文本，只能触发人工核对 | 会增加少量预填前确认，但不会自动误放/误拦 | 对任何标题数字届别都返回 `unknown/title`；结构化值存在时不读标题 |

### 3.1 方案比较

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 独立纯函数 + CLI 前置门禁（采用） | 新建 `eligibility.py`，返回明确三态；CLI 只负责展示和停止 | 边界清楚、可独立测试、以后 submitter/其他入口可复用 |
| B. 把判断直接写进 `cli.apply` | 少一个文件 | 解析、业务判定和 UI 混在一起，其他入口容易再写一份 |
| C. 自动把 intent 届别改成教育经历届别 | 从发现侧消灭矛盾 | 静默改写用户意图，且会改变 MCP 查询结果；超出本轮安全修复范围 |

## 二、具体实现

### 4. 数据长什么样，空值怎么办

| 字段 | 有值时 | 取不到时 | “没有值”和“不匹配”分开了吗 |
|---|---|---|---|
| `FormProfile.grad_term` | 只接受 `_split_end` 后严格四位 ASCII `20xx`，返回 `"27"` | 缺失、Unicode 数字或其他畸形值返回 `None` | 是：`None` → unknown，不是 mismatch |
| `jobs.grad_year` | `"27"`、`"26-27届"`、`"不限"` | `None` / 空串 / 无法解析 | 是：解析结果分别是列表、空列表、`None` |
| 标题届别 | NFKC 规范化后两到四位 Unicode 十进制数字 +“届”只作为“存在届别线索”，覆盖普通、全角、上标、带圈及非拉丁数字 | 没有数字届别线索 | 是：标题线索一律 `unknown/title`，不自动形成 match/mismatch |
| `jobs.recruit_type` | 只有结构化届别缺失且标题也没有数字届别线索时，`social` 才表示不适用 | 缺失时不能假定社招 | 是：标题线索先触发人工核对，不被 social 标签覆盖 |
| `EligibilityVerdict.state` | `eligible` / `ineligible` / `unknown` | 不存在第四种兜底 | 是 |

纯函数接口固定为：

```python
class EligibilityState(StrEnum):
    ELIGIBLE = "eligible"
    INELIGIBLE = "ineligible"
    UNKNOWN = "unknown"

@dataclass(frozen=True)
class EligibilityVerdict:
    state: EligibilityState
    reason: str
    basis: str | None
    profile_term: str | None
    job_terms: tuple[str, ...] | None
```

公开入口的完整类型签名是
`assess_grad_year(job: Mapping[str, object], form: FormProfile) -> EligibilityVerdict`。

判定顺序：

1. 先检查 `job.grad_year`；硬门禁只接受完整匹配的正向白名单：单届、同为两位或同为
   四位且正向、跨度不超过 10 届的范围，位数一致的明确枚举，或纯“不限”词。
   两位/四位混用、全角数字、疑似、否定、排除、年份与“不限”混写、额外修饰和无法
   完整验证的值一律 `unknown/job_term_ambiguous`；
2. 结构化字段非空但不在白名单时不回退标题，避免较弱标题覆盖矛盾证据；
3. 只有结构化字段真正缺失/空白时才看标题；标题是自由文本，NFKC 规范化后任何两到四位 Unicode 十进制数字 +“届”
   都只返回 `unknown/job_term_ambiguous`、`basis=title`，由预填前默认 N 的人工确认决定。
   标题永远不能自动形成 eligible 或 ineligible；
4. 岗位解析为 `[]`（明确不限）→ `eligible/unlimited`；
5. 得到任何明确届别时，无论 `recruit_type` 是什么都按它判断；画像届别缺失
   → `unknown`，有交集 → `eligible`，否则 `ineligible`；
6. 两个届别通道都无证据且 `recruit_type == "social"`
   → `eligible/not_applicable`；
7. 其他无证据场景 → `unknown`，返回稳定的 reason code。

合法缺失和无法解析是业务上的 `unknown`。判断函数本身若意外抛异常，CLI 不得捕获后
降级放行；异常会在任何路由、写入或浏览器副作用前停线。

### 5. 硬约束在哪一行

在 `jobagent/cli.py::apply` 中，`profile.load_profile()` 成功之后、
`routing.resolve()`、`routing.get_submitter()` 和
`db.reserve_application()` **之前**调用 `assess_grad_year()`。

`ineligible` 直接 `raise typer.Exit(1)`。`unknown` 显示 reason 后调用默认 `N` 的
`typer.confirm()`，回车或 `N` 同样退出；只有显式 `Y` 继续。二者的停止路径物理上
都到不了：

- 路由和 submitter；
- 投递占位或额度占用；
- Playwright 浏览器；
- 表单填写、简历上传与最终提交。

`--again` 和 `--dry-run` 都不能绕过这道门禁或 unknown 确认，也不新增绕过参数。
显式继续后的 unknown 警告并入 `SubmissionPlan.warnings`，由现有
`mark_application_prefilled()` 写进当前 note 字段，不改 schema。

### 6. 判据的粒度

判据是**所选岗位 + 本次实际表单画像**，不是：

- 整个公司；
- `intent.grad_years`；
- 当前年份；
- 招聘入口名称的猜测；
- 用户是否愿意点击最终确认。

发现层与投递层有意采用不同证据标准：发现层可用标题回退，代价只是多展示一个岗位；
投递层只有结构化字段能硬判，标题只触发人工确认，因为误判后会打开网页并上传资料。
两层都保留三态，不会把 unknown 冒充符合。

### 7. 数字的口径

本轮不新增产品统计数字。测试条数只作回归证据，不写成长期常量。

### 8. 这次明确不做什么

- 不自动修改 `profile.yaml` 或 `intent.grad_years`，因为那会改用户意图。
- 不把真实个人年份、学校或简历内容写进方案、测试、日志或 GitHub。
- 不修改匹配排序、MCP 返回结构、采集器、数据库 schema、调度或生产数据库。
- 不自动推断岗位描述正文里的隐含届别；已有结构化字段和严格标题后备之外一律 unknown。
- 不修改发现侧 `normalize.parse_grad_years()` 的宽松展示语义；本轮只在不可逆投递入口
  叠加严格证据校验，避免影响采集、匹配和既有岗位可见性。
- 不取消最终人工提交确认，也不增加 `--yes`。
- 不顺手处理 Issue #8 的岗位族长尾。
- 不在本轮重构 submitter token、投递编排和 `reserve_application()` 身份接口，因为
  它们是独立安全债、影响两个 submitter 与已有协议；混入会把一个可验证的小门禁变成
  大范围投递重写。本轮承诺明确收窄为：保护当前唯一生产写入口 `cli apply`；未来新增
  MCP/脚本写入口前必须复用这一判定，不能直接调用 raw submitter。
- 不在本轮修复 `prepare()` 异常后的 `reserved` 收尾，因为它不影响门禁前的零副作用，
  应作为独立缺陷按现有状态机完整设计和测试，不能顺手塞进本补丁。
- 超大输入、批量部分成功和跨写原子性不适用：本门禁一次只判断一个岗位，且在首次写入
  前完成；不存在批量写事务。

## 四、复盘（实现完回填，不是写方案时填）

### 11. 方案和实现差在哪

| 方案里写的 | 实际做成什么样 | 为什么改了 |
|---|---|---|
| 三态纯函数 + CLI 前置门禁 | 按方案实现，并补稳定 `reason` / `basis` | CLI 不需要重新猜判断原因，测试也能钉住证据来源 |
| 直接复用发现侧届别解析 | eligibility seam 改为正向白名单；只在完整验证后的片段上复用规范化函数 | 两轮对抗审查证明禁词黑名单会漏等义表达并误伤“非技术”；展示容错不能直接充当投递硬证据 |
| 标题满足白名单时可硬判 | 标题任何数字届别线索都只返回 unknown，永远需要预填前人工确认 | 连续对抗审查证明自由文本后缀无法有限穷举；取消标题硬判比继续增加规则更小、更安全 |
| unknown 显式同意写入现有 note | 写入 `SubmissionPlan.warnings`，并在 dry-run、放弃、执行异常和最终结果收尾时合并保留 | GREEN 后新增审计测试发现旧终态会覆盖 prefilled note，不能只写一半 |
| 明确社招不适用届别 | 收紧为“只有结构化字段与标题都无届别证据时才不适用” | reviewer 证明 `social` 标签可能与明确届别并存；更强证据必须优先 |

### 12. 实现中踩到的坑

- **现象**：unknown 用户同意预填后，`dry-run` 终态 note 只剩 `dry_run`。
  **原因**：`mark_application_prefilled()` 先写 warnings，随后
  `complete_application()` 用终态 note 覆盖旧值。
  **修法**：CLI 对所有终态备注合并 eligibility warning；prepare blocked 也保留 warning。
  **钉住它的测试**：
  `test_unknown_consent_is_kept_in_the_existing_application_note`。
- **现象**：`非2027届`、`2027届除外` 和反向范围会被判成明确 eligible。
  **原因**：发现侧解析器为了不漏展示会尽量提取数字；投递门禁直接把宽松结果当硬证据。
  **修法**：在 eligibility seam 只让结构化字段的完整单届、合法范围、明确枚举或纯
  “不限”成为硬证据；任何标题数字届别线索统一返回 `job_term_ambiguous`，默认停止；
  不改发现侧解析器。
  **钉住它的测试**：`test_ambiguous_structured_term_is_unknown`、
  `test_ambiguous_title_term_is_unknown`、
  `test_ambiguous_term_defaults_to_no_before_all_side_effects`。
