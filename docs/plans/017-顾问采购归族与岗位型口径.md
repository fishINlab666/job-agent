## 一、产品设计

### 1. 为什么现在做

issue #8 的正文现在是错的，而它是下一步分类工作的依据。原文的结论是
「一个大桶（顾问 225 条，34.2%）+ 平坦长尾」，据此该先做的事是「把顾问归族」。
实测这个形状是 nio 把城市写进标题造成的：`校招实习-蔚来顾问-<城市>` 有 116 个
城市、`乐道顾问` 90 个，去重后仍是 206 条 distinct 标题，而它们是**同一个词表缺口**。
按岗位型重算，头部是 `策略` 10.6%，没有大桶 —— 曲线是真平的。

不改的后果不是「数字不好看」，是**下一次决策会照着假形状做**：看见 34.2% 的大桶
会去投入一条规则，做完发现只动了 2 个岗位型，然后以为「规则这条路走不通」。

顺带把两条真值得加的词落地（`顾问`、`采购`），因为试算已经做完了，
证据摆在这儿不用不合算。

### 2. 用户会看到什么

```
用户跑 jobagent sync                → 247 行（顾问 233 + 采购 14）不再是「岗位族未知」
用户跑 jobagent digest              → 这批不再出现在「信息不全」分组里，
                                      而是明确地不匹配（岗位族 sales 不在 [operations, product]）
用户读 issue #8                     → 「658 条判不出」改成「502 个岗位型，其中 452 个判不出」，
                                      并写明两种口径差在哪
```

对这份画像（`families: ["operations", "product"]`），`顾问 → sales` 的效果是
**把 233 行从「不确定」搬到「确定不合」**。不是让它们变成候选，是让它们不再占用
「待人工看」的位置。

### 3. 哪些是已核实的，哪些是我猜的

**这张表里所有的数都是「改规则之前」测的（2026-08-12 库快照，`normalize.py`
还没有 `顾问`/`采购` 两条）。** 规则加上之后同一条命令给的是别的数 ——
`顾问`/`采购` 变成救回 0（它们已经在表里了），`vocab-curve` 的分母从 452 掉到
418、头部 `策略` 从 10.6% 变成 11.5%。这不是数错了，是**判据本身变了，
基数跟着变**。改后的对照见 §9 命令 A′。

写这段是因为「已核实 + 一条能跑的命令」有个陷阱：命令还能跑，输出已经不是
表里这个数，读的人会以为方案在说谎。凡是拿自己要改的东西当分母的测量，
都必须写清测的是改之前还是改之后。

| 事实（改规则**之前**测） | 怎么核实的 |
|---|---|
| 判不出的 708 条 distinct 标题塌成 502 个岗位型 | `measure_family_gaps.py city-collapse` |
| 放大只集中在 2 个岗位型（蔚来顾问 116、乐道顾问 90），第三名是 3 | 同上，放大榜 |
| 502 个岗位型下面，family 结论全部一致（剥城市没剥过头） | `vocab-curve` 头两行，不一致就拒绝出数 |
| 按岗位型算，判不出 452 个，头部 `策略` 48 个（10.6%） | `vocab-curve` |
| `顾问 → sales` 救 233 行 / 21 个岗位型，两个插入位置都改判 0 | `candidates` |
| `采购 → other` 救 **14** 行（不是 17）/ 14 个岗位型，末尾插入改判 0 | `candidates`；17 的来历见下方注 |
| `采购` 放进 `COMPOUND_RULES` 会改判 5 条（`采购方向` 是修饰语） | §6 的 heredoc，输出见 §9 命令 D |
| `服务 → sales` 进 sales 组会把 28 行 tech 改判成 sales | `candidates` |
| 这份画像里 `sales` 和新族 `service` 效果相同（都判「不在目标族」） | `jobagent/match.py:89-90` + `profile.yaml:7` |

**注：`采购` 那行原本写 17，回填时对不上，查清了 —— 两个数都是真的，数的不是一批东西。**

```
在架 + 标题含「采购」                       23 行
  ├─ 规则判 other 的                        17 行  ← 原来写的这个
  │    ├─ 库里现在是 NULL（这条规则救回的）   14 行  ← 该写的这个
  │    └─ 库里已经是 other（别的规则早判出）   3 行
  └─ 规则判别的族（product 3 / tech 2 / finance 1）  6 行
```

「一条规则值多少」该数的是**它把多少行从 NULL 变成有值**，
不是「多少行最终是这个族」—— 后者把别人的功劳算进来了。
`顾问` 那边两个数恰好都是 233（含顾问的 235 行里，另外 2 行是 marketing，
没有一行是「已经判成 sales」的），所以同一个口径错误在它身上不显形。
**一个数在一处对得上，不代表口径是对的。**

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|
| `乐道顾问`/`蔚来顾问` 是门店销售岗，不是售后服务岗 | 归 sales 而不是新开 service 族，判据本身错了；但对这份画像两者结果相同，只在画像改成想投服务岗时才暴露 | 不验。理由见 §8：这份画像下两者不可区分，现在定 service 等于编 |
| `AI时尚顾问实习生-广告业务` 归 sales 是错的（更像 product/operations） | 1 行被判成 sales，如果它真是 operations，这行从「不确定」变成「确定不合」，用户看不到它 | 已知误判，写进 §7 的代价栏；不为 1 行加例外，理由见 §8 |
| 剥「尾段是城市名」不会把两个真不同的岗位并成一个 | 岗位型数偏小，曲线偏乐观 | `vocab-curve` 里的 `disagree` 检查：同一 stem 下 family 结论不一致就拒绝出数（现在 0 条不一致） |

## 二、具体实现

### 4. 数据长什么样，空值怎么办

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| `jobs.job_family` | `FAMILIES` 里的一个 | `None` | 是 —— `match.py:86` 把 `None` 走 `unknowns`（「岗位族未知」），`fam not in fams` 走 `miss`。这次改动只把一批行从前者搬到后者 |
| `family_from_title()` 返回值 | 族名 | `None` = 判不出，调用方用源站族兜底 | 是 |
| `_stem_map()` 的 stem | 剥掉尾部城市的标题 | 标题本身不含城市时 stem == 标题 | 不涉及空值；但**空 stem 要防**：标题整个就是一个城市名会剥成 `""`，实测 0 条，加断言 |

### 5. 硬约束在哪一行

这次全是软约束级别的改动 —— 改错了顶多是岗位分类不准，不产生不可撤销后果，
不涉及代投/删除/外发。

唯一需要「硬」一点的是**测量脚本不许出错数**：`vocab-curve` 的 `disagree` 检查
和 `candidates` 的 `drift` 检查都是**先自证再出数**，不一致就打印原因并 `return`，
不是打个 warning 继续算。理由是这两个脚本的输出会被抄进 issue 和方案，
错数比不出数难发现得多。

### 6. 判据的粒度

三个词各是哪一级，差一级会命中什么：

| 词 | 这一级是 | 差一级会命中 | 结论 |
|---|---|---|---|
| `顾问` | 职能级（面客销售/咨询） | 无更粗的一级；`AI时尚顾问` 里它是**头衔**不是职能 | 加。已知 1 个岗位型误判 |
| `采购` | 职能级（供应链） | `采购方向` 里降级成**域词**（`AI产品经理（采购方向）`：职能是产品） | 加，但只能加在 `TITLE_RULES` 末尾 |
| `服务` | **域级**，不是职能级 | `抖音生活服务` 是业务线名、`服务工程` 是技术岗、`服务大区管理` 是管理岗 | **不加**。这正是 issue #9 的形状 |

`采购` 的层位是量出来的，不是推出来的：

| 放哪 | 救回 | 改判 | 改判的是什么 |
|---|---|---|---|
| `COMPOUND_RULES` 的 other 组 | 14 条标题 | **5 条** | `AI产品经理（采购方向）` product→other、`采购政策与合规` finance→other、`硬件采购实习生` tech→other |
| `TITLE_RULES` 末尾 | 14 条标题 | **0 条** | —— |

原因是 `COMPOUND_RULES` 在第 2 层**之前**，会盖住 `产品`/`财务`/`硬件` 的既有命中。
`other` 在第 2 层没有组，所以只能新建一组放在末尾 —— 末尾是对的，因为
「供应链」这个判断应该是**所有具体职能都没命中之后**的兜底，不该抢在前面。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
下面每个数都标了**改规则前 / 后**。同一条命令在两个时点给不同的数，
因为分母里含着「当前代码判不出」这个条件，而这一轮改的正是当前代码。

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| 库里 `job_family IS NULL` 的 distinct 标题 **708** | `job_family IS NULL AND closed_at IS NULL` 的标题去重，**不剥城市**，不问代码判不出判得出 | —— | 会。这是「库里待处理」的总量，改代码不影响它，跑 sync 才会降 |
| 塌成 **502** 个岗位型 | 同上，剥掉尾部城市后去重 | —— | 会。`708 − 502 = 206` 就是「把城市写进标题」造成的重复，两个数并列是为了让这个差额看得见 |
| 判不出的岗位型：改前 **452** / 改后 **418** | 502 个岗位型里**当前代码判不出**的那些 | —— | 会。这一轮 −34 是 `顾问`/`采购` 判出来的岗位型数 |
| 判不出的 distinct 标题：改后 **420** | 708 条里当前代码判不出的 | —— | 会。和 418 只差 2，说明剩下的长尾几乎没有城市重复 —— 城市放大是 nio 一家的毛病 |
| `策略` 覆盖率：改前 **10.6%** / 改后 **11.5%** | 含 `策略` 的判不出岗位型 **48**（两个时点都是 48） | 判不出岗位型 452 → 418 | 会。**分子没动，分母小了**，所以这个百分比升高不代表 `策略` 变严重了 |
| `顾问` 救回 **233 行 / 21 个岗位型** | 加规则后 `job_family` 从 NULL 变有值的行 | —— | 已固化。规则已在表里，现在跑 `candidates` 显示救回 0（见 §9 A′） |
| `采购` 救回 **14 行 / 14 个岗位型** | 同上 | —— | 已固化，同上。行数=岗位型数是因为采购岗没有多城市重复 |
| 改判 **0 行** | 加规则后 `job_family` 从一个非空值变成另一个的行 | —— | 会，且**会被别的规则改动影响** —— `服务` 的改判数就因为 `采购` 这条新规则从 28 变成 29 |
| 待刷新 **331 行 / 288 条标题** → 刷完是 **0** | 库里 `job_family IS NULL` 但当前代码判得出的 | —— | 会。含方案 015 遗留的 `tech 50`，不全是 017 的。**2026-08-13 已刷完，见 §9 命令 I** |

**「救回 233 行」和「救回 21 个岗位型」是同一件事的两个口径，不许只报一个**：
只报行数会让这条规则看着像顶了 34.2% 的大头（那是原 issue 的错），
只报岗位型会让它看着像只值 21 个（对用户来说 233 行是 233 个列表项）。
决策看岗位型，工作量看行数。

### 8. 这次明确不做什么

- **不新开 `service` 族。** 对这份画像（`operations`/`product`），`sales` 和
  `service` 判出来的结果逐条相同（都走 `fam not in fams` → miss），
  现在定它等于编一个不可区分的差别。等画像里真出现服务类目标族再说。
- **不为 `AI时尚顾问实习生-广告业务` 加例外。** 1 行的收益配不上一条例外规则的
  长期成本 —— 例外规则是下一个 issue #9 的原料。写进 §3 的已知误判栏。
- **不加 `策略`/`分析`/`管理`/`方向`/`大区`/`研究` 等曲线头部词。**
  它们覆盖率高但不定职能（`策略产品`是产品、`策略运营`是运营、`广告策略`是技术），
  加了必然造成大批改判。曲线按覆盖率排，排不出这个区别。
- **不改 `_stem_map()` 去处理「城市写在标题中段」的情况。** 现在只剥尾段，
  实测 0 条不一致，够用；剥中段会把不同岗位并成一个，代价方向是**看不见的**。
- **不刷新存量库以外的东西。** 这次不动 `match.py`、不动 digest 的分组逻辑。

注意 `stale` 打出的族分布 `{'tech': 50, 'sales': 225, 'other': 13}` 是**按 distinct

**同一个函数里两个口径并排打出来，最容易被当成同一个口径读。**

### 12. 实现中踩到的坑

- **现象**：issue #8 的头部是「顾问 225 条、34.2%」，一个大桶加一条平尾，
  看起来只要把这一个词归族就能吃掉三分之一的缺口。
  **原因**：口径失效。「按 distinct 标题计」这条规则本来就是为了让「一个标题开在
  N 个城市」不算 N 个问题，但 nio 把城市写进了标题本身（`校招实习-蔚来顾问-<城市>`
  116 个城市、`乐道顾问` 90 个），去重挡不住 —— 206 条 distinct 标题其实是
  **1 个词表缺口**。
  **修法**：`_stem_map()` 剥掉标题尾部的城市名，改按岗位型计。708 → 502。
  重算之后头部是 `策略 10.6%`，`顾问` 掉到第 5（4.6%），**曲线是真平的**，
  没有大桶可打 —— 结论从「先归顾问」变成「加词治不了这个长尾」。
  **钉住它的测试**：`vocab_curve()` 里的 `disagree` 自证（同一 stem 下所有标题的
  family 结论必须一致，不一致说明城市剥过头了，直接拒绝出数）；
  `city-collapse` 子命令把放大倍数榜单打出来，这个假象下次会自己现形。

- **现象**：`candidates` 第一版报 `服务 → sales` 会改判 **500 行**，
  这个数大到不合理，但它和「顾问改判 0」是同一个函数算出来的。
  **原因**：那版用「标题含这个词且当前已能判出」当改判的代理。第 2 层是先命中的赢，
  所以真实代价取决于**插到哪个位置**，代理算法看不出位置，把「所有含这个词的
  已决行」全算成了改判。
  **修法**：`_judge_with()` 真的把词插进 `list(n.TITLE_RULES)` 的副本再跑一遍，
  两个位置各算一次。真数是 28（进 sales 组）/ 0（加末尾）。
  **钉住它的测试**：`TestInsertPositionMatters` 三条 —— 两条钉方向
  （进组抢走 tech、末尾不抢），第三条钉「`at_end` 参数真的接线了」：
  两个取值必须至少在一条标题上给出不同结论，否则那两行数永远相同，
  看着像验了两种情况而其实只验了一种。

- **现象**：`服务 → sales` 救 59 行，比 `采购` 的 14 行划算得多，数据上该先加它。
  **原因**：覆盖率和正确性是两件事。`服务` 在真标题里绝大多数不指「干什么活」——
  `抖音生活服务` 是业务线名、`服务工程` 是技术岗、`服务大区管理` 是管理岗。
  它是**域词**，正是 issue #9 那个病根的形状。
  **修法**：明确不加，并把这个「决定不做的事」写成测试。
  **钉住它的测试**：`TestServiceIsDeliberatelyNotSales` —— 5 条正向
  （`服务` 不许抢走 tech/design/marketing 的真职能）、1 条反向
  （只有 `服务` 时判 None，不许兜底成 sales），外加
  `test_service_is_in_no_word_list` 从结构侧断言 `服务` 不在任何组里。
  **单靠行为测试挡不住**：下一个人只要同时改期望值就绿了，结构断言才拦得住。

- **现象**：`采购` 归 other 之后，「放在哪一层」看着无所谓 —— 反正它判 other。
  **原因**：位置就是语义。放进 `COMPOUND_RULES`（第 2 层之前）会改判 5 条：
  `AI产品经理（采购方向）` product→other、`采购政策与合规` finance→other、
  `硬件采购实习生` tech→other —— 因为 `采购方向` 里 `采购` 又是域词。
  「供应链」这个族的语义是**所有具体职能都没命中之后的兜底**，
  这件事只能由「在表末尾」表达，注释里写一百字都不算数。
  **修法**：留在 `TITLE_RULES` 末尾，改判 0。
  **钉住它的测试**：`test_other_group_is_last_in_layer_two` 断言
  `TITLE_RULES[-1][1] == "other"` 且 other 组只有一个。行为测试挡不住「往前挪一格」——
  挪到 tech 之后、marketing 之前，那 4 条行为用例全绿。

- **现象**：§0 里「`采购` 救 17 行」这一行标着**已核实**，但回填时按它给的命令
  重新数，怎么数都是 14。
  **原因**：17 和 14 都是真数，数的不是一批东西 —— 17 = 在架且规则判 other 的行，
  14 = 其中**库里现在还是 NULL** 的行。差的 3 行早就被别的规则判成 other 了，
  算成这条规则的功劳是把别人的成绩记在自己账上。
  **一条规则的价值 = 它把多少行从 NULL 变成有值**，不是「多少行最终是这个族」。
  **修法**：§3 加了一段拆解（23 → 17 → 14 三层各是什么），§0/§7/§9 和
  `tests/test_normalize.py:343` 的数一起改。
  **为什么没早发现**：`顾问` 那边两个口径**恰好都是 233** —— 含顾问的 235 行里
  另外 2 行是 marketing，没有一行「已经是 sales」。同一个口径错误在它身上不显形，
  于是「233 对得上」被当成了「口径是对的」。
  **一个数在一处对得上，不代表口径是对的**；两个口径撞出同一个数，
  恰恰是最难发现的那种巧合（和「[两列数字恰好相同](#)」是同一个形状）。

- **现象**：`candidates` 的表头打出「在架 distinct 标题 6513，岗位型 502」，
  两个数并排像是同一批东西的两种口径。另一处对 `other` 打出「加进 other 组」，
  而当时第 2 层根本没有 other 组。
  **原因**：两处都是标签错，不是数错。`6513` 是在架全部标题（改判要在这批上找），
  `502` 只是**判不出的那批**塌成的岗位型 —— 分母不同的两个数放在一行，
  读的人会去算它们的比值。
  **修法**：表头改成「在架 distinct 标题 N；**其中判不出的**塌成 M 个岗位型」，
  位置标签改成 `f"{fam} 在第 2 层没有组，只能加在末尾"`，由 `has_group` 实时判。
  **这类错没有测试能兜**：数是对的，测试断言的也是数。只能靠「打印出来自己读一遍，
  凡是并排的两个数都问一句分母是不是同一个」。上一次踩的是
  [两列数字恰好相同](#) 那个形状，这次是反过来 —— 两个数不该比而被并排了。

- **现象**：验 `mutate_017.sh` 自己的闸门时，故意把 `-k` 写成
  `TestAdvisorIsSalesRENAMED`（匹配 0 条测试），脚本报的是
  `✗ **没红** —— 这条判据没有测试守着`。**报警对了，诊断反了。**
  **原因**：第一版按 pytest 的 `no tests ran` 字样认「一条都没跑」。
  实际 `-k` 匹配 0 条时末行是 `768 deselected in 0.48s` —— 既没有 `no tests ran`
  也没有 `0 selected`，于是掉进了下面那个通用的「没红」分支。
  同一个 ✗ 指向两个相反的结论：一个是「测试改名了，这条等于没验」，
  一个是「判据真的没人守」。
  **修法**：反过来判 —— 末行里 `passed`/`failed`/`error` 一个都没有，
  就说明一条测试都没跑，先报这个，再问红没红。判据顺序有讲究：
  **先问「跑了吗」，再问「红了吗」。**
  **钉住它的测试**：这条闸门自己被验过能红（改名 → `✗ -k 一条测试都没匹配上`，
  退出码 1），另一条「改坏没落到文件上」的闸门也用同样办法验过
  （perl 表达式瞄一个文件里不存在的串 → `✗ 改坏没落上`，退出码 1）。
  **改坏脚本本身也是判据，也要被改坏一次。**

### 13. 如果重来，方案里该提前写上哪句话

- **「代价必须真跑一遍规则表，不许用代理指标。」**
  这一条如果提前写上，`服务` 那个 500 就不会出现。凡是判据里有「先命中的赢」，
  代价就依赖位置，而任何「含不含这个词」的近似都看不见位置。

- **「去重之前先问：这个源会不会把维度写进被去重的那个字段里。」**
  按 distinct 标题去重是为了消掉城市维度，而 nio 把城市塞进了标题。
  口径没坏，是**数据形状让口径失效了** —— 这种失效不报错，只是给出一个
  更像结论的数字。凡是「按 X 去重来消掉 Y」的口径，都得先验一遍 Y 不在 X 里面。

- **「一个数报出去之前，问它的分母是什么；两个数并排之前，问分母是不是同一个。」**
  这次两处标签错都是这么来的。数是对的，测试也断言不出问题，
  只有读的人会去算那个不该算的比值。`stale` 的族分布也是同一个坑：
  它按标题数（288），紧挨着的上一行按行数（331），中间没有一句话说这事。

- **「『已核实』的那条命令，回填的时候要真的再跑一遍。」**
  `采购 17` 那行当时是标着已核实的 —— 命令能跑、输出有那个数、结论看着成立。
  错的是**我数的东西和我想数的东西不是一回事**，这种错在写的那一刻查不出来，
  只有隔一段时间按自己留的命令重跑才会撞上。§0 要求附命令的价值不在写的时候，
  在**回填的时候能拿它当反证**。

- **「方案里提到的每个测试名，都要 `--collect-only -k` 跑一遍。」**
  §10 里我编了两个不存在的测试名（`test_service_is_not_sales`、
  `test_stem_collapse_preserves_family`）。写的时候它们是「打算写的测试」，
  写完忘了对齐。下一个人按名字搜不到，会以为测试被删过。
  顺带：验这件事的脚本第一版也写错了 —— 拿 `tests collected` 当命中判据，
  而 pytest 打的是 `no tests collected`，**子串把「没有」读成了「有」**。

- **「改坏脚本的每道闸门，也要被改坏一次。」**
  `-k` 匹配 0 条那道闸门写错了，而它的症状和「判据没测试守着」长得一模一样。
  验证手段自己没被验证，是这类 bug 唯一的存活条件 —— 002 那轮的
  `--dry-run` 写库泄漏是同一个形状。

- **「刷存量之前先跑试运行，并且把『变更 N 行』拆到能归因为止。」**
  字节报 `变更 7276`，看着像这一轮要动 7276 行，实际本轮只让 331 行的
  `job_family` 从 NULL 变有值，7096 行是上一个任务（#32 改列不碰指纹）留下的
  自愈账。**一个大数字不解释清楚就动手，等于放弃了「出事之后能分清是谁干的」这件事。**
  拆法不是猜成因，是找一个不受影响的对照组：`tencent_join` 809 行指纹全自洽，
  因为 `repair_apply_url` 没扫它 —— 有它才能把「真全坏」和「我系统性算错」分开。

- **「『跑一轮就自愈』要问清楚：自愈的前提是什么？」**
  指纹不同步从 8594 掉到 155 而不是 0，剩下的全是本轮下线的岗位。自愈的机制是
  「重新抓到 → 重算指纹」，那么**抓不到的就永远不愈**。写「跑一轮 sync 就会自愈」
  的时候我没写这个前提，于是刷完之后多出一个非 0 的数要临时解释。
  **凡是说「会自愈」，同时得说清哪一类不会。**

- **「另一份方案里量过的数，在本方案里要留一句指路。」**
  8594 / `/detail` 这件事 016 §7 已经量得很干净，可是做 017 的人先看见的是
  「变更 7276」，而解释它的那句话在另一份文件里。跨方案的因果，得在**看见症状的
  那一份**里写明去哪查。

- **「决定不做的事，也要有测试。」**
  `服务` 不加进 sales 是这轮最重要的判断之一，而它在代码里的痕迹本来只有一条注释。
  注释拦不住下一个看着 59 > 14 就动手的人。
