## 一、产品设计

### 1. 为什么现在做

不做的后果不是「文档旧了」，是**文档会被当成判据用**。

三件已经发生的事：

1. **SPEC 自称「必须与代码一致」**（页首第一行），而它不知道 `health.py` /
   `mcp_server.py` / `queries.py` 存在，§2 的模块表停在 M7，CLI 清单少 3 条。
   一份宣称与代码一致的文档说错话，比一份没人信的文档危险 ——
   §9 的验收命令就是从这里抄出去跑的。
2. **CLI 清单已经漏过两次**，SPEC 自己在 §2 记着这件事（`refresh-grad-year` 从 007 起、
   `repair-apply-url` 从 010 起），并且写了核对办法。**这是第三次**，
   而且这次漏的 `health` / `checkup` 是两条**只读巡检**命令 ——
   它们存在的理由就是「判据静默失效时有人喊」，而它们本身在文档里是隐形的。
3. **用例数在三个文件里各写了一份**，`CLAUDE.md` 明文禁止这件事
   （「用例数不写死在这里……改漏了就变成一个假的回归信号」），
   但那条规则只管住了 `CLAUDE.md` 自己。README / SPEC / CHANGELOG 各写各的，
   已经出现过 464 与 504 在同一个 commit 上对打。

第 3 条决定了这次的做法：**不是把 464 改成 847**，那样三个月后又是同一局。
是把用例数收成**一个**出处（README 现状那一节，数字和产生它的命令放在一起），
其余地方改成「跑那条命令」或写成历史快照并标注日期。

### 2. 用户会看到什么

```
新来的人（或三个月后的我）想知道「这个项目现在有哪些命令」
  → 打开 docs/SPEC.md §2
  → 现在：9 条清单，跑 `cli health` 报 "No such command"…… 不，反过来 ——
          命令能跑，但文档里没有，于是他不知道有这个东西
  → 改完：12 条，且每条标着落地的方案编号；MCP 只读层单列一节

想知道「测试有多少条」
  → 现在：README 说 504、SPEC 说 464、CHANGELOG 说 504，实际 847
  → 改完：只有 README 现状那一节有数字，旁边就是产生它的命令；
          SPEC/CHANGELOG 不再写当前数（历史快照保留并标日期）
```

## 二、具体实现

### 4. 数据长什么样，空值怎么办

这次改的是文档，没有运行时字段。但有一个「取不到值」要处理：

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| 文档里的用例数 | 一个整数 + 产生它的命令 + 日期 | **不写**（改成「跑这条命令看最后一行」） | 是。这是关键：写一个**没有日期的数**等于宣称「现在就是这个数」，而它只会在写下的那一刻为真。历史快照必须带日期才能和「当前值」区分开 |
| SPEC 变更记录的「基线」列 | 历史快照，带日期 | 保留旧值不动 | 是。旧行是历史，不是当前值 —— 这一栏本来就该是快照，问题只在页首那个「当前基线」 |

### 5. 硬约束在哪一行

**全是软约束。** 文档改错的后果是有人读到旧话，不是不可撤销的动作。

但有一条可以做成半硬的：CLI 清单漏过三次，说明「记得回来改」这个软约束在这一处
已经证明失效。§10 加一条测试，拿 `cli --help` 的实际命令集和 SPEC 里那张清单对，
少一条就红。这是把「文档承诺」变成可查的 —— 同 019 的做法
（见 `019` §10 的 `test_docstring_does_not_promise_everything`）。

**不给用例数加这种测试。** 那等于把「写死的数字」再钉一遍，方向反了：
正确的做法是让它在文档里只出现一次，且旁边有命令。

### 6. 判据的粒度

这次要「认出文档和代码对不上」，判据是**清单级**，不是字符串级。

- **清单级**（这次用的）：从 `cli --help` 解析出命令名集合，和 SPEC 里的清单比集合。
  差一个就红，且红的时候能说出差哪一个。
- 差一级会命中什么：**字符串级**（比如 `assert "health" in spec_text`）
  会被正文里任何一处提到 `health` 的地方满足 —— 包括「§6 异常处理」里
  顺口提一句的场景。它证明的是「这个词出现过」，不是「清单里有这一条」。
  这正是 015 那类坑的形状（域词抢走职能词：词出现 ≠ 判定成立）。

解析 `--help` 输出用的是「取 `│ 命令名  描述` 这一列的第一个 token」。
这个判据依赖 Typer 的输出格式，格式变了它会**数出 0 个** ——
所以要按 019 学到的那条补一句：数出 0 个必须红
（见 [[an-empty-anchor-is-falsely-green]] 那一类）。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| 847 | `pytest -q` 最后一行的 passed 数，**数的是用例（函数级，含参数化展开）** | 无 | **会，每次加测试就动**。所以它只写在 README 现状一节 + 日期 + 命令 |
| 22 | 测试**文件**数 | 无 | 会 |
| 12 | `cli --help` 里的命令数 | 无 | 会，但很慢 |
| 133 | `test_normalize.py` 一个文件的用例数 | 无 | 会。README 的表里**不再逐文件写数** |
| 504（历史） | 发布 commit `9d6ffb1` 上的收集数 | 无 | 不会 —— 它钉在一个 commit 上 |
| 464（历史） | 012 落地时的数 | 无 | 不会，但它**被当成了当前值**写在 SPEC 页首，这是这次要修的 |

口径提醒三条：

1. **847 和 22 不同维度**（用例 vs 文件），别放一起比。README 的表以前把
   「文件」和「用例数」并排列，加起来要等于总数 —— 一旦漏文件就静默对不上
   （现在漏了 6 个）。
2. **`--collect-only` 数的是收集到的用例，`-q` 数的是跑过并通过的**。
   有 skip / xfail 时两个数不等。这次全绿所以相等，但写的时候要说清是哪个命令。
3. **「测试 41 → 504」这种区间写法是对的**，因为它带了两个端点和一个版本范围。
   页首「测试基线 → 464 passed」是错的，因为它不带日期就宣称当前值。

### 8. 这次明确不做什么

- **不把 847 写进 SPEC / CHANGELOG / WIKI。** 那是这次要拆掉的东西本身。
- **不逐文件写用例数**（README 那张表）。22 个文件各一个数，等于 22 个会过期的事实
  和 1 个必须手算的加总。表保留，但列改成「这个文件覆盖什么」。
- **不动 `docs/ATS_RESEARCH.md` / `kb/`。** 前者是调研记录（本来就不承诺跟代码一致），
  后者有自己的版本机制和 `test_kb_index.py` 守着。
- **不删 `M6_COMPLETE.md` / `QUICK_REF.md` / `_VERIFICATION_CHECKLIST.md`。**
  它们确实过期，但删文件和收敛口径是两件事，混在一个 diff 里说不清在修什么。
  这次只在 README 里标一句它们是历史文档。
- **不给 013–019 补 WIKI 变动表的逐条细节。** WIKI 那张表每行都是当时的现场记录
  （带着「顺带发现了什么」），事后补写等于**编造现场** ——
  我现在写出来的是复盘视角，不是那天的视角。改成补一行说明「013 起改用方案 §0 记录进度，
  这张表不再逐轮追」，把指针指向 `docs/plans/`。这是这次唯一「明确不补」的漂移。
- **不发新版本号。** 013–019 该落成 0.3.0，但版本号意味着一次发布动作
  （打 tag、CHANGELOG 定稿），而当前 7 个分支都没合进 `main`。
  版本落点等合并时再定，这次只在 CHANGELOG 里开一个 `[未发布]` 段。
