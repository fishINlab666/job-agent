## 一、产品设计

### 1. 为什么现在做

不做的后果不是「文档旧了」，是**文档会被当成判据用**。

三件已经发生的事：

1. **SPEC 自称「必须与代码一致」**（页首第一行），而它不知道 `health.py` /
   `mcp_server.py` / `queries.py` 存在，§2 的模块表停在 M7，CLI 清单少 3 条。
   一份宣称与代码一致的文档说错话，比一份没人信的文档危险 ——
   §9 的验收命令就是从这里抄出去跑的。
2. **CLI 清单已经漏过两次**，SPEC 自己在 §2 记着这件事（`refresh-grad-year` 从 007 起、
   `repair-apply-url` 从 010 起），并且写了核对办法。**这是第三次**，
   而且这次漏的 `health` / `checkup` 是两条**只读巡检**命令 ——
   它们存在的理由就是「判据静默失效时有人喊」，而它们本身在文档里是隐形的。
3. **用例数在三个文件里各写了一份**，`CLAUDE.md` 明文禁止这件事
   （「用例数不写死在这里……改漏了就变成一个假的回归信号」），
   但那条规则只管住了 `CLAUDE.md` 自己。README / SPEC / CHANGELOG 各写各的，
   已经出现过 464 与 504 在同一个 commit 上对打。

第 3 条决定了这次的做法：**不是把 464 改成 847**，那样三个月后又是同一局。
是把用例数收成**一个**出处（README 现状那一节，数字和产生它的命令放在一起），
其余地方改成「跑那条命令」或写成历史快照并标注日期。

### 2. 用户会看到什么

```
新来的人（或三个月后的我）想知道「这个项目现在有哪些命令」
  → 打开 docs/SPEC.md §2
  → 现在：9 条清单，跑 `cli health` 报 "No such command"…… 不，反过来 ——
          命令能跑，但文档里没有，于是他不知道有这个东西
  → 改完：12 条，且每条标着落地的方案编号；MCP 只读层单列一节

想知道「测试有多少条」
  → 现在：README 说 504、SPEC 说 464、CHANGELOG 说 504，实际 847
  → 改完：只有 README 现状那一节有数字，旁边就是产生它的命令；
          SPEC/CHANGELOG 不再写当前数（历史快照保留并标日期）
```

## 二、具体实现

### 4. 数据长什么样，空值怎么办

这次改的是文档，没有运行时字段。但有一个「取不到值」要处理：

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| 文档里的用例数 | 一个整数 + 产生它的命令 + 日期 | **不写**（改成「跑这条命令看最后一行」） | 是。这是关键：写一个**没有日期的数**等于宣称「现在就是这个数」，而它只会在写下的那一刻为真。历史快照必须带日期才能和「当前值」区分开 |
| SPEC 变更记录的「基线」列 | 历史快照，带日期 | 保留旧值不动 | 是。旧行是历史，不是当前值 —— 这一栏本来就该是快照，问题只在页首那个「当前基线」 |

### 5. 硬约束在哪一行

**全是软约束。** 文档改错的后果是有人读到旧话，不是不可撤销的动作。

但有一条可以做成半硬的：CLI 清单漏过三次，说明「记得回来改」这个软约束在这一处
已经证明失效。§10 加一条测试，拿 `cli --help` 的实际命令集和 SPEC 里那张清单对，
少一条就红。这是把「文档承诺」变成可查的 —— 同 019 的做法
（见 `019` §10 的 `test_docstring_does_not_promise_everything`）。

**不给用例数加这种测试。** 那等于把「写死的数字」再钉一遍，方向反了：
正确的做法是让它在文档里只出现一次，且旁边有命令。

### 6. 判据的粒度

这次要「认出文档和代码对不上」，判据是**清单级**，不是字符串级。

- **清单级**（这次用的）：从 `cli --help` 解析出命令名集合，和 SPEC 里的清单比集合。
  差一个就红，且红的时候能说出差哪一个。
- 差一级会命中什么：**字符串级**（比如 `assert "health" in spec_text`）
  会被正文里任何一处提到 `health` 的地方满足 —— 包括「§6 异常处理」里
  顺口提一句的场景。它证明的是「这个词出现过」，不是「清单里有这一条」。
  这正是 015 那类坑的形状（域词抢走职能词：词出现 ≠ 判定成立）。

解析 `--help` 输出用的是「取 `│ 命令名  描述` 这一列的第一个 token」。
这个判据依赖 Typer 的输出格式，格式变了它会**数出 0 个** ——
所以要按 019 学到的那条补一句：数出 0 个必须红
（见 [[an-empty-anchor-is-falsely-green]] 那一类）。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| 847 | `pytest -q` 最后一行的 passed 数，**数的是用例（函数级，含参数化展开）** | 无 | **会，每次加测试就动**。所以它只写在 README 现状一节 + 日期 + 命令 |
| 22 | 测试**文件**数 | 无 | 会 |
| 12 | `cli --help` 里的命令数 | 无 | 会，但很慢 |
| 133 | `test_normalize.py` 一个文件的用例数 | 无 | 会。README 的表里**不再逐文件写数** |
| 504（历史） | 发布 commit `9d6ffb1` 上的收集数 | 无 | 不会 —— 它钉在一个 commit 上 |
| 464（历史） | 012 落地时的数 | 无 | 不会，但它**被当成了当前值**写在 SPEC 页首，这是这次要修的 |

口径提醒三条：

1. **847 和 22 不同维度**（用例 vs 文件），别放一起比。README 的表以前把
   「文件」和「用例数」并排列，加起来要等于总数 —— 一旦漏文件就静默对不上
   （现在漏了 6 个）。
2. **`--collect-only` 数的是收集到的用例，`-q` 数的是跑过并通过的**。
   有 skip / xfail 时两个数不等。这次全绿所以相等，但写的时候要说清是哪个命令。
3. **「测试 41 → 504」这种区间写法是对的**，因为它带了两个端点和一个版本范围。
   页首「测试基线 → 464 passed」是错的，因为它不带日期就宣称当前值。

### 8. 这次明确不做什么

- **不把当前用例数写进 SPEC / CHANGELOG / WIKI。** 那是这次要拆掉的东西本身。
  （落地过程里 README 那个数我写了三遍：853 → 854 → 856 —— 每次是我自己又加了
  一条判据。三次都由 `test_readme_count_is_actually_true` 报出来，没有一次靠我记得。）
- **不逐文件写用例数**（README 那张表）。23 个文件各一个数，等于 23 个会过期的事实
  和 1 个必须手算的加总。表保留、补全到一个文件一行，但列改成「这个文件覆盖什么」，
  并给「有没有文件不在表里」加判据 —— 老表烂掉不是因为数字错，是因为它靠一个
  「其余 N 个文件」的桶兜着，新文件进不进表都看不出来。
- **不动 `docs/ATS_RESEARCH.md` / `kb/`。** 前者是调研记录（本来就不承诺跟代码一致），
  后者有自己的版本机制和 `test_kb_index.py` 守着。
- **不删 `M6_COMPLETE.md` / `QUICK_REF.md` / `_VERIFICATION_CHECKLIST.md`。**
  它们确实过期，但删文件和收敛口径是两件事，混在一个 diff 里说不清在修什么。
  这次只在 README 里标一句它们是历史文档。
- **不给 013–019 补 WIKI 变动表的逐条细节。** WIKI 那张表每行都是当时的现场记录
  （带着「顺带发现了什么」），事后补写等于**编造现场** ——
  我现在写出来的是复盘视角，不是那天的视角。改成补一行说明「013 起改用方案 §0 记录进度，
  这张表不再逐轮追」，把指针指向 `docs/plans/`。这是这次唯一「明确不补」的漂移。
- **不发新版本号。** 013–019 该落成 0.3.0，但版本号意味着一次发布动作
  （打 tag、CHANGELOG 定稿），而当前 7 个分支都没合进 `main`。
  版本落点等合并时再定，这次只在 CHANGELOG 里开一个 `[未发布]` 段。

### 10. 测试钉的是哪几条

`tests/test_docs_match_code.py`，**9 条**（跑 `uv run pytest tests/test_docs_match_code.py -q`）。
下表最后一列写的是「哪个做一半的动作会让它红」。

| 结论 | 测试 | 做一半会红的那条 |
|---|---|---|
| SPEC 的 CLI 清单 = `cli --help` 的实际命令集 | `test_spec_cli_list_matches_help` | 就是它。加了新命令没回来改 SPEC 时红（这已经发生三次）|
| 解析 `--help` 真的解析到了东西 | `test_help_parser_finds_commands` | 解析器因 Typer 换版本数出 0 个时红 —— 否则「空集 == 空集」全绿 |
| SPEC 提到 `jobagent/*.py` 每一个模块 | `test_spec_mentions_every_module` | 新增模块没进 SPEC 时红 |
| 豁免只给真没内容的模块 | `test_exemptions_are_only_for_empty_modules` | 拿 `NOT_REQUIRED` 绕开上一条时红 |
| SPEC 页首和 §9 都不钉当前用例数 | `test_no_pinned_current_count[docs/SPEC.md]` | 只改了清单没拆用例数时红 |
| README 的数带着产生它的命令和日期 | `test_readme_count_travels_with_its_command` | 把数搬过来但没搬命令时红 |
| README 的数**等于真实收集数** | `test_readme_count_is_actually_true` | 加了测试没回来改 README 时红 |
| README 分文件表覆盖 `tests/test_*.py` 全部文件 | `test_every_test_file_is_in_the_table` | 加了测试**文件**没进表时红（这正是烂掉的那次，8 个文件）|
| 表里没有已经不存在的文件 | `test_table_has_no_file_that_does_not_exist` | 删/改名测试文件没改表时红 |

最后一条是这次的关键，也是原方案没写的：前面那条只管**格式**。
504 当年格式是合规的 —— 有日期、附近有 `pytest -xvs` —— 它烂在没人核对内容。
一个只查形状的守卫会一直绿着看它烂掉。代价是自觉的：加一条测试就得改一次 README，
这正是「唯一出处」的意思，要么这个数是真的，要么套件红，没有第三种状态。

锚点一律取**代码侧**：`cli --help` 的输出、`ls jobagent/*.py`、`--collect-only` 的收集数。
拿文档里的表当锚点只查得出「表里有不存在的东西」，查不出「东西没进表」，
而这几次漂移全是后者（3 个模块 SPEC 完全不知道，CLI 漏三次）。同 019 那条锚点选择。

### 10b. 逐条改坏（`scripts/mutate_020.py`，17 条）

只验绿等于没验，所以 9 条判据逐条改坏跑一遍：`uv run python scripts/mutate_020.py`
→ **17 条改坏全部按预期变红，对照组全部保持绿**。

每条改坏都配一个**该保持绿**的对照组并断言（只打印不算）：对照组红了有两个意思 ——
改坏的波及面超出了判据，或者对照组挑错了，两者输出一样。同时断言 `-k` 匹配到的条数
不是 0，因为 `-k` 是子串选择器，名字写错会静默匹配 0 条，而 0 条在 pytest 里长得像
「没失败」。

被改坏的不只是文档，也包括**守卫自己**：把 `--help` 解析器的命令区识别弄坏（改坏 4）、
把 `--collect-only` 锚点弄坏（改坏 13）、拿 `NOT_REQUIRED` 绕开判据（改坏 6）。
探针的缺陷长得像被探对象坏了，所以探针也得挨改坏。

### 12. 实现中踩到的坑

- **现象**：守卫报 SPEC 里钉着 `464`，而我明明已经把基线数拆掉了。
  **原因**：我在**解释**这件事的时候引用了旧值（「这里原先钉着一个数（`464 passed`）」），
  而守卫分不清「历史引用」和「当前声明」—— 它只看见一个数。同一个坑犯了两次：
  先在页首，修好后又在 §9 复现。
  **修法**：历史一律搬去文末变更记录（守卫不看那里），被守的段落里不复述旧数字，
  并在正文里写清为什么不复述。
  **钉住它的测试**：`test_no_pinned_current_count` + 改坏 7、8。

- **现象**：改坏「拿掉 README 用例数旁边的日期」，判据**照样绿**。
  **原因**：判据用 600 字窗口找日期，被正文里另一处引用 SPEC 的 `2026-08-13` 喂饱了。
  窗口越宽，判据越容易被无关内容满足 —— 而宽窗口是我为了「宽容一点别虚警」故意选的。
  **修法**：改成「日期必须紧跟这个数、同一行 30 字内」。
  **钉住它的测试**：改坏 9 + 改坏 14（跨段挪日期：窗口里仍有日期但不属于这个数）。

- **现象**：改坏「把 `mcp_server.py` 加进 `NOT_REQUIRED`、理由写『懒得写』」，照样绿。
  **原因**：豁免口没有任何判据看着它。而它被滥用的时刻恰好是「新模块没进文档」的时刻，
  也就是那条判据唯一有用的时候。白名单本身是对的（漏的方向看得见），
  但**白名单的准入条件**当时是一句自由文本。
  **修法**：豁免依据换成文件自己的属性 —— 没有任何 `def`/`class`。理由字符串不算理由。
  **钉住它的测试**：`test_exemptions_are_only_for_empty_modules` + 改坏 6。

- **现象**：改坏 1 抛「原文还在（替换没生效）」。
  **原因**：`` `checkup` / `health`。 `` 在 SPEC 里有 **2 处**（变更记录那行也这么结尾），
  `replace(..., 1)` 只换第一处。落点有歧义时我根本不知道改坏落在哪一处 ——
  这是「歧义定位上取 `.first`」，只不过发生在改坏脚本自己身上。
  **修法**：`Mutation` 加 `count` 字段，默认 **1 = 必须唯一**，命中数不等于 1 直接算失败；
  真要全换的（改坏 5：判据要求 `queries` 一次都不出现）显式写 `count="all"`。
  **钉住它的测试**：脚本自己的落点断言。

- **现象**：改坏 5「抹掉 `queries`」不咬。
  **原因**：SPEC 里 `queries` 出现 3 次，只换 1 处它还在，判据当然不红。
  **改坏不生效**和**判据失守**长得一模一样。
  **修法**：同上，`count="all"`。

- **现象**：改坏 8 落点没找到。
  **原因**：我按记忆写了标题 `# 校招 Agent 需求规格`，实际是 `# 方案文档：校招 Agent 当前实现`。
  **修法**：先 `sed -n '1,8p'` 打出真文本再写落点。脚本的 `hits == 0` 检查把它和
  「判据没守住」分开了 —— 没有这道检查，它会被记成一条假的「判据失效」。

- **现象**：改坏脚本第二次跑直接被自己的「工作树必须干净」挡住。
  **原因**：那正是它该做的 —— 残留改坏态会伪装成被测对象的缺陷，且伪装得合理。
  **修法**：先提交再跑。

- **现象**：改坏 14 第一版「该红的没红」。
  **原因**：这次是**我的改坏太软**，不是判据漏。日期挪到 15 字外仍在同一行 30 字内，
  按判据的定义那本来就算「跟着这个数」。
  **修法**：改坏改成跨段。记在这里是因为它和「判据失守」在输出上同形，

- **现象**：我在 §3 写「README 表漏 6 个文件」，去发布 commit 上一核，**整张表当天是对的** ——

### 13. 如果重来，方案里该提前写上哪句话

1. **「文档里的数只有两种活法：受守卫管，或者不写。」** 原方案想的是「把三处数字改对」，
   那只是把过期时间推后一次。真正的选择是「这个数有没有人核」—— 没有就删掉，
   有就让它红。README 分文件表那 23 个数字按这条规则一个都留不下来。

2. **「只查格式的守卫会一直绿着看它烂掉。」** 504 有日期、旁边有 `pytest` 命令、
   位置也对，它**全部合规**。判据要落在「这个数是真的吗」，而唯一能回答的方式是
   跑一次产生它的命令，比一次。

3. **「白名单是对的，但白名单的准入条件也要有判据。」** `NOT_REQUIRED` 挑白名单的
   理由（漏的方向看得见）站得住，但准入靠一句自由文本时，绕开它比修它便宜。
   准入条件要能从被豁免对象**自己的属性**算出来。

4. **「改坏落点必须唯一，不唯一就不是一次改坏。」** 落点命中 2 处时我不知道改动落在哪，
   而「成功地改错地方」不会报错。默认要求唯一、要全换的显式声明 —— 这条该写在
   改坏脚本的模板里，不是每次现踩。

5. **「该红的没红有两个成因，方向相反。」** 判据漏了要改判据；改坏太软要改改坏。
   输出一样，所以每次都得回去看改坏后的源码，确认它真的越过了判据的边界 ——
   改坏 14 就是后者，如果当时顺手去「修判据」，会把一条本来正确的判据改宽。

6. **「历史引用和当前声明，在字符串级判据眼里是同一个东西。」** 想在被守的段落里
   解释「这里以前写着 X」是做不到的。历史归历史区（变更记录），被守的段落只写现状。
   这条我在同一个文件里犯了两次。

7. **「拿今天的值对照文档里的值，差异不等于『文档写错了』。」** 还有一种成因是
   **时间**：它当天是对的，之后世界动了。两者修法相反 —— 前者改数字，后者说明
   那种写法本身留不住（README 那个「其余 N 个文件」的桶）。分辨办法只有一个：
   回到文档写下的那个 commit 上取真值。这次回去一看，整张表当天全对。

8. **「合计对上不代表每一列都对。」** 老表的用例数合计正好等于当时真实的 504，
   而错的是**文件数**那一列。一个维度对了会给另一个维度背书 ——
   所以交叉校验要写清「这一列数的是什么」，不能只看总数收口。
