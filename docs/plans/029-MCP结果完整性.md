## 一、产品设计

### 1. 为什么现在做

现有五个只读 MCP 工具已经能返回真实数据，但 `list_sync_runs` 和 `job_changes`
都接受 `limit`，返回值却只给数组。数组有 20 条时，调用方无法区分“总共正好 20 条”
和“这里只展示前 20 条”，容易把局部结果当成全部事实。

另一个已复现的边界是：事件时间损坏时，SQLite 的 `julianday()` 返回 `NULL`。
带 `since` 的查询会把这条记录静默过滤，最后回答“没有变化”，而真实情况是
“有一条记录无法判断是否在时间窗内”。这类假阴性比明确报错更危险。

### 2. 用户会看到什么

```text
用户查询最近 20 次采集或最近 50 条岗位变化
    → 系统返回本页条数
    → 同时明确告诉用户后面是否还有结果

用户按时间查询岗位变化，但库里有无法解析的事件时间
    → 系统明确报“事件时间损坏，无法可靠筛选”
    → 不再把坏数据伪装成“这段时间没有变化”
```

### 3. 已核实与假设

| 事实 | 怎么核实的 |
|---|---|
| `list_jobs` 已有 `total` / `returned`，另外两个限量工具只有数组 | `jobagent/mcp_server.py` 当前实现 |
| `list_sync_runs` 和 `job_changes` 的 SQL 都在查询层直接 `LIMIT` | `jobagent/queries.py::sync_runs` / `job_changes` |
| 损坏的 `occurred_at` 在带 `since` 查询中被静默排除 | 内存 SQLite 最小复现 |
| 生产库当前没有损坏的事件时间 | 对生产库执行只读 `COUNT` 检查 |

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|
| 多取一条足以判断“是否还有更多” | `truncated` 可能误报 | 分别覆盖少于、等于和多于 `limit` 的真实查询测试 |
| 增加返回字段不会破坏现有调用方 | 老客户端可能拒绝新字段 | 走真实 MCP 协议并运行完整测试；不删除或改名现有字段 |
| 查询层只在使用 `since` 时预检脏时间；公开 MCP 无 `since` 时仍须为全局排序拒绝脏时间 | 两层契约混写会让调用方误以为 MCP 能返回无法排序的行 | 查询层与真实 MCP 分别测试：查询层无 `since` 交出原行，MCP 有无 `since` 都明确失败 |
| 跨 kind 的多次读取需要共享快照 | 截断标记可能描述一个拼接出来的瞬时集合 | 在真实 MCP 调用中监测每次查询都处于同一只读事务 |

## 二、具体实现

### 4. 数据形状与空值

| 字段 | 有值时 | 取不到时 | 空值与不匹配是否分开 |
|---|---|---|---|
| `runs` / `events` | 最多 `limit` 条 | 没有记录时为 `[]` | 是 |
| `returned` | 本次实际返回的数组长度 | 没有记录时为 `0` | 是 |
| `truncated` | `True` = 至少还有一条没返回 | `False` = 已证明没有更多 | 是；不是“未知” |
| `occurred_at` | SQLite/Python 可解析的时间 | 缺失或无法解析 | 是；查询层带 `since` 时拒绝静默过滤；公开 MCP 有无 `since` 都须拒绝无法全局排序的坏行 |

`truncated` 只回答“还有没有”，不承诺精确总数。实现使用 `limit + 1` 读取，
把多出的探针行丢掉；不增加第二次全表计数。

### 5. 硬约束

- 注册表仍精确为五个只读工具，不新增第六工具。
- SQLite 连接继续使用 `mode=ro`；不写生产库、不迁移历史数据。
- `job_changes` 继续只返回采集侧白名单事件，代投侧事件仍不能过边界。
- 脏时间只允许明确失败，不能回退成空数组或跳过坏行。查询层无 `since` 时可把
  原始脏行交给其他非排序调用方；MCP 必须全局排序，因此有无 `since` 都失败。
- `job_changes` 跨 kind 的读取必须在同一个只读事务快照内完成。

### 6. 判据粒度

- “被截断”按**当前筛选条件下至少存在第 `limit + 1` 条记录**判断。
- `job_changes(kind=None)` 按全部允许的采集侧种类合并后判断，不是每个种类各报一次。
- 脏时间按**本次查询会覆盖的事件种类**检查；指定 `kind` 时，其他种类的坏行不阻断。

### 7. 数字口径

| 数字 | 分子/含义 | 分母 | 会不会变 |
|---|---|---|---|
| `returned` | 当前响应实际包含的记录数 | 无 | 随数据和 `limit` 变化 |
| `truncated` | 布尔值；是否存在未返回的下一条 | 当前筛选结果全集 | 新数据写入后可能变化 |

本次不返回 `total`：精确总数需要额外查询，而且在并发采集时可能和数组来自不同快照。
用户现在需要的是“这是不是全部”，不是一个会快速过期的总数。

### 8. 明确不做

- 不做分页游标；目前没有用户证据证明需要翻到第 2 页，先避免扩大接口。
- 不新增查询工具；这是修正现有工具的输出契约。
- 不修改采集、通知、匹配、投递或三日观察逻辑。
- 不修复或重写生产数据；当前生产库脏时间数为 0。
- 不重新引入 Transaction Gate 或额外审批框架。

## 四、复盘（实现完成后回填）

### 11. 方案和实现差在哪

- 截断提示按方案使用 `limit + 1`，没有引入精确总数或分页游标。
- 脏时间检查为了避免“检查后、查询前”被并发插入坏行，查询层在自己尚未处于
  事务时先开启同一只读快照，检查和结果查询完成后回滚该只读事务；调用方已有事务
  时不接管也不回滚调用方事务。
- MCP 聚合多个事件种类时再在外层建立一个只读快照，保证整页事件和 `truncated`
  描述同一时点；查询层检测到调用方事务后会复用，不嵌套开启事务。
- 独立审查指出最初的事务测试只检查 `in_transaction=True`，不能证明九次读取是
  同一个事务。最终改成真实并发可见性用例：第一次调用中途由第二连接提交标记事件，
  当前页看不见、下一次调用可见。
- 独立审查还指出 Plan 把查询层和 MCP 的无 `since` 行为混成一句。最终明确：
  查询层无 `since` 可以交出原始坏行；MCP 必须排序，所以有无 `since` 都 fail-closed。
- 原定的 `tests/test_docs_match_code.py` 在当前主线不存在，相关验证改用真实存在的
  `tests/test_packaging.py` 加完整测试；没有为了让命令通过而新造一个空测试文件。

### 12. 实现中踩到的坑

- **现象**：相关测试命令在收集前报 `tests/test_docs_match_code.py` 不存在。
  **原因**：旧计划引用了当前主线没有的测试路径。
  **修法**：先用 `rg --files tests` 核实，再运行现存的打包测试和完整测试。
  **钉住它的测试**：`tests/test_packaging.py` 与全量 `tests cloud/collector/tests`。
- **现象**：只用 `julianday(occurred_at) >= ...` 时，坏时间行不会报错而是消失。
  **原因**：SQLite 对无法解析的时间返回 `NULL`，`WHERE NULL` 不成立。
  **修法**：同一数据库快照内先查相关 kind 的坏时间，发现即明确失败。
  **钉住它的测试**：`test_since_rejects_dirty_event_time` 和真实 MCP 错误用例。

### 13. 如果重来，方案里该提前写上哪句话

“计划里的验证路径也必须先用 `rg --files` 证明存在；涉及先检查再读取的数据库判据，
要在同一快照里完成，不能把两次 SELECT 当成天然一致。”
