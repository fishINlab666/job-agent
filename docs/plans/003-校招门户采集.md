### 3. 哪些是已核实的，哪些是我猜的

**接口没变，变的是一个请求头：**

```
POST https://<host>/api/v1/search/job/posts
     User-Agent: <Mac UA，见 002 §3 UA 门，仍然承重>
     Referer: https://<host>/
     website-path: campus          ← 这一行是全部开关
     {"keyword":"","limit":200,"offset":0}
  → {"code":0,"data":{"count":627,"job_post_list":[...]}}
```

| 事实 | 怎么核实的 |
|---|---|
| **`website-path` 单独一个头就够** | 纯 httpx，无浏览器、无 `_signature`、无 cookie。只加这个头：nio 2250→627 |
| `portal_type` 是陪跑的 | 真浏览器请求里有 `portal_type=6&portal_entrance=1`（query 和 body 都有），复放时删掉/改值，四个租户 count 一模一样。**002 §8 上一轮猜错的方向就是它** |
| 门户不存在时是干净的负信号 | `code=-9000003`。nio 上 `edu`/`school`、sensetime 上 `index`/`campus` 都是这个 |
| 全量翻页在带头时照样准 | 12 个门户逐个翻到底，**每个都 `rows==count` 且 id 全 unique**（见下表） |
| **池子是稳定的，不是每次调都不一样** | `haidilao/(none)`、`haidilao/index`、`sensetime/(none)` 各连打三次，id 集合三次全等。所以「不带头」是真的第三个池，不是抖动 |
| **校招池的 `recruit_type` 确实是校招** | 全部校招门户上 `parent.name` 恒为「校招」（`parent.id="2"`），leaf 是 `正式`(201)/`实习`(202)。社招池是 `parent="社招"` + leaf `全职`(101)/`劳务`(103)/`实习`(301) |
| 自定义域名是同一个租户 | `hr-jobs.sensetime.com` 与 `sensetime.jobs.feishu.cn` 打 `edu` 返回**同样 159 条、id 交集 159** |
| 蔚来的自建站在飞书前面 | `campus.nio.com` 是自建 Vue（`nio-school-front`），「立即投递」跳 `nio.jobs.feishu.cn/campus/` —— 数据仍在飞书 |

**全量翻页结果（2026-08-05，`rows==count` 全部成立）：**

| 租户 | 不带头 | index（社招）| campus/edu（校招）| 子门户 |

| sensetime 商汤 | 71 | 无此门户 | **159**（`edu`）| —— |
| haidilao 海底捞 | 52 | 34 | **无** | —— |

**门户间 id 交集（决定去重口径）：**

| 关系 | 交集 | 读法 |
|---|---|---|
| 校招 ∩ 社招（三家全部组合）| **0** | 两批岗位完全不重叠，可以分别入库 |
| `xiaopeng/campus` ∩ `xiaopeng/398875` | **335 = 全含** | 398875 是 campus 的子门户，**采了 campus 就别再采它** |

## 二、具体实现

### 4. 数据长什么样，空值怎么办

**校招池 vs 社招池的字段差异（全量对比，不是抽样）：**

| 字段 | 社招池 | 校招池 | 影响 |
|---|---|---|---|
| `recruit_type.parent.name` | 社招 | **校招** | `_recruit_type()` 必须改，见下 |
| `recruit_type.name`(leaf) | 全职/劳务/顾问/外包/实习 | **正式 / 实习** | 同上 |
| `job_category` / `job_function` | **按门户**，不是按租户 | 同 | 002 §3 那条要改 |
| `job_post_info.experience` | nio 2077/2077 有 | nio **0/627** | 校招没有年限要求，对得上 |
| `job_post_info.required_degree` | 有 | 有 | 学历整数码，仍不是届别 |
| `department_id`/`job_type`/`min_salary`/`max_salary`/`job_process_type` | 全空 | 全空 | 12 个门户上全空，不用再找 |
| 标题里的届别 | 个位数 | **xiaopeng 349/436、nio 1/627、sensetime 0/159** | 见下 |

`job_category`/`job_function` 按门户的实测（**这条推翻 002 §3**）：

| 门户 | job_category | job_function |
|---|---|---|
| nio/index、nio/campus、nio/(none) | 0 | 全量 |
| xiaopeng/index | **0** | 1659 |
| xiaopeng/(none)、xiaopeng/campus | 1642 / 436 | **0** |
| **xiaopeng/398875** | **335** | **335（两个都有）** |
| sensetime/*、haidilao/* | 全量 | 0 |

所以「两个字段互斥」是假的。实现不变（两个都读、取到就用、只落
`raw_category` 不参与族判定），但**理由要改**：不是「互斥所以随便读一个」，
是「取值是门户自定义的，映射不过来」。

字段口径：

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| `recruit_type` | `parent=校招` + leaf `实习` → **`campus_intern`**？见下面的决定 | 认不出的组合 → `None`，**不许兜底 social** | 是 |
| `grad_year` | 仍然 `None`（结构化字段里没有） | —— | 是。抠标题见 §8 |
| `raw_category` | `job_category or job_function` 的 `name` | 两个都空 → `None` | 是 |
| `job_family` | `family_from_title(title)` | 判不出 → `None`，**不许兜底 `"other"`** | 是（002 §4 已定，不变）|
| `apply_url` | `https://<host>/<portal>/position/<id>`，**门户段必须有**（见偏差 4）| —— | 自定义域名要用自定义域名 |

**`recruit_type` 这个决定单独说清。** 现在的实现是：

```python
if "实习" in leaf: return "intern"
return "social"          # 因为 parent 恒为「社招」，全量核实过
```

那句注释现在是假的。校招池上它会把 **校招/正式** 判成 `social`——
**这是「把校招岗位标成社招」，比判不出更糟**：判不出用户还能靠 `--loose` 看到，
标错就是静默错到另一个类里去了。

改成先看 `parent`：

```python
parent = (recruit_type.parent.name)      # 社招 / 校招
leaf   = (recruit_type.name)             # 全职/劳务/顾问/外包/实习 · 正式/实习
校招 + 正式 → "campus"
校招 + 实习 → "intern"      # 校招实习：面向学生的实习，本来就归 intern
社招 + 实习 → "intern"
社招 + 其余 → "social"
认不出     → None           # 不兜底
```

`campus + 实习 → intern` 而不是新造一个 `campus_intern`：`match.py` 和
`cli jobs --recruit-type` 现在只认 `campus`/`intern`/`social` 三个值，
加第四个值要同时改 `match.classify()` 的 `rtypes` 判定和 CLI 的帮助文本，
而**收益只是把「校招实习」和「社招实习」分开——用户画像里两者都要**。
不做，但在 §8 写明这是有意不做的。

### 5. 硬约束在哪一行

这次仍是采集，没有不可撤销动作。已在代码里的三条兜住风险：

| 约束 | 在哪 | 挡什么 |
|---|---|---|
| 空结果不许当「全部关闭」 | `ingest.sync()` `jobagent/ingest.py:116` | 门户改名 → `code=-9000003` → 全部岗位被判关闭 |
| 消失比例守卫 | `CLOSE_GUARD_RATIO=0.4` / `MIN_COUNT=5` | 翻页半残 → 批量假关闭 |
| 翻页拿到空批次就整轮失败 | `feishu.py` `fetch()` | 静默截断 |

**新增一条这次必须硬的：门户不存在（`code=-9000003`）必须抛，不许当空。**
它跟 `count=0` 长得像但含义相反：`count=0` 是「这家现在没岗位」（事实），
`-9000003` 是「我打错了门户」（配置错）。后者要是被 `empty_is_authoritative`
放过，表现就是**校招门户改个名，我们静默把 627 条全部关闭**，run 记 `ok`。
所以 `code != 0` 的分支照旧抛，且**不置** `empty_is_authoritative`。

### 6. 判据的粒度

`source_key` 从 `feishu:<tenant>` 变成 **`feishu:<tenant>:<portal>`**。

差这一级会命中什么：不带门户，一个 `source_key` 就得同时装社招 2077 条和
校招 627 条，于是**关闭判定的分母被混在一起**——校招门户整个下线（换届之间
很正常）时，消失比例是 627/2704=23%，低于 0.4 的守卫，**627 条会被静默关闭**。
分开之后同一件事是 627/627=100%，守卫必然触发，run 记 partial 等人看。

门户清单**不许猜路径**。002 §8 上一轮就是猜 `/api/v1/campus/...` 白费的。
做法是从门户 HTML 里读 `website_info`：

| 现象 | 含义 |
|---|---|
| `process_type: 1` | 这个门户是社招 |
| `process_type: 2` | 这个门户是校招 |
| `children_website_info` 非空 | 有子门户（xiaopeng 的 398875）——**父门户已含全部，不单独采** |
| `code=-9000003` | 这个 `website-path` 在这个租户上不存在 |

`ats.py` 的 `domains=("jobs.feishu.cn",)` 挡住了自定义域名。
`hr-jobs.sensetime.com` 要能用，得让 `sources.entry_url` 的 host 参与判定，
**这一步动的是路由判据，风险在「放宽 domains 会把无关站点判成飞书」**——
所以做法是：host 只从 `sources` 行里取（人工登记过的），不从岗位链接里现推。

### 7. 数字的口径

| 这个数 | 分子 | 分母 | 会不会动 |
|---|---|---|---|
| 校招覆盖条数 | 校招门户翻页拿到的条数 | —— | 会。~~1222（三家，2026-08-05）~~ → **8618**（四家，2026-08-06，海底捞换字节）|
| 校招门户覆盖家数 | 有 `process_type=2` 门户的租户数 | 已登记租户数 | 会。~~3/4~~ → **4/4**（换掉海底捞之后，登记的四家都有校招门户）|
| 族判不出比例 | 该门户 `job_family is None` 条数 | 该门户抓到条数 | **必须按门户报，不许按租户合并**——理由同 002 §7 按租户不合并 |

**「校招共 1222 条」这个数的算法要写死在这里**：nio 627 + xiaopeng 436 +
sensetime 159。**不含** xiaopeng 的 398875（335），因为
`campus ∩ 398875 = 335` 是完全包含。上一轮我口头报的 1557 就是这么多算的。

**落地后同一个算法的结果是 8618**：nio 627 + xiaopeng 436 +
**bytedance 7395** + sensetime 160。同样不含 398875。
算法不变、成员变了 —— 所以这两个数并不矛盾，但**任何一个单独出现时必须带
日期和家数**，否则下一个人会拿其中一个去核对另一批数据。

## 8. 这次明确不做什么

- **不做「不带 website-path 那个池」的归属结论。** 三个池两两互不包含
  （nio: 2250/2077 交 1737；haidilao: 52/34 交 9），我不知道它是什么。
  现在给它编一个解释（「全量」「未分配」）就是编。**采集上先只采有
  `process_type` 的门户**，这个池留在 Wiki 的待查里。
- **不做 `campus_intern` 第四个 recruit_type 值。** 理由见 §4 末尾。
- **不做标题抠届别。** xiaopeng 校招池 349/436 标题带「27届」，
  值得做，但它动 `normalize.py`，会同时影响腾讯已落的 801 条
  （那边 `grad_year` 100% 有值，来自站点配置）。单独一份方案。
- **不做门户自动发现。** 这一轮门户路径写在配置里（人工探过的），
  从 HTML 读 `website_info` 是下一份方案。理由：读 HTML 要解析内联 JS，
  只在 4 个租户上试过，n=4 撑不起「所有租户都这样」。
- **不做代投。** 校招门户的投递表单没实测过。

## 四、复盘（实现完回填）

### 11. 方案和实现差在哪

- **多修了一个方案里没有的 bug：`apply_url` 缺门户段。** 方案 §4 把错的形状
  （`/position/<id>`）写成了「口径」，实测是硬 404。见偏差 4。这是这轮唯一
  影响到**已落的 4810 条**的改动 —— 方案里所有「口径」都该被当成待验，
  哪怕它写在「已核实」那一栏里：**§4 那张表当时没有任何一行是打开过链接的。**
- **多了 host/tenant 对不上就炸**（`FeishuAdapter.__init__`）。方案 §6 只说
  「host 只从 sources 行取」，没说取到之后要不要核对。落在飞书自己域名下时
  租户就在子域名里，能核对就必须核对：`entry_url` 抄错一行的失败方式是静默的
  —— 把 B 家的岗位落在 A 家名下。自定义域名抠不出租户，所以只在
  `.jobs.feishu.cn` 后缀下检查。
- **`portal_of()` 落在 `routing.py` 而不是适配器里。** 方案没指定归属。
  放路由层是因为「一行 sources = 一个采集单位」这条要由路由层维持，
  适配器只该收到已经解析好的 `portal`。
- **`portal=""` 归一成 `None`。** 方案没提空串。发 `website-path: ` 空头等于
  赌接口怎么处理空值 —— 实测不带头是第三个池（2249），带 `index` 是社招池
  （2078），不赌。
- **海底捞的替补比方案预期的大一个数量级**：字节 campus **7395** 条，
  是原五源合计（4809）的 1.5 倍。判不出族反而最低（6%），因为它的标题
  规范（「XX实习生」「XX工程师」）最贴 `TITLE_RULES`。
- **数字全部动了**（sensetime 159→160、nio index 2077→2078）。这不是偏差，
  是 §3 那条「验证接口正常要看 `code` 和门户是否存在」正在生效。

### 12. 实现中踩到的坑

| 坑 | 钉住它的测试（都真跑过）|
|---|---|
| 只看 leaf 不看 parent → **把校招正式岗标成社招** | `test_campus_formal_is_campus_not_social` + 反向 `test_campus_intern_still_intern` |
| 认不出的组合兜底 `social` | `test_unknown_parent_is_none`（谁加 `or "social"` 就红）|
| 加了 `portal` 参数但没真发出去 | `test_website_path_header_sent` + `test_no_header_without_portal`（不带门户时**不许有这个键**）|
| 门户不存在被当成「当下没岗位」 | `test_raises` + 对照 `test_count_zero_still_authoritative` |
| 老源的键被改成三段 → 库里 4810 条全成孤儿 | `test_key_without_portal_unchanged` |
| **`apply_url` 不带门户段（全是 404）** | `TestApplyUrlCarriesPortal` 两条，反向那条专盯回退 |
| 自定义域名的投递链接指回飞书域名 | `test_apply_url_uses_custom_host` + `test_request_goes_to_custom_host` |
| `entry_url` 抄错 → 岗位落在别家名下 | `test_feishu_host_tenant_must_match` |
| 门户名里有冒号被静默截断成另一个门户 | `test_portal_with_colon_not_truncated` |
| host 从岗位链接现推 → 放宽域名判据 | `test_host_injected_from_entry_url` + `test_missing_entry_url_leaves_host_none` |

**探租户的错法值得单独记：** 找海底捞替补时先猜了 18 个租户 slug，
16 个直接 `JSONDecodeError`。这和 002 §8 猜门户路径、猜 body 参数是同一种错法
—— **猜命名空间**。管用的做法是打开页面看它自称什么（这条早先就抓出
`luckin` 页面自称「加入狂浪俱乐部」、`horizon` 自称「加入汉森」）。

### 13. 如果重来，方案里该提前写上哪句话

- **「拿到一批数据先问『这是哪一个池』，再问『这批里有什么』。」**
  002 那四轮「飞书没有校招」全都成立——在社招池里。错的不是观测，是没问
  观测的是哪个池。这是 `ATS_RESEARCH.md`「七次口径错」的第八种：
  **把一个视图的性质当成了数据源的性质。**
- **「两个键不等于两批数据，先算交集。」** xiaopeng 的 436+335 我直接加成 771，
  实际交集 335、完全包含。报数之前算一次交集，成本一行代码。
- **「写进方案的每个 URL 形状，都要有一次真打开过。」** §4 那张表把
  `/position/<id>` 当口径写着，它是 404。方案里的「口径」栏如果没有一条
  「怎么核实的」，它就只是**上一个人的假设被排版成了事实** —— 这轮 4810 条
  坏链接的全部来源。**表格排版会让假设看起来像已核实。**
- **「找替补要看页面自称什么，不要猜命名空间。」** 猜 18 个租户 slug、
  猜门户路径、猜 body 参数，是同一种错法的三次复发。
- **「判不出族的比例是公司属性，不是系统属性。」** 同一个 `TITLE_RULES` 下
  字节 6%、商汤 9%、小鹏 37%、蔚来 44%。差异来自标题写法（蔚来大量
  「实习-NSC机电技师」这类内部岗名），不是规则坏了。写「飞书源判不出 40%」
  这种句子就会得出错误结论。
