## 一、产品设计

### 1. 为什么现在做

**不做的后果：用户看到 95 条，而不是本该看到的那些。**

主库 9401 条开放岗位，严格档只有 95 条（1.0%）。拆开看，瓶颈不在「不合格」而在
「判不了」：

```
9401 开放
├─ miss    6868   确定不该推（5689 条是 job_family=tech，画像要 product/operations）
├─ unknown 2438   判不了
│   ├─ 2335 缺 grad_year   ← 本方案针对这一块
│   └─  581 缺 job_family
└─ hit       95
```

缺届别的 2335 条里，**字节一家占 2209 条**。而字节的届别一直在我们自己库里的
`snapshots.raw_json` 里：`job_subject.name.zh_cn` = `2027届校园招聘`（1852 条）、
`2027届前沿技术领域人才校招`（136）、`2027届Seed大模型人才校招`（85）。

**所以这不是上游没给，是我们没解析。** `kb/job-fields.md` v3 那句「飞书 0/8594，
字段真的不存在」说的是 `grad_year` 那一列，当初没发现 `job_subject` 这条通道，
后来这句话被当成了「整个数据源没有届别」的结论。本方案纠正的是这个。

**这件事的性质和 plan 010 的死链同型**：素材早就有，缺的是有人去看。
010 是「docstring 写了缺口没人验」，这次是「一列填充率 0% 被当成了数据源的性质」。
`kb/job-fields.md` v3 自己写着「**反过来也成立：不在这张表里的 0% 就是该查的**」——
飞书 `grad_year` 就在那张「已知为空」表里，于是它免于被查。

### 2. 用户会看到什么

```
用户跑 jobs --matched（严格档）
  → 现在：95 条
  → 做完：多出那些「届别本来就写在招聘项目名里、且岗位族和城市也对得上」的岗位
    屏幕上多出来的行，来源主要是字节校招

用户跑 jobs --matched --allow-missing grad_year
  → 现在：1952 条，其中大量是「我们不知道届别」
  → 做完：这一档变小或不变，因为一部分岗位从「不知道」升级成了「确定命中/确定不命中」
    **这一档变小是好事**：它意味着不确定性减少了，不是岗位变少了
```

**具体多少条，方案阶段不报数。** 届别对上了还得岗位族和城市也对得上，
这三个条件的交集要跑完才知道。§7 写清了这个数该怎么量。

## 二、具体实现

### 4. 数据长什么样，空值怎么办

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| `job_subject` | 嵌套 dict：`{"name": {"zh_cn": "2027届校园招聘"}}` | 整个键缺失 / `name` 为 `None` / `zh_cn` 为 `None` —— **三层都要防**（小鹏是整个 `job_subject` 为 `None`，商汤有 7 条也是） | 是 |
| 解析结果 | `["27"]` | **`None`**（信息不全），**不是 `[]`** | 是 —— `[]` 的语义是「不限届别，任何届别都命中」，把「项目名里没写届别」洗成「不限」等于把不知道说成确定命中 |
| `jobs.grad_year` | 两位字符串 `"27"` | 保持 `NULL` | 是 |

**多届别怎么存。** `grad_year` 列是单值（`TEXT`），而解析出来是 list。
现有约定是取第一个（腾讯那边一直是单值）。本方案实测 21 个取值全部解析成**单元素**
`['27']`，所以这次不会触发多值截断。但代码要写成「取第一个并在注释里说明」，
而不是假装它一定是单元素 —— 下个招聘季出现 `26/27届` 时这里不能静默丢。

**已有值不许被覆盖成空。** 照 `refresh_grad_year` 的第三条硬约束：
重算出 `None` 而库里有值时，保留旧值并计入 `skipped_would_null` 报出来。

### 5. 硬约束在哪一行

本方案不引入不可逆动作，硬约束是**防假信号**那一类，两条：

1. **`grad_year` 不进 `_fp()`。** 这是既有设计（`ingest.py:52-63` 刻意不含），
   本方案不动它。所以存量刷新必须走 `refresh_grad_year()`，不能靠 sync ——
   sync 看指纹没变就只动 `last_seen_at`（plan 008 实测：807 行里 804 行被静默跳过）。
2. **`grad_year_from_raw()` 是 classmethod / staticmethod。**
   `refresh_grad_year()` 用 `getattr(type(adapter), "grad_year_from_raw", None)` 取它
   （`ingest.py:99`），写成实例方法取不到，会被当成「这个源不支持刷新」而抛
   `RefreshUnsupported` —— 那是静默跳过，不是报错。

### 6. 判据的粒度

**「这个项目名说的是哪个届别」的判据是「项目名整串 + 必须含『届』字」**，
粒度是**招聘项目级**，不是租户级也不是岗位级。

差一级的后果，两个方向都要写清：

- 粗一级（按租户定届别，「字节都是 27 届」）：字节 7368 条里有 5295 条实习，
  项目名是 `ByteIntern` / `日常实习`，**不带届别**。按租户一刀切会把这 5295 条
  钉成 27 届，而它们大概率不限届别 —— 把「不知道」洗成「确定」，方向最错。
- 细一级（按岗位标题）：那是通道二，已经有了，飞书四家里只有小鹏的标题带届别。

**这条判据和 007→009 那次的教训是同型的**：007 拿 `recruitLabelName` 字符串匹配，
009 换成 `projectId` 分桶，因为字面量会变而 id 不会。这里用的是**项目名字符串**，
所以同样有「文案一变就失效」的风险 —— 但飞书接口给的 `job_subject` 只有
`id` + `name`，而 id 是每个租户自己的（`7194661644654577981` 这种），
**跨租户没有稳定语义**，没法像腾讯 projectId 那样分桶。所以这里只能用字符串，
代价是换季要复核。这一点进 §12 和 kb。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| `job_subject` 届别覆盖率 | 最新快照里 `job_subject.name.zh_cn` 能解析出届别的岗位数 | 该源最新快照总数 | **会** —— 岗位池是活的，且换季时项目名会全换 |
| 严格档条数变化 | `jobs --matched --limit 1` 的标题行数字 | —— | 会 |
| 刷新条数 | 实际 UPDATE 的行数 | 该源全部行（含已关闭）| 会。**幂等：跑第二次报 0** |

**报「严格档从 95 涨到 N」时必须同时报另外两个数**（`--allow-missing grad_year`
和 `--loose`）。理由是 plan 004 立的那个不变量：**后两档的数不该随「加一条观测通道」
变大** —— 通道只该把行在档之间搬，不该扩大岗位池。第三档涨了说明多算了岗位，
跌了说明错杀。004 落地时前两档 41→95、后两档 1952/2533 纹丝不动，就是这个在起作用。

### 8. 这次明确不做什么

- **不改 `parse_grad_years` / `grad_years_from_title`**，因为现有实现对这 21 个取值
  全部给出正确结果。那条 `（25/26届）` 只解析出 `['27']` 是既有行为（四位年份先命中
  就返回），**只影响 1 条**，而改共用解析函数会波及标题通道的 348 条。
  要改也该单独立方案，先量清影响面。

- **不把 `job_subject` 落成新的库列**，因为当前唯一用途是推导届别。
  照 `raw_category` 的先例（`kb/job-fields.md`：只落原文、不参与判定）——
  真要落也该等有第二个用途。原文已经在 `snapshots.raw_json` 里，不会丢。

- **不动 `_fp()` 的键**（不把 `grad_year` 加进指纹），因为指纹口径变一次全库重算，
  而且 008 那条「换季刷新」的设计就建立在它不在指纹里之上。

- **不给实习岗兜底届别。** `ByteIntern` / `日常实习` / `营销暑期实习生招募` 这些
  解析成 `None`（信息不全），**不写成「不限」**。腾讯那边实习是「不限」，但那是
  projectId 分桶实测出来的（plan 009）；飞书这里没有等价证据，编一个「不限」
  等于把 5295 条实习岗洗成「任何届别都命中」。

- **不做小鹏的增量**，因为它 `job_subject` 全是 `None`，届别在标题里、通道二已覆盖。
  本方案对小鹏是 0 增量，这是预期不是遗漏。

所以在 `match.classify()` 眼里它就是**字段通道**（`match.py:104` 先读字段、
读不到才退标题）。已有的 `test_field_wins_over_title` 钉的就是这个顺序。
新写一条只会重复。**这一点值得写下来**：通道三是「补数据」不是「加判定分支」，
所以它的测试全在采集层和刷新层，match 层一行不用改。

**「做一半」在这次具体长什么样**：写了 `grad_year_from_raw()`、刷了存量，
但没接进 `fetch()`。跑 `refresh-grad-year` 全绿、库里数字也对，
**但下一次 sync 进来的新岗位届别又是 NULL** —— 而且因为 `grad_year` 不在指纹里，
这些新岗位不会因为「届别为空」触发任何事件。表现是「数字慢慢退回去」，
几周后才被发现。所以必须有一条守采集路径的测试。

### 12. 实现中踩到的坑

- **现象**：`kb/job-fields.md` v3 写着「飞书 0/8594，字段真的不存在」，这句话让届别
  补全在飞书上停了四天没人再看。
  **原因**：那句话说的是 `grad_year` **那一列**，是准确的。但它被放在
  「已知为空的字段」表里，而那张表的语义是「查过了，确实没有」——
  于是「这一列没有」被读成了「这个数据源没有届别」。
  实际上届别一直在 `job_subject.name.zh_cn` 里，从采集第一天起就在快照中。
  **修法**：kb v5 改写那一行，明确区分「列不存在」和「数据不存在」，
  并把三条通道并列写出来。
  **钉住它的测试**：`test_real_subject_values_all_four_tenants`（17 个真实取值）。

- **现象**：一条既有测试 `test_unsupported_source_exits_zero_with_explanation` 变红。
  **原因**：它拿飞书当「源站本来就没有届别通道」的例子，而本方案给飞书加上了通道。
  两个真实适配器现在都支持刷新，那个场景在真实适配器里已经不存在。
  **修法**：用假适配器 `NoGradYearAdapter` 构造那个场景（那条 `RefreshUnsupported`
  分支还在，是给将来新增的源用的），**并加一条反向用例**
  `test_feishu_now_supports_refresh`。只改前者的话，将来谁把 `grad_year_from_raw`
  删掉或改成实例方法，前者反而变绿 —— 通道没了却没人知道。
  **钉住它的测试**：上面那两条。

- **现象（没踩到但差一步）**：`grad_year_from_raw` 如果写成实例方法，
  `refresh_grad_year` 会抛 `RefreshUnsupported` 而**静默跳过**，不报错。
  **原因**：`ingest.py:99` 用 `getattr(type(adapter), ...)` 从类上取。
  **修法**：写成 `@staticmethod`，并加 `test_grad_year_from_raw_is_class_accessible`
  显式从类上直取。这条是照腾讯那份抄的形状，抄的时候顺手把这个约束也抄了。

### 13. 如果重来，方案里该提前写上哪句话

**「『已知为空』的清单需要定期回头质疑，否则它会从『我们查过了』退化成『不许再查』。」**

`kb/job-fields.md` v3 自己写着「**反过来也成立：不在这张表里的 0% 就是该查的**」——
这句话立得很好，但它只覆盖了「不在表里的」。飞书 `grad_year` 恰好**在**那张表里，
于是它免于被查。一张「已知为空」的表同时是一张「不用再看」的表，这是它的副作用。

这和 plan 010 §13 是同一类问题的两个面：010 是「写清了没验什么，但没人去验」，
011 是「验过了一个更窄的命题，结论被当成了更宽的」。两次的共同点是
**文档里的一句准确的话，被下一个读者放大了适用范围**。

**具体该加的动作**：`kb` 里凡是「已知为空/已排除/不支持」这类清单，
每一条都要写清**验的是哪个命题**（这里应该是「`grad_year` 这一列不存在」
而不是「没有届别」），并且**记下验的日期**，让它看起来像一个会过期的观测，
而不是一条定律。kb v5 已经按这个改了。
