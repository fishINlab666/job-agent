## 一、产品设计

### 1. 为什么现在做

两件事，一个根因。

**问题 5（反馈报告原文）**：`jobagent/adapters/tencent_join.py:44` 的 `GRAD_WINDOW` 是按招聘项目推的常量，注释写着「每个招聘季这两个窗口都会变，换季时必须重新核对」。但 `grad_year` **不在指纹字段里**（`ingest.py:52-63`）—— 换季时就算记得改常量，存量岗位因为指纹没变走的是 `ingest.py:258-261` 那条「只更新 `last_seen_at`」的分支，库里的届别停在旧值，永远不会更新。

实测确认（§9 命令 A）：改了常量跑一轮，`updated=0`、`job_updated` 事件 0 条、库里届别一个字没动。

不做的后果**不是「今天有用户受损」**。今天真画像下因届别漏掉的岗位是 **0 条**（§9 命令 D）。后果是两条：

1. **换季那天会白排查一次。** 有人改了常量、跑了 `sync`、看到 `updated=0`，然后去翻适配器代码找为什么没生效。而 007 落地时就会踩到这个 —— 它改的正是 `GRAD_WINDOW` 的值。
2. **故障的外观和健康完全一样。** 届别过期时 `cli status` 显示 `ok`、805 条、同步时间新鲜；`cli jobs` 没有届别列；`cli digest` 打印「没有新增。」用户没有任何通道能发现届别是旧的。而过期届别判的是 `miss` 不是 `unknown`（§9 命令 C），连 `cli jobs` 那个「?」信息不全标记都不亮，`--allow-missing grad_year` 也救不了。

所以本方案做两件事：**让存量能被刷新**（问题 5，选方案 B）+ **让过期能被看见**（告警）。

### 2. 用户会看到什么

场景一，换季刷新：

```
用户改了 tencent_join.py 里的 GRAD_WINDOW（或者跑完 007）
  → 跑 uv run jobagent refresh-grad-year tencent_join
  → 屏幕上出现：已更新 805 条岗位的届别（应届类 459 → 26，在读实习类 346 → 不限）
  → 再跑一次：已更新 0 条岗位的届别（已经是最新）
```

场景二，过期告警：

```
用户跑 uv run jobagent status --check-grad-year
  → 表格照常打印（源/公司/开放岗位/最近同步/状态/抓取数）
  → 抓一次 join.qq.com 的 V2Index bundle（6KB），读站点自我声明的届别
  → 站点声明 27，代码里是 26 → 表格下面多一行：
     ⚠ tencent_join 的应届届别代码里是 26，站点现在写「2027应届生招聘」——
       改 tencent_join.py 的 CAMPUS_GRAD_YEAR，再跑 refresh-grad-year --apply
  → 两边一致时不打印任何东西
```

告警不阻塞任何操作，`status` 的退出码不变。

**为什么要一个 flag**：告警需要联网抓 bundle，而 `status` 现在是纯本地只读命令。默认不抓 —— 让一条本地命令悄悄依赖外网会让它在断网时变慢或报错。`--check-grad-year` 显式要求这次去看。

## 二、具体实现

### 4. 数据长什么样，空值怎么办

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| 007 之后的届别推导结果 | 应届类 `"26"`、在读实习类 `"不限"` | `None`（认不出标签） | 是。`None` 落库成 `NULL` |
| 站点声明的届别（告警用） | `"26"`（从 `"2026应届生招聘"` 抽） | 抽不到 → **不告警**，打印「拿不到站点声明」 | 是。抽不到不等于过期 |
| `jobs.grad_year`（刷新写入） | 常量当前值 | **写 `NULL`，不写空串** | 是 |
| `refresh-grad-year` 的 WHERE 条件 | 只更新 `grad_year` 和常量不一致的行 | —— | —— |
| 告警读到的届别 | 过 `parse_grad_years` 取 `max` | `None`（看不懂）→ **不告警**；`[]`（不限）→ **不告警** | 是。这两态都不是「过期」，静默跳过 |

四条硬要求：

1. **`refresh-grad-year` 只写 `grad_year` 一列，不许碰 `fingerprint`。** 顺手重算指纹会把方案 B 变成方案 A，带上 9401 条洪水。有一条专门守这个的测试（§10）。
2. **必须幂等。** WHERE 里带 `grad_year IS NOT <新值>`，第二次跑改 0 行。
3. **认不出 `recruit_type` 的行不许被兜底成某个届别。** `recruit_type IS NULL` 的行 `grad_year` 应该保持 `NULL`。
4. **告警的三态必须分开。** 库里届别是 `NULL` 是「这个源就没有」（飞书 8594 条全是），不是「过期」；`parse_grad_years` 返回 `[]` 是「明确不限」，也不是过期。只有「有明确集合且 `max` 小于期望届别」才叫。

### 5. 硬约束在哪一行

`refresh-grad-year` 是一条**批量写库**命令，会改 807 行。按项目原则它需要一道闸门，但它不是不可撤销的（跑错了改回常量再跑一次就回来，且不产生事件、不外发）。所以：

- **软约束**：命令默认 `--dry-run`，打印「会改多少行、从什么改成什么」，不写库。
- **要真写库必须显式 `--apply`。** 这是 API 形状的硬约束：没有 `--apply` 这个 flag，代码走不到 `conn.commit()`。
- 不做「输入 yes 确认」那种交互式闸门 —— 项目里所有命令都是非交互的，加一个例外会破坏可脚本化。

对照 `docs/SPEC.md §7`：`apply --dry-run` 不许写库那条约束的精神在这里同样适用，默认不写是对的。

告警是纯读、纯打印，无约束。

### 6. 判据的粒度

告警的判据必须是 **`source_key` × `recruit_type` 两级**，不能只到 `source_key`。

差一级会命中什么（已实测，§9 命令 E）：

```
只按 source_key 分组：max(grad_year) = '27'  → 期望 27 → 不告警  ← campus 的 26 被 max() 盖掉，规则整个空转
按 source × recruit_type：campus '26' / intern '27' → campus 告警  ← 正确
```

这是本方案最容易做废的一处：粒度差一级，代码写完了、测试也能绿，但**告警永远不会响**。

另一条粒度提醒：`GRAD_WINDOW` 本身的粒度也是粗的 —— 6 种 `recruitLabelName` 压成 2 个 `recruit_type`，`日常实习`（大二大三可投）和 `实习生 青云计划` 共用一个届别。本方案不修这个（§8），但告警是按 `recruit_type` 分组的，所以**它也看不见桶内的混淆**。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| `refresh-grad-year` 报的「已更新 N 条」 | 实际 `UPDATE` 的 rowcount（`grad_year` 和常量不一致的行） | 不是比率 | **会。** 幂等，所以第二次是 0；随库里岗位数动 |
| 「9401 行指纹会变」 | 新 `_fp`（含 `grad_year` 键）重算结果 ≠ 库里已存 `fingerprint` 的行数 | 9401 条 `jobs` 全表（含已关闭） | 会。随库增长 |
| 「807 条届别值会变」 | 换季后 `grad_year` 值真的不同的行数 | 9401 条全表；这 807 全在 `tencent_join` | 会 |
| 「今天因届别漏 0 条」 | 真画像下 `miss` 且改届别后变 `hit` 的腾讯开放岗位数 | 805 条腾讯开放岗位 | 会。**换画像就变** —— 画像收窄成 `['28']` 时是 31 条 |

三条口径警告：

- **9401 和 807 是两个不同的问题的数，不要混。** 9401 是「加了一个 JSON 键导致哈希变了」，807 是「届别值真的变了」。把它们当成同一个数会得出「加进指纹只影响腾讯」这个错结论。
- **「今天漏 0 条」不等于「这个 bug 无害」。** 它今天零影响，因为真画像同时要 26 和 27 两届。画像一收窄就露出来。
- **不要把 `807` / `9401` / `41` 写进任何文档当常量。** 报数字必须带日期和画像。最后一轮 sync 是 2026-08-06T17:07，本方案的所有数字是 2026-08-09 的快照。

### 8. 这次明确不做什么

- **不改届别的值，也不改推导形状。** 那是 007 的事（应届类 `"26"`、在读实习类 `"不限"`）。本方案只提供**刷新的手段**和**过期的告警**。`docs/plans/004-届别补全.md §8` 那条「不改 `GRAD_WINDOW`，要动得先去门户上看页面写的是哪一届」的前置条件**已经满足了** —— 2026-08-09 核实过，见 §3 的核实表。
- **不按日历推期望届别。** 那条判据（「N 年 8 月起应是 N+1 届」）和它要监控的对象共用同一个被推翻的前提，实测对今天正确的 `campus=26` 也告警（§9 命令 E）。唯一可靠的信号是站点自己的声明。
- **不让 `status` 默认联网。** 告警要抓 bundle，做成 `--check-grad-year` 显式 flag。让一条本地只读命令悄悄依赖外网，会让它在断网时变慢或报错。
- **不声称「问题 5 已修」，除非 5b 也做了。** 本方案落地后系统输出**零变化**（因为不改任何届别值）。往文档里写「已修」会让下一个人以为库里届别现在是对的。§0 里也只写「刷新命令可用」，不写「届别已正确」。
- **不把 `grad_year` 加进 `_fp()`（方案 A）。** 三条理由，逐条有实测：① 改全部 9401 行指纹，要先做一次不可逆的指纹回填 —— 而 plan 006 §0 立的「全等才动手」前置检查这次是 `0/9401`，不通过；② 造 9401 条空 diff 的假 `job_updated`，是 plan 006 问题 1 同型放大 588 倍；③ 要做完得改三处（`_fp`、`ingest.py:224` 的 diff 清单、`cli.py:241` 的渲染门），漏任一处就是「有更新但用户看不到内容」，那已经是这个形状的第三次。买到的只是省掉一条一年跑一两次的命令。

- **不把刷新挂进 `db.migrate()`。** `jobagent/cli.py:57` 的 `sync` 每轮都调 `db.init()` → `migrate()`，挂进去等于每次 sync 按当前常量重刷存量 —— 那是方案 C 的隐蔽版本，而且 `migrate()` 现有内容全是幂等结构变更（补列/建索引），掺业务数据回填会破坏这层语义。
- **不做「不落库、判定时现场推导」（方案 D）。** 实测它的输出和现状**完全相同**（严格/放开届别/全放开三档一字不差），因为推导规则就是同一个 `GRAD_WINDOW`。它只搬动了「猜的值存在哪里」，却要红三条既存回归锁（`test_adapter_tencent.py:106/108/131`，那是问题 3 刚补的）并连带改四处文档口径（`docs/kb/job-fields.md` 的 KNOWN_EMPTY 表、`scripts/run_five.py:159`、`docs/SPEC.md:78`、`docs/SPEC.md:182`）。它是一次纯口径重构，有独立理由时单独立项。
- **不修 `_recruit_type` 的粒度**（6 种标签压 2 桶）。要按 `recruitLabelName` 或 `projectName` 分桶，得先有站点侧证据说明每个项目各自的窗口。现在做等于编。

- **不改 `cli.py:241` 的渲染门。** 本方案不产生 `job_updated` 事件（`refresh-grad-year` 不走 `sync` 路径），渲染门与它无关。改它是方案 A 的连带工作。

- **监控规则不能和被监控对象共用假设。** 这次的告警判据用「8 月该换届」推期望值，而它要监控的恰恰是「届别常量对不对」—— 两者共用同一个前提，所以前提错的时候，规则不会报警，反而会对正确值报警。写监控时要先问一句：**这条规则的判据来自哪里？如果来自我自己的推理，它就只能验证一致性，不能验证正确性。** 可靠的判据必须来自被监控系统之外的独立信号（这次是站点自己的声明）。这一条该进模板 §6（判据的粒度）旁边，加一个「判据的来源」槽位。
