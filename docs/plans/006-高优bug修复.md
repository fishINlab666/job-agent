## 一、产品设计

### 1. 为什么现在做

四个 bug，前三个来自反馈报告，第四个是过方案时发现的。都有明确的修复路径：

**问题0：diff 键名契约对不上，`digest` 当场崩（高，本方案新增）**
- **不做会怎样：** 岗位改了标题或岗位族、且该岗位够得着用户画像时，
  `digest` 命令抛 `KeyError('old')` 直接崩掉。用户当天什么都看不到 ——
  不是少看到城市变更，是整个日报打不开
- **影响面：** 比报告里的问题 1 更靠前。问题 1 是「该显示的没显示」（死代码），
  这条是「显示的时候崩」。
  **但准确说法是「上了膛没击发」，不是「活故障」**（2026-08-07 实测改掉原来的
  「活故障」）：崩溃机制已端到端复现，今天可达的条数却是 **0** —— 唯一产生过
  `job_updated` 的源（tencent_join）是 tech 重仓，和画像错开了。
  前向暴露面是 **2533/9399** 在招岗位，其中 2492 挂在四个还没过 bootstrap 的
  飞书源上，**第二轮飞书同步就带电**。口径和数据见 §7
- **崩了之后不自愈，会卡住：** `--mark` 的 UPDATE 在 `cli.py:287-292`，
  在渲染循环（`:240-250`）**后面**，且 `digest` 全程没有 try/except。
  渲染崩了 → `notified_at` 一行都写不进去 → 下次 `digest` 同一批重新扫、
  同一行重新崩。而 `shown` 在 `cli.py:202` 就把所有检查过的事件都收了，
  所以一条坏事件会把**整批**待推送事件一起卡住
- **根因：** 生产端 `ingest.py:200` 写 `{"from":…, "to":…}`，
  消费端 `cli.py:243/245/249` 读 `['old']`/`['new']`，
  中间 `db.add_event`（`db.py:307-314`）只做 `json.dumps`，不改键名
- **为什么一直没被发现：** `digest` 的 `job_updated` 渲染分支零测试覆盖。
  `tests/test_e2e.py:126` 那句是 `print(f"  - digest: ✓")` —— 一句 print，
  不是断言
- **为什么必须排在问题 1 前面：** 见 §8

**问题1：城市变更不推送（高）**
- **不做会怎样：** 岗位从"北京"改成"只剩深圳"时，按城市硬过滤的用户收不到通知，相当于岗位关闭却不知道
- **影响面：** 文档场景三承诺的核心功能
- **根因：** `ingest.py:199-203` 的 diff 字段清单不包含 cities，且库里 cities 存为 JSON 字符串，新数据是 list，直接比较永远不等

**问题3：腾讯 recruit_type 兜底违反规则（高）**
- **不做会怎样：** 腾讯源站加一种新的招聘项目标签，一批岗位会被静默标成确定命中的 26 届校招（比判不出糟糕得多）
- **影响面：** 违反 SPEC §6 硬规则"认不出就写 None，不许兜底"
- **根因：** `tencent_join.py:47-52` 认不出时兜底 "campus"，`grad_year` 跟着被推成 "26"（`:129` `GRAD_WINDOW.get(rtype)`）。
  **两个字段都错，但只需要改一处** —— `.get(None)` 返回 `None`，
  `_recruit_type` 改完 `grad_year` 自动跟着对（见 §0 偏差 2）

**问题4：腾讯分页静默截断（中→高）**
- **不做会怎样：** 接口说总数还有、批次返回空时，腾讯适配器带着半截数据正常返回。40% 关闭守卫能兜住大截断，但 30% 的截断会穿过去，把两百多条在招岗位误判关闭
- **影响面：** 数据完整性
- **根因：** `tencent_join.py:99-102` 遇到空批次直接 break，飞书的正确做法是抛异常

### 2. 用户会看到什么

**问题0修复前（触发时的行为。库里 106 条 `job_updated` 里 88 条负载长这样，
但今天可达 0 条 —— 口径见 §7）：**
```
公司把岗位标题从「产品运营」改成「产品运营（高级）」
→ 指纹变了，触发 job_updated，diff = {"title": {"from": …, "to": …}}
→ 用户跑 `digest`
→ cli.py:243 读 diff['title']['old']
→ KeyError: 'old'，命令崩掉
→ 用户当天看不到日报 —— 不是看不到这条变更，是整个日报打不开
```

**问题0修复后：**
```
同样的改动
→ digest 正常打印「标题: 产品运营 → 产品运营（高级）」
→ 其余新增岗位、匹配结果照常显示
```

**问题1修复前：**
```
岗位原本在北京、上海、深圳三地招聘
→ 公司更新：只在深圳招
→ 用户画像：只接受深圳
→ 系统触发 job_updated 事件（因为 cities 在指纹中）
→ 但 payload.diff 为空
→ 用户收到通知："岗位 XXX 有更新"，但看不到是城市变了
→ cli.py:248 渲染城市变更的代码是死代码，永远走不到
```

**问题1修复后：**
```
岗位从北京、上海、深圳 → 只在深圳
→ 系统触发 job_updated 事件
→ payload.diff = {"cities": {"from": ["北京", "上海", "深圳"], "to": ["深圳"]}}
→ 用户收到通知："岗位 XXX 有更新 — 城市: 北京, 上海, 深圳 → 深圳"
```

**问题3修复前：**
```
腾讯源站新增招聘项目"管培生计划"
→ _recruit_type("管培生计划") 不匹配已知模式
→ 兜底返回 "campus"
→ grad_year 被设为 "26"
→ 用户看到：一批"26届校招"岗位，实际上是认不出的新项目
→ 不符合 26 届画像的用户被错杀
```

**问题3修复后：**
```
腾讯源站新增招聘项目"管培生计划"
→ _recruit_type("管培生计划") 返回 None
→ grad_year 也写 None（因为 GRAD_WINDOW 只针对已知类型）
→ 用户看到：岗位的 recruit_type 和 grad_year 为空
→ 按 SPEC §6 规则，进入"信息不全"分类，不会被错杀
```

**问题4修复前：**
```
腾讯接口返回 count=500
→ 前 4 页正常（batch 非空）
→ 第 5 页 batch 为空（接口异常）
→ 腾讯适配器：if not batch → break，带着前 400 条返回
→ 40% 关闭守卫未触发（400/500 = 80%）
→ 100 条岗位被误判关闭
```

**问题4修复后：**
```
腾讯接口返回 count=500
→ 前 4 页正常
→ 第 5 页 batch 为空
→ 腾讯适配器：抛 RuntimeError("返回空批次，但 count=500 只拿到 400 条，拒绝返回半截数据")
→ 整个源标记为 failed
→ 用户看到同步失败，数据库不写入半截数据
```

## 二、具体实现

### 4. 数据长什么样，空值怎么办

**问题1：cities 字段**

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| cities（库） | `'["北京","深圳"]'`（JSON 字符串） | `NULL` 或 `'[]'` | 是 —— 都表示「没拿到」，**不表示「不限」** |
| cities（内存） | `["北京", "深圳"]`（list） | `[]`（`RawJob` 的默认值，`base.py:22`） | 同上 |
| 「哪都行」 | `["不限"]` / `["全国"]` / `["远程"]` —— **非空列表** | — | 是 —— 它是一个**有值**的状态 |

**`[]` 不是「不限」。原方案这一行写错了（§0 偏差 7）。**
「不限」在本仓是一个真实的城市值：它在 `normalize.CITY_WILDCARDS`（`normalize.py:106`）
里，源站写「工作地点不限」「全国多地」时，`normalize_city` 会把它留在列表里，
`any_city_ok`（`:121`）认它为「哪都行」。所以：

- `["不限"]` = 源站明说哪都行 → 匹配时**放过**
- `[]` = 这次什么都没拿到 → 匹配时判 `unknown`，`missing` 里记一条 `cities`
  （`match.py:123-125`）

两个状态渲染成同一句话就把这个区分抹掉了。空列表显示**「未写」**，
沿用 digest 表格里已有的写法（`cli.py:298`）。

**实测（2026-08-07，真库 9401 行）：** `cities` 今天 `NULL=0`、`'[]'=0`、`''=0`，
`json_array_length` 为 0 的也是 0 —— 全都有值。但空是能出现的形态
（`RawJob.cities` 默认 `[]`，见 `base.py:22`；`split_cities(None)` 返回 `[]`，
见 `normalize.py:90-91`），代码要接住，所以有 `test_cities_going_empty_is_a_change`。

```bash

q = lambda s: c.execute(s).fetchone()[0]
print('总行数', q('select count(*) from jobs'))
print('NULL  ', q('select count(*) from jobs where cities is null'))
print('空数组', q(\"select count(*) from jobs where json_array_length(coalesce(cities,'[]')) = 0\"))

```

**修复策略（实际实现）：**
- 抽一个 `ingest._cities()`，两种形态都接（库里的 JSON 串 / 内存里的 list），
  内部 `sorted`。**`_fp` 和建 diff 处共用它** —— 让「同口径」由代码保证，
  不靠注释提醒。不 sorted 会出现「指纹说没变、diff 说变了」：指纹算的是排序后的值
  （`_fp`），存库存的是适配器给的原始顺序（`:183`/`:212`），真库 9401 行里
  **1090 行本身没排序**，这不是纸上防御
- 动 `_fp` 之前先量过：两种写法在 9401 行上结果**相同 9401、不同 0**，
  不会造一轮假 `job_updated` 洪水（§0 偏差 9）
- diff 里存**排序后的 list**，不是字符串 —— 渲染时才拼
- 渲染：`cli._fmt_cities()`，`"、".join(cities)`，空列表 → 「未写」。
  用顿号而不是逗号，和 `cli.py:487` 的详情页一致（digest 表格里的 `/` 是列宽所迫）

**问题0：diff 的键名契约**（已修，下表是**修之前**的状态）

### 8. 这次明确不做什么

**修复顺序是硬的：问题 0 必须在问题 1 之前。**

不是「先修严重的」这种排序偏好，是两个改动之间有依赖：

```
修之前：cities 不进 diff → 渲染里的 cities 分支够不到 → 那行的 KeyError 是死的
只修问题 1：cities 进 diff → 分支活了 → 那行 KeyError 跟着活
```

那个分支用的是同一套 `['old']`/`['new']` 错键。先修问题 1 的话，
等于把一个崩溃点从「够不到」变成「够得到」—— **单独修问题 1 会让情况更糟**。
反过来先修问题 0 是安全的：键名对上之后，cities 分支不管什么时候活过来都是对的。

**这个约束已经履行（2026-08-07）：** 问题 0 先落地（键名改消费端），
问题 1 后落地（cities 进 diff）。落地后 106 条存量负载全过一遍新渲染，0 崩溃 ——
也就是说那个「跟着活」的 KeyError 在活过来之前就已经被填掉了。

- **不改 diff 的生产端键名** —— `ingest.py` 建 diff 处继续写 `from`/`to`。库里 90 条
  存量负载都是这套键，改生产端等于把它们变成读不出来的孤儿（§4）
- **不改 cities 的存储格式** —— 仍然存 JSON 字符串，只在比较和展示时处理
- **~~不改指纹的计算逻辑~~ —— 这条实现时破了，破得有限**：cities 仍然在指纹里，
  diff 也开始包含它，这部分照原样。但 `_fp` 的**写法**改了 —— 内联的
  `sorted(job.cities)` 换成调用 `_cities()`，为的是让指纹和 diff 共用一个口径、

### 12. 实现中踩到的坑

**1. 表的列名靠记忆写，第一条查询就报错。**
`events` 表的列是 `kind`，不是 `type`（`schema.sql:80`）；`events` 里**没有**
`external_id`，要关 `jobs` 得走 `job_id`；`jobs` 里**没有** `status`，「在招」是
`closed_at IS NULL`。三次都是查了 `pragma table_info` 才对。写查询之前先看列，
比事后改三遍快。

**2. 量「改动安不安全」时，第一版量成了自己跟自己比。**
为了确认动 `_fp` 不会造假 `job_updated` 洪水，第一版脚本写的是
`d_new = dict(d_old)` 再比两个指纹 —— 那当然全等，**什么都没证明**。
有效的版本是拿新 `_fp` 去重算**库里已存的** `jobs.fingerprint`：对照物必须来自
被改动之外。这个坑不报错、结果还很好看，最容易蒙过去。

**3. 加函数把自己 docstring 里的行号写废了。**
`_cities` 的 docstring 引用「存 cities 的两处，见 `:183/:212`」，而这个函数插在它们
上面 —— 写完的瞬间它们就变成了 `:197/:236`。`_fmt_cities` 同样把 `cli.py:280`
推成了 `:297`。同一文件内的行号引用，只要在它上面加东西就废。现在两处都改成
描述位置 + 一句「这里不写行号：这个函数本身就把下面的行号推移过一次」。
顺带发现 `cli.py` 里引用 `schema.sql:56` 也是错的（实际 `:57`）。

**4. 方案指定的测试是空转的，但它是绿的。**
`test_city_reorder_is_not_a_change` 在正确实现上绿、在「忘记 sorted」的变异上
**也绿**。如果只按方案写这一条、看到绿就收工，sorted 缺失会带着一条绿测试上线。
六种变异里只有这一条给出了新信息，其余五条都只是确认了预期。
**变异测试的价值不在「确认测试有效」，在「找出哪条测试其实什么都没测」。**

**5. 「不限」这个词差点被当成占位符用掉。**
方案 §4 写着 `[]` 显示「不限」，照着写会让两个相反的状态印成同一句话。
发现它的路径是去读 `match.classify` 怎么用 cities —— 空列表判 `unknown` 并往
`missing` 里记一条，非空的「不限」直接放过。**渲染层的措辞不能和匹配层的取值撞车。**

### 13. 如果重来，方案里该提前写上哪句话

1. **「加函数会把同文件后面的行号全推移，方案里的行号引用写完就得复查一遍；
   docstring 里尽量引符号名，不引行号。」** —— 这次三处行号写废，两处是自己造成的。

2. **「一个字段只在指纹里、不在 diff 里，症状就是空 diff 事件。
   查 bug 先按「哪个字段两边不对称」去找，不是按「哪里报错」去找。」** ——
   这个 bug 不报错，只是让用户收到一句没有下文的「有更新」。

3. **「测试要能跑到被改的那行代码。写反向用例之前先问：这个用例下，
   被改的代码执行吗？」** —— 只重排城市这个用例读起来完全合理，
   但它连建 diff 的分支都进不去。方案里点名让它守 sorted，是纸上推理的结果。

4. **「量『改动是否安全』时，对照物必须来自被改动之外（库里存的值、
   改动前的输出），不能是当场从同一份代码算出来的第二个副本。」**

5. **「渲染兜底用的词，先去匹配层确认它不是一个真实取值。」** ——
   「不限」「未知」「无」这类词在归一化仓库里往往真的是某个字段的合法值。

6. **「存量数据能验的分支，取决于 bug 本身放进去了什么。修 A 字段进不了 diff
   的 bug，存量负载里就一条 A 都没有 —— 拿它验 A 的渲染是循环论证。」** ——
   §9 命令 ⑤ 因此分成两半：存量验不崩，快照重建验 cities 分支。
