## 一、产品设计

### 1. 为什么现在做

不做的后果是**问一句话要贴一次日志**。

现在想知道「蔚来还有几个开放岗位」，动作是：我跑 `cli.py jobs --company 蔚来`、
把输出贴进对话、你读。中间那一步是纯人力搬运，而且搬运的是**已经在本地库里的数据**。
更糟的是它带着一个静默失效面：贴进来的输出是某个时刻的快照，
对话往下走几轮之后它已经过期了，但看起来和刚查的一样新。

第二个原因是**判据体检没有入口**。`checkup` 那套东西（投递表单的选择器还认不认
对方页面）只能在 CLI 里跑，而它的结论恰恰是对话里最该问的那类：
「现在能投吗」。代投卡在真登录上（Task #34/#35），但「判据还活着吗」这个问题
不需要登录也该能问。

第三个原因，也是决定**边界画在哪**的那个：这一层最大的风险不是查不到，
是**代投混进来**。`execute()` 提交之后对方系统里那条记录撤不回来，
而闸门的全部价值在「人看过字段清单再点头」。把 `prepare`/`execute` 做成 MCP 工具，
等于把这个闸门交给一个会自己决定要不要调工具的东西。这条不做出决定，
整个 MCP 层就不该存在。

### 2. 用户会看到什么

```
用户在对话里问「蔚来还有几个开放岗位」
  → 模型调 list_jobs(company="蔚来")
  → 屏幕上出现实时条数 + 前 30 条，不用等我跑命令贴日志
```

```
用户问「现在能投字节那个岗位吗」
  → 模型调 check_form_selectors(external_id=..., user_data_dir=...)
  → 屏幕上出现逐条判据的绿/红，以及「哪几条这次证明不了」
```

要能一眼看出**「查不到」和「没有」的区别**，这两件事的处置完全不同：

```
list_sources 里 last_run 为 null   → 这个源一次都没跑过，去 sync
list_sources 里 status = failed    → 跑过但失败了，去查错
```

反面例子（这一层刻意做不到的）：

```
用户在对话里说「帮我投这个岗位」
  → 没有这个工具。模型只能告诉你去命令行跑 jobagent prepare
```

## 二、具体实现

### 4. 数据长什么样，空值怎么办

这一层不写库，所以「空值」问的是**返回值里的空怎么表达**。
关键是每一处空都要能被区分成「没有」还是「查不出来」：

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| `job_family` | tech / product / … | `None`（判不出族） | **是** —— 判不出族的岗位按任何族筛都查不到它，**包括 other**。工具 docstring 明写这一句，否则「按 other 筛」会被当成兜底 |
| `explain_match.state` | `hit` / `miss` | `unknown` + `missing` 列出缺哪几维 | **是** —— 三态，不是布尔。`unknown` 是「信息不全，既没被排除也没被确认」，要人看一眼，不是不合格 |
| `list_sources.last_run` | 最近一次采集 | `None` = **一次都没跑过** | **是** —— 和「跑过但失败了」（`status=failed`）分成两种。前者去 sync，后者去查错 |
| `apply_limit` / `apply_remaining` | 数字 | `None` = 没设上限 | **是** —— 不是 0。判成 0 的话「没设上限」会被读成「配额用完了」 |
| `runs.finished_at` | ISO 时间 | `None` = 这轮没收尾（进程被杀或正在跑） | **是** —— 这条痕迹是故意留的，不是数据缺失 |
| `events.payload` | dict | 解不开时给 `payload_raw` | **是** —— 那是数据问题，不是「这次没有变动」 |
| `list_jobs.notes` | 给人看的提醒 | `[]` | 有内容就该转述（例如 `allow_missing` 没生效） |
| `_intent()` | profile 里的 intent | `{}`（档案不存在） | 匹配退化成「什么都不排除」，不是整个工具挂掉 |

`total` 和 `returned` 是两个数，**`total` 不受 limit 影响**：
混了就会把「返回 30 条」说成「只有 30 条」。钉住它的是
`test_total_is_not_capped_by_limit`。

### 5. 硬约束在哪一行

这一层的全部价值在于**它做不到的事**。所以三条约束都必须是形状上的，
不是 docstring 里的请求。

**① 注册表里没有写动词 —— 主约束。**
`prepare` / `execute` / `submit` / `apply` / `sync` 一个都不注册。
模型调不到不存在的工具。守它的不是「我记得没注册」，是
[test_no_write_verb_is_registered](tests/test_mcp_server.py:105)：
**遍历真实注册表**比对 `WRITE_VERBS`，将来谁手滑加一个 `@mcp.tool()` 的写动词，那条会红。

管的是**头动词**不是子串：

```python
READ_VERBS  = {"list", "get", "explain", "count", "search", "check"}
WRITE_VERBS = {"prepare", "execute", "submit", "apply", "confirm", "discard",
               "sync", "init", "repair", "delete", "update", "insert", "write",
               "create", "remove", "set", "refresh", "add", "mark", "run"}
NOUN_PHRASE_TOOLS = frozenset({"job_changes"})   # 例外列出来，不是把规则放松
```

为什么管头词：`list_sync_runs` 读的是采集历史，名字里有 sync 但它不采集。
按「出现即禁」会把它拦下来，逼人把守卫放松成子串匹配之类 —— **那才是真的把门拆了**。
反过来正面清单漏的方向是「新工具名不在清单里就红」，需要人答一句
「它是只读的吗」，这个方向是安全的。

**② 连接是 `mode=ro`。** `db.connect_readonly()`。这条是兜底，管的是
「我在工具体里写错一句 SQL」——SQLite 自己拒绝，不靠我记得。

**③ 事件种类是白名单，不是黑名单。**

```python
JOB_EVENT_KINDS = frozenset({
    "job_opened", "job_closed", "job_updated", "source_bootstrapped",
})
```

同一张 `events` 表里还躺着代投侧的事件，它们的 payload 里有 `screenshots/` 路径 ——
那些截图是**填好的表单，画面上有姓名手机身份证**。而代投侧的 kind 是
`f"apply_{result.status}"` **拼出来的，grep 数不出全集**：将来多一个状态
就多一个漏出去的 kind。黑名单在这种形状下一定会漏；白名单漏的方向是
「少给一类事件」，看得见。

**④ 只有 `intent` 过边界，而且是白名单挑键。**
`_intent()` 是这一层**唯一**读 `profile.yaml` 的地方。
第一版写的是「只取 `intent` 这一段」，红队验出来**这条当时是假的**：
把它改成 `return match.load_profile()`（整份 profile 往下传），
哨兵测试**照样全绿** —— 因为 `match.classify` 只读它认识的那几个键，
身份数据传进去了但没被用到、于是没出现在返回值里。

也就是说「只有 intent 过边界」靠的是**下游恰好不读**，不是这一层真的挡住了。
下游哪天多读一个键，这条就静默失效，而失效的表现是**身份数据出现在对话里**。
改成 `INTENT_KEYS` 白名单之后，断言放在「交出去那一刻」而不是「下游用不用」。

**⑤ `execute` 留在 CLI，`SESSIONS` 压根不碰。** 这不是「暂时不做」，
见 §8 第一条。

### 6. 判据的粒度

**「这个工具是读还是写」的判据是「头一个词」，不是「名字里有没有」。**
差一级的后果在 §5 ① 写了：按子串判会把 `list_sync_runs` 误伤，
而被误伤一次就会有人去放松守卫。

**「这条判据还活着吗」的判据分两级，不能混。**
`check_form_selectors` 返回的 `all_valid=true` **不等于**「站点没改过文案」：
有些判据只在异常页面上才触发（岗位已关闭、提交成功、重复投递），
拿一个正常岗位页核不动它们。所以返回值里 `unprovable` 单列一栏 ——
这一级是「这次证明不了」，和「验过了是好的」不是同一件事。
转述时要一起说，只说「全部有效」就是把 `unprovable` 那几条洗成了绿的。

**「走不到表单」和「判据坏了」是两级。** 没有登录态时会走到登录墙，
那时 `checkup` 只返回一行 blocker（不是一片假红），`reached_form=false`。
混成一级的后果是每次没登录都满屏红，人开始忽略这个工具。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| `list_jobs.total` | 筛完的**全量**条数 | — | 会（采集在动） |
| `list_jobs.returned` | 实际返回的条数（`min(total, limit)`） | — | 会 |
| `apply_remaining` | 该公司剩余配额 | 该公司 `apply_limit` | 会（投一次少一个） |
| `job_changes` 的 limit | **合并重排后**的最近 N 条 | — | 会 |

三条口径提醒：

- **`total` 不受 `limit` 影响。** 混了就会把「返回 30 条」说成「只有 30 条」。
- **`job_changes` 的 limit 是「最近 N 条」，不是「每种最近 N 条」。**
  各 kind 分别取了 limit 条，合起来必须重新排序再截断 ——
  不重排的话条数对，但**不是最近的那些**。
- **配额按公司算，不按源算。** 同一家公司多行源时用量是合起来的。

### 8. 这次明确不做什么

- **不做代投工具。** `prepare` / `execute` 不注册，`SESSIONS` 这一层不碰。
  理由不是「以后再说」：`execute()` 提交之后对方系统里那条记录**撤不回来**，
  闸门的价值全在「人看过字段清单再点头」。做成工具就是把闸门交给一个
  会自己决定要不要调工具的东西。这是硬边界，不是排期问题。
- **不做投递记录查询。** `applications` 不在这一层。那里有投过哪些岗位、
  截图路径、脱敏后的字段值 —— 都不该为了「方便问一句」而进对话。
  要看去 `jobagent applications`。
- **不做 `health` 巡检工具**（plan 013）。它要开浏览器、跑 7 分钟、
  且会对外发几十个请求。只读层的边界是「不对外」，
  唯一的例外是 `check_form_selectors`，而它 docstring 里带了成本警告
  （`test_the_docstring_warns_about_the_cost` 钉住这句话必须在）。
- **不开 HTTP 传输。** 只走 stdio。一个本地库不需要监听端口，端口就是攻击面。
- **不缓存连接成模块级单例。** sqlite3 连接默认绑在创建它的线程上，
  而 MCP 的工具调用不保证同线程。开连接对本地 SQLite 是微秒级的事。
- **不做写库的「便利工具」**（比如「顺手标一下这条已关闭」）。
  一旦有一个写动词，`WRITE_VERBS` 那条守卫就得开例外，
  而例外一开就没有形状约束了，只剩我记不记得。

弹一个看不见的窗口只是白占资源。这条差异容易被「统一一下默认值」抹掉，
所以有一条专门的测试钉它。

**⑥ 「调起来了」是两件事，方案原先只当一件写。**
§0 原来只有「配到客户端」一行，勾上它就算完。实际是：

```
server 侧：进程能起、握手能过、tools/call 能返回真数据  ← §9 命令 J 已核实
客户端侧：客户端读到配置、拉起这个进程、把工具挂进对话  ← 还差一次重启
```

分成两行写的理由不是仪式感：合成一行的话，命令 J 全绿就会被当成整件事做完了，
而它只排除了「server 不会说话」这一种失败模式。**能自己验的那半不许替另一半签字。**

**而「客户端侧」自己又是两件事，这一层 2026-08-13 才炸出来。**
上面那个方框里写的是「还差一次重启」——**这个诊断是错的**。

当天试了 §2 那句原话「蔚来还有几个开放岗位」，模型**没调 `list_jobs`**，
自己开只读连接查了库。真因不是没重启，是**配错了客户端**：

```
Claude Desktop  ~/Library/Application Support/Claude/claude_desktop_config.json  ← 只配了这个
Claude Code     ~/.claude.json 的 projects.<路径>.mcpServers                      ← 一直是空的
```

`MCP_SETUP.md` 里**两个客户端各有一节**，而只有 Desktop 那节的命令跑过。
Claude Code 那条 `claude mcp add` 写在文档里，从没执行。
所以：**写进文档的命令 ≠ 跑过的命令**，一份文档可以同时是完整的和没用的。

这次失效的形状值得单独记：**答案是对的**（611 行 / 336 个岗位型），
没有报错、没有空结果，只有「工具调用」那一行没出现。
只看答案对不对会判成通了 —— 判据得是「`list_jobs` 有没有被调」，
不是「回答像不像查了库」。

还有一条给我自己的：**「重启一下就好」是个太顺手的解释。**
它听起来总是对的，于是挡住了「配置到底写在哪个文件」这个能一眼查证的问题。

修完顺带定了 scope：`-s local` 而不是 `-s project`。后者写项目根 `.mcp.json`，
两个坑 —— `command` 是绝对路径，钉着我的家目录，而这个仓库是公开的，
别人 clone 下来就是坏的；而且 project scope 首次使用要人工批准
（`⏸ Pending approval`），那个动作我做不了。现在 `claude mcp list` → `✔ Connected`。

**⑦ 「写进了配置文件」不含「App 会读这个文件」。**（2026-08-13 复查，推翻了 §0 一行「已核实」）

⑥ 把「调起来了」拆成 server 侧和客户端侧两件事，但客户端侧那半我又只验了
一半：`Claude Desktop` 那行当时的判据是**「我写进去的那个文件里有这段 JSON」**。
这个判据全绿，而 App 从头到尾没读过那个文件 —— 它是 `3p` 构建，支持目录叫
`Claude-3p/`，我配的是 `Claude/`。

漏的原因是判据的落点选在**我的动作**上（我写了），而不是**目标系统的反应**上
（它读了）。这跟 ⑥ 是同一个错误又犯了一次，只是位置更靠前：⑥ 那次是拿 server
的反应替代客户端的反应，这次是拿自己的动作替代客户端的反应。

三条旁证，当时**其中两条**任何一条都够：

- 进程表里从来没有过 `jobagent.mcp_server`（配上了就该有常驻进程）
- 同目录的 `mcp.log` 是 0 字节
- ~~`main.log` 里 `LocalMcpServerManager` 每次 `Closing all (0 servers)`~~ ——
  **这条当时是对的，但它作为旁证不成立**，理由见 ⑨：`Closing all` 只在关闭路径上
  发，配置生效的机器上旧进程退出时**照样**报 0。它当时读对了纯属巧合。

而**「配置文件里有这段 JSON」和「配置文件没人读」在文件内容上完全一样**，
所以查文件内容永远查不出这个。要问的是进程：

```bash
lsof -p "$(ps ax -o pid=,comm= | awk '/\/Claude\.app\/Contents\/MacOS\/Claude$/{print $1; exit}')" | grep -o 'Application Support/Claude[^/]*' | sort -u
```

84 个句柄全在 `Claude-3p`，`Claude/` 零。`docs/MCP_SETUP.md` 已改成先用这条
定位目录再改配置，而不是写死一个路径。

（这条命令原先用 `pgrep -x Claude`，**在这台机器上返回空** —— 而 `lsof -p ""`
会打印所有进程的句柄，于是结论变成随机的。`ps ax -o comm=` 看得见这个进程。
判据：把这条命令真敲一遍，而不是只写进文档，见「文档里有 ≠ 跑过了」。）

顺带一个反例，防止过度推广：Claude Code 那半的判据（`claude mcp list` →
`✔ Connected`）是**目标系统自己的回答**，所以它当时是对的，今天复查照样对。
两行写在一起、当时都标「已核实」，但一行的判据能活一行不能 —— 光看状态字
分不出来，得看判据落在谁身上。

**⑧ ⑦ 后面还藏着第二层阻塞，而它的表现和 ⑦ 一模一样。**（2026-08-13，方案 021）

⑦ 查完之后，下一步很自然：往 `Claude-3p/claude_desktop_config.json` 里补
`mcpServers`。**那一步当时一定会失败**，而且失败的样子和 ⑦ 完全相同 ——
「配了但对话里看不见工具」。

真因在另一层：这个包从来没装进 venv（`pyproject.toml` 缺 `[build-system]`，
uv 把它当虚拟项目，只装依赖不装它自己）。`-m jobagent.mcp_server` 能被找到，
**只因为 Claude Code 启 server 时 cwd 恰好是项目目录**。Desktop 启 stdio server
的 cwd 不是仓库根，于是 `ModuleNotFoundError`。

判据是探针带 cwd 参数跑两遍（原先探针里硬钉着 `cwd=ROOT`，所以这个问题
**问不出来** —— 探针自己先 cd 回仓库了，然后报「通过」）：

| cwd | 021 之前 | 021 之后 |
|---|---|---|
| 仓库根 | 6 工具齐、`total=300` | 同 |
| `/tmp` | `ModuleNotFoundError` | 6 工具齐、`total=300` |

这条的教训不是「再多查一层」，是**两个不同的原因会产出同一个表现，而我已经
为这个表现写好了一个解释**。⑦ 刚查完，「配置目录不对」这个解释正热着；
如果先动配置再看结果，我大概会归因成「这个构建不支持用户配的 server」，
写进方案，然后它成为一条没人再验的错误结论 —— 因为它「解释得通」。

所以 021 §8 明确写了「这次不去验 Desktop 对话侧支不支持」：在包没装进环境
之前验等于编，那条路一定失败，而失败表现和「不支持」区分不开。

**⑨ 三个数里有一个瞄在了关闭路径上，于是它答不了我在问的那个问题。**
（2026-08-13 重启后）

写配置的时候我留了一条三合一判据：重启后 ①`main.log` 里出现 `(1 servers)`
或非 0、②`mcp.log` 不再是 0 字节、③进程表里有 server，**三个里只变一个都不算**。
重启后实测：

| 数 | 基线 | 重启后 | |
|---|---|---|---|
| `mcp.log` 字节 | 0 | **1706**，一次完整握手、零 error | ✓ |
| `jobagent.mcp_server` 进程 | 无 | **两对**（7110 @18:29:52、7193 @18:29:56） | ✓ |
| `Closing all (0 servers)` 次数 | 36 | **39，还是报 0** | ✗？ |

第三个数没按我预期变，而按我自己写的「只变一个都不算」，这该判成没生效。
但它是**判据的缺陷**，不是系统的：`Closing all` 只在**关闭路径**上发，
报的是「正在死掉的这个进程配了几个 server」。我拿一个只在退出时才有意义的量，
去问「启动后加载了吗」—— 取值域上它就答不了。

三条新增行的时间戳是 **18:29:47**，比 `mcp.log` 的握手（18:29:52）**早 5 秒**：
那是**旧进程**在退出，报的是旧进程自己的数（0，正确 —— 那个进程启动时配置还没写）。
也就是说这三行恰恰是「重启真的发生了」的证据，而我差点把它读成反面证据。

还有一层，是测量前记下的那条 caveat 救的：`mcp.log` 里 `Initializing server`

对照「对照组的绿和红各有两种含义」那条：③ 变红时有两种读法 —— 真没生效，
或我选错了观测点。我在动判据之前先去查了时间戳和子系统归属，是这一步分开了两者。
**顺序很重要**：如果先改判据再解释，我会得到一条「看起来自洽」的记录。

### 12. 实现中踩到的坑

- **现象**：把 `_intent()` 换成整份 profile 往下传，身份哨兵测试全绿。
  **原因**：断言放在「返回值里有没有出现哨兵串」，而下游只读它认识的键，
  所以传过去的身份数据没被用到、也就没出现在输出里。
  **修法**：`INTENT_KEYS` 白名单，在交出去那一刻挑键。
  **钉住它的测试**：`test_intent_helper_hands_over_only_whitelisted_keys`
  + `test_an_unknown_intent_key_is_not_handed_over`

- **现象**：`job_changes(limit=10)` 返回 10 条，但不是最近的 10 条。
  **原因**：四个 kind 各取 10 条再拼起来，没重排就截断。
  **修法**：合并后按 `(occurred_at, id)` 倒排再切。
  **钉住它的测试**：`test_limit_means_the_most_recent_overall`

- **现象**：工具名守卫把 `list_sync_runs` 判成写工具。
  **原因**：按「名字里出现写动词」判，`sync` 是子串。
  **修法**：改判**头动词**，配 `READ_VERBS` 正面清单。
  **钉住它的测试**：`test_the_verb_lists_do_not_overlap`
  + `test_the_guard_would_catch_a_write_tool`

- **现象**：`printf '...' | .venv/bin/python -m jobagent.mcp_server` 里
  `initialize` 有输出，`tools/call` 一个字都没有 —— 看起来就是工具坏了。
  **原因**：管道到 EOF 之后 server 开始关闭，工具还没跑完就没人写 stdout。
  坏的是**探针**，不是被探的东西。
  **修法**：subprocess 保持 stdin 打开，读到对应 `id` 再收（§9 命令 J）。
  **为什么值得记**：这个缺陷偏向报「坏」。当时收手的话，结论会是
  「MCP 的 `tools/call` 不通」，方向完全反了 —— 而这个结论看起来是有证据的。

- **现象**：`all_valid=true` 被读成「站点没改过文案」。
  **原因**：有些判据只在异常页面才触发（岗位已关闭、提交成功、重复投递），
  拿正常岗位页核不动它们，但它们照样计入 `all_valid`。
  **修法**：`unprovable` 单列一栏，投递器在自己那行说明里写「不代表」。
  **钉住它的测试**：`test_unprovable_checks_are_surfaced`

- **现象**：`claude mcp get job-agent` 报 `error: unknown option '-G'`，
  于是我判「`get` 本身坏了」，并且以为和 `.mcp.json` 里路径的写法有关。
  **原因**：报错跟 `claude` 无关。下一条命令里压根没调 `claude`，
  只有 `cat` 和 `grep`，照样报 `-G` —— 是 harness 的 shell snapshot
  把 `grep` 换成了一个包 `ugrep -G` 的 shell 函数，而这里 `ugrep` 起不来。
  **修法**：`command grep` 绕开函数。
  **为什么值得记**：错误是**沿着管道串到别人头上**的 ——
  `grep` 的失败被读成了「`claude mcp get` 的失败」，因为我看的是整条命令的输出。
  真正把它暴露出来的是「这条命令里没有 `claude`，为什么还报同样的错」。
  **排查工具自己坏掉时，症状会挂在被排查对象身上。**

### 13. 如果重来，方案里该提前写上哪句话

- **「这个功能的入口配好了吗」要写进 §2。** 这次代码全绿、
  `mcpServers` 是空的 —— 功能做完了一次没用上，这个状态持续了一整天。
  §2 问「用户会看到什么」，而「用户看不到，因为客户端不知道它存在」
  是这一栏该拦住的事。
- **§0 里「接上了」这类步骤要按「谁能验」拆行。** 一头是我，一头是用户，
  就该是两行。写成一行的话，我能验的那半绿了就会顺手把整行勾掉 ——
  而那半只排除了一种失败模式。见 §11 ⑥。
- **「配到客户端」要写成「配到**哪些**客户端」，并且一个客户端一行。**
  这次 `MCP_SETUP.md` 里两个客户端各有一节，文档是完整的，
  但只有一节的命令被执行过，而 §0 那一行把两者一起勾了。
  **写进文档的命令 ≠ 跑过的命令** —— §0 的核实列该填「执行了哪条命令、
  看到什么输出」，不是「文档里有」。
- **「功能通了」的判据要落在「工具有没有被调用」，不能落在「回答对不对」。**
  这次答案完全正确（611 行 / 336 个岗位型），而工具压根没起来 ——
  模型自己开只读连接查了库。没有报错、没有空结果，
  失效只表现为界面上少了一行工具调用。**能被正确答案掩盖的失效，
  必须有一条不看答案的判据。**
- **别把「重启一下就好」当诊断。** 它听起来永远成立，
  于是挡住了「配置写在哪个文件」这种一眼能查证的问题。
  这次真因是配错客户端，重启一万次也不会好。
- **验证脚本的缺陷和被验对象的故障长得一样，而且常常偏向报「坏」。**
  管道版探针让 `tools/call` 看起来完全不通。判「不通」之前先换一种驱动方式
  再问一次 —— 这条和 memory 里「subagent 的结论要打折看」是同一个形状：
  **否定结论比肯定结论更需要复验**，因为它会让人停手。
- **手写的验证脚本也要被改坏一遍，它和测试同权。** §9 命令 J 是那行
  「已核实」的全部依据，所以它自己挨了三次改坏。第三次（删掉
  `notifications/initialized`）**照样绿**，逼出一个我本来写错的结论：
  那一步不是握手必需项。**如果只验绿，文档里就会留下一句「三步握手都通了」，
  而其中一步根本没在起作用。**
- **「只有 X 过边界」这句话，断言要放在交出去那一刻。** 放在下游的
  「有没有被用到」上，等于让约束靠一个巧合成立 ——
  而下游多读一个键就静默失效，失效的表现是身份数据出现在对话里。
- **守卫被自己的合理用例误伤时，别放松守卫，去改判据的粒度。**
  `list_sync_runs` 那次如果按「加个例外」处理，
  下一个 `sync_xxx` 就会顺着例外进来。
- **数不出全集的东西只能用白名单。** `f"apply_{status}"` 拼出来的 kind
  grep 不出来，黑名单必漏。这条已经进了模板级的教训
  （和 plan 013 的 `EXPECTED_SHAPE` 是同一条）。
- **「全部有效」之前先问一句：这次能证明的和不能证明的分开了吗。**
  `unprovable` 那一栏不列出来，一个绿灯就把「没验过」洗成了「验过是好的」。
