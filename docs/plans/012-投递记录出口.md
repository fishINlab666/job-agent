## 一、产品设计

### 1. 为什么现在做

**不做的后果：代投这条链路已经能跑，但跑完看不见。**

库里现在有 14 条投递记录，全是 `blocked`（plan 010 那轮 prepare 留下的）。
这 14 条包含每家公司的**拦截原因**和**截图路径**——也就是「为什么投不出去」
的全部证据。现在没有任何命令能把它们打出来：`cli status` 只读 `sources` 和
`runs`（`cli.py:514-523`），`cli jobs` 只读 `jobs`。想看投递记录只能开 sqlite3
手写 SQL。

具体会发生什么：

- **plan 010 / 011 都卡在「需要你登录一次」**，而「哪几家、卡在哪一步、
  截图在哪」这三个问题的答案就在这张表里，用户拿不到。
- 等真的投出去了，**没有任何地方能回答「投了多少、成了多少」**。
  这不是锦上添花——代投是本项目唯一会产生不可撤销后果的动作，
  它的历史记录必须可查，否则出了问题无法复盘。
- `screenshot_path` 存了提交那一刻的存证，**存了但没人看得见**，
  等于白存。

### 2. 用户会看到什么

```
用户敲 cli applications
  → 系统读 applications 表，按时间倒序
  → 屏幕上出现一张表：公司 / 岗位 / 状态 / 时间 / 卡在哪
    状态用颜色分档：submitted 绿、blocked 黄、failed 红、prefilled 蓝

用户敲 cli applications --funnel
  → 系统按状态分组计数，再按拦截原因二次分组
  → 屏幕上出现漏斗（2026-08-10 实际输出）：
      投递漏斗（14 次尝试，7 个岗位）   ← 次数和岗位数分开报
      被拦        14
      填好待确认   0
      已提交       0
      失败         0
      无需投递     0
      已放弃       0

      被拦的 14 条卡在哪：
        10 次 / 5 个岗位  要登录（手机号+验证码，只能你本人做）（最近 08-10 00:42）
        4 次 / 3 个岗位   找不到投递按钮（页面结构变了）（最近 08-09 23:13）

      登录只能你本人做一次，且必须带 --user-data-dir，否则登录态不落盘

    ↑ 方案初稿这里写的是「卡在登录门 14 / 全都停在这里」，**那是错的**：
      实际是两个原因，而且「找不到投递按钮」那 4 条更早、已经修掉了。
      每档带上「最近一次」的时间，就是为了让「哪个原因还活着」看得出来。
      详见 §7 的更正。

用户敲 cli applications --status blocked
  → 只看被拦的，附每条的拦截原因和截图路径
```

不懂技术的人读完应该能说出：**「所以我敲那个命令，屏幕上会告诉我投了几个、
卡在哪、截图在哪。」**

### 3. 哪些是已核实的，哪些是我猜的

| 事实 | 怎么核实的 |
|---|---|

| `prefilled` 是中间态，由 `finalize_application()` 改成终态 | `db.py:266-284`，`UPDATE ... SET status=?` |

| 14 条 `blocked` 的 `error` 文案足够自解释 | 若文案太长会挤爆表格 | 实测最长那条：`需要登录 商汤科技 的招聘账号。登录是手机号+验证码，只能你自己做：用 --no…` 已被截断存储，**表格里要再截一次**并给全文出口 |

## 二、具体实现

### 4. 数据长什么样，空值怎么办

**这张表几乎每一列都可以是 NULL**，因为它要覆盖从「刚填好」到「投出去了」
到「压根没走通」三种命运。

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| `status` | 7 个取值之一 | **不可能为空**（`NOT NULL`）| 是 —— 唯一的非空业务列，可以直接分组 |
| `submitted_at` | 提交时刻 | `None` = **还没提交**，不是「提交失败」 | **是，且这是关键**：`blocked` / `prefilled` 都是 `None`。按它排序会把 14 条全排在一起，所以**排序用 `created_at`** |
| `error` | 拦截原因 / 报错 | `None` = 没出错 | 是 —— `blocked` 必有 `error`，`submitted` 必无 |
| `screenshot_path` | 存证路径 | `None` = 没截到 | 是 —— 展示成 `-`，**不许显示成 `None`** |
| `filled_fields` | JSON 数组 | `None`（不是 `[]`）| **要小心**：`json.loads(None)` 会抛。统一走 `json.loads(x or "[]")`，和 `cli.py:265` 处理 `cities` 同一套写法 |
| `skipped_fields` | JSON 数组 | 同上 | 同上 |
| `confirm_token` | prepare 与 execute 的关联键 | `blocked` 行是**显式 NULL** | 是 —— 空串会撞唯一索引（`db.py:251`），展示时不管，但**不许把 NULL 渲染成空串再写回** |
| `note` | 人工备注 / 迁移来源 | `None` | 是 |
| `job_id` → `jobs.title` | 岗位标题 | **连不上时是 `None`** | **这是本方案最重要的一条**：见下 |

> **孤儿行不许静默消失。** 取岗位标题要 `JOIN jobs`，而 `job_id` 指向的
> `jobs` 行**可能已经不在了**（schema 自己写了 `external_id` 的用途是
> 「jobs 行被重建也能追溯」）。如果用 `INNER JOIN`，孤儿行会从结果里
> 悄悄消失——**投递记录消失比岗位消失严重得多**，它是不可撤销动作的唯一凭证。
> 所以必须 `LEFT JOIN`，标题取不到时退化成 `external_id` 并标记，
> 而不是把整行丢掉。

**2026-08-10 更正：上面这段的结论对，但理由错了。**
实测 `schema.sql:104` 是 `job_id INTEGER NOT NULL REFERENCES jobs(id)`，
而 `db.py:44` 有 `PRAGMA foreign_keys=ON`，FK 是默认的 `NO ACTION`，
且全仓没有任何 `DELETE FROM jobs` 的代码路径
（`grep -rn "DELETE FROM jobs" jobagent/` → 无）。所以：

- **孤儿行在正常运行路径下产生不出来。** 删 `jobs` 行会直接被 FK 拒掉，
  而不是留下一条孤儿投递记录。写方案时我把 `external_id` 那句注释
  （「jobs 行被重建也能追溯」）读成了「孤儿行是常态」——**注释说的是
  这一列的用途，不是说约束不存在**。这和 011 那次「窄命题被读宽」是同一个动作。
- **`LEFT JOIN` 仍然是对的**，理由换成：唯一能产生孤儿的路径是
  **人工修库 / 从备份恢复时 `foreign_keys=OFF` 把 `jobs` 重建一遍**，
  而那恰好是最需要这批记录还在的时刻。`LEFT JOIN` 的成本是零，
  `INNER JOIN` 的代价是不可恢复的凭证丢失——不对称，所以选防御的那边。
- **测试要造孤儿就必须显式 `PRAGMA foreign_keys=OFF`**
  （`tests/test_cli.py` 的 `app_row(orphan=True)`）。这不是测试作弊，
  它模拟的就是上面那条唯一路径；而「造孤儿需要先关 FK」这件事本身
  就是「正常路径下没有孤儿」的证明。
>
> 这就是本项目的头号 bug 原型在这张表上的样子：
> 「没有值」（岗位行没了）被当成「不合格」（这条投递不存在）。

### 5. 硬约束在哪一行

**本方案是只读的，不写库、不碰网络**，所以不需要新的硬约束。
但它必须**不破坏**已有的那条：

- `applications` 上的唯一索引条件是 `WHERE confirm_token IS NOT NULL`。
  本命令只 `SELECT`，不会影响它。
- **本命令不提供任何修改状态的开关**（不做 `--mark-abandoned` 之类）。
  理由见 §8：状态变更必须走 `apply` 的两阶段闸门，
  从一个「查看」命令里改终态，等于给闸门开后门。

### 6. 判据的粒度

这次要「认出」的是**状态属于哪一档**，判据是**状态字符串级**的精确匹配，
不是前缀、不是模糊：

| 档 | 成员 | 差一级会怎样 |
|---|---|---|
| 已提交 | `submitted` | —— |
| 在途 | `prefilled` | 把它算进「失败」会虚报失败数；它其实是「等用户确认」 |
| 被拦 | `blocked` | —— |
| 失败 | `failed` | —— |
| 无需投 | `duplicate` / `closed` | 算进「失败」会虚报：`duplicate` 是「已经投过了」，`closed` 是「岗位关了」，两个都不是错误 |
| 放弃 | `abandoned` | —— |

**差一级的具体后果**：把 `duplicate` / `closed` 混进失败档，
会让「代投不好用」这个结论凭空多出两类本来正常的记录。
所以 `--funnel` 的分档表要**写死这 7 个值的归属**，
而且**遇到表里出现第 8 个值时要显式报出来**，不许静默归进「其他」——
静默归类就是下一次口径事故。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| 尝试投递 | `applications` 全表行数 | —— | 会，只增 |
| **覆盖岗位数** | `COUNT(DISTINCT external_id)` | —— | 会，只增 |
| 卡在登录门 | `status='blocked'` 且 `error` 含登录字样 | 尝试投递 | 会 |
| 已提交 | `status='submitted'` | 尝试投递 | 会 |
| **不报「成功率」** | —— | —— | —— |

**尝试次数和覆盖岗位数必须分开报。** 实测 **14 次尝试只覆盖 7 个岗位**：
腾讯 `1281715884913959936` 一个岗位重试了 **7 次**（改选择器、调超时那轮），
`1277774706287944716` 试了 2 次。把 14 读成「14 个岗位试过了」是**翻倍高估覆盖面**。
按公司：腾讯 10 次 / 3 个岗位，飞书四家各 1 次 / 1 个岗位。

**为什么不报成功率。** 今天是 14 尝试 / 0 提交，成功率 = **0%**。
这个数字字面正确，但它会被读成「代投不管用」——而真相是
**14 条全部停在投递前，一条都没走到表单**，也就是说
**代投的提交逻辑一次都还没被执行过**，谈不上成功或失败。
0% 的分母里装的全是「还没试到那一步」的记录。

> **2026-08-10 更正：**上面原本写的是「14 条全部停在**登录门**」，这是错的。
> 实测 `blocked` 分两类：**10 条登录门**（含 4 条「等待登录超时」，那也是登录门）
> + **4 条「未找到申请按钮，页面结构可能已变」**。后者根本没走到登录那一步。
>
> 而且这 4 条**比同一岗位的登录记录更早**（最近 `08-09 23:13`，
> 登录门那档最近 `08-10 00:42`）：同一个 `external_id`
> 先报「找不到按钮」（id 4）、后报「需要登录」（id 5），
> 说明选择器问题当时已经修掉了，后面那次跑得更远。
> **所以这两档不是并列的两个现存问题，其中一个是历史。**
> 光报一个「被拦 14」会把已修好的问题算进现存卡点，
> 所以 `--funnel` 里按原因分组、**每档带上「最近一次」的时间**。

这正是 `kb/job-fields.md` 那条「三态不是两态」在投递侧的样子：
`blocked` 是**信息不全**（不知道能不能成），不是**不命中**（试过了没成）。
把它折进成功率的分母，等于把「没试」洗成「失败」。

所以 `--funnel` 报**分层条数**，不报单一比率。真到了有 `submitted`
的那天再决定比率怎么定义，那时分母才有意义。

### 8. 这次明确不做什么

- **不做任何状态修改开关**（`--mark-abandoned` / `--retry`），因为状态变更
  必须走 `apply` 的 prepare/execute 两阶段闸门。从查看命令里改终态等于开后门，
  而这条闸门是 001 定的硬约束。

- **不做 `--export csv/json`**，因为当前唯一的消费者是终端里的人。
  真要导出应该等有第二个消费者（比如给 digest 用），
  现在做等于猜一个还不存在的下游要什么格式。

- **不动 `applications` 的 schema**，一列都不加。本方案是给已有数据开个出口，
  不是改数据模型。真发现缺列该单独立方案。

- **不做「重投」**（拿 `filled_fields` 回放一次 prepare）。它需要处理
  「岗位已关」「表单变了」「token 过期」三种情况，是一个独立方案的体量。
  `filled_fields` 存下来就是为了将来能做，但不是这次。

- **不给 `blocked` 的截图做自动打开**（`open screenshots/...`）。
  打印路径就够了，自动开图会在无 GUI 的环境里炸，而且属于外部副作用。

## 三、怎么验

### 9. 验证命令

命令 A —— 全表读出来，14 条一条不少：

```bash
uv run python -m jobagent.cli applications
```

期望（2026-08-10 实测）：标题行显示 `投递记录 14 条`，14 行全部 `被拦` 且带黄色，
「卡在哪」列 10 行是登录文案、4 行是 `未找到申请按钮，页面结构可能已变`，
末尾列出 14 条的截图路径。加 `--status blocked` 时标题要变成
`投递记录 14 条（筛选：status=blocked）`——**筛过的表必须在标题里说自己筛过**，
否则截图会被当成全表读。

命令 B —— 漏斗：

```bash
uv run python -m jobagent.cli applications --funnel
```

期望（2026-08-10 实测）：标题 `投递漏斗（14 次尝试，7 个岗位）`，
分档 `被拦 14` / `填好待确认 0` / `已提交 0` / `失败 0` / `无需投递 0` / `已放弃 0`，
下面按原因分组打出 `10 次 / 5 个岗位  要登录…（最近 08-10 00:42）` 和
`4 次 / 3 个岗位  找不到投递按钮…（最近 08-09 23:13）`，
并且**不出现任何百分比**（`grep -c "%"` → 0）。

命令 C —— 按状态过滤，且不认识的状态要报错而不是给空表：

```bash

uv run python -m jobagent.cli applications --status submitted # 0 条，但要明确说「没有」
uv run python -m jobagent.cli applications --status nonsense  # 应报错并列出可选值
```

命令 D —— 全量测试：

```bash

```

期望：比落地前的 **450** 大，且全绿。

| `--funnel` 不输出百分比 | `test_funnel_has_no_percentage` | 「顺手加个成功率」时会红 |
| 被拦原因要分开报，不混成一个数 | `test_funnel_groups_blocked_reasons` | 只报「被拦 14」时会红 |
| 尝试次数和岗位数分开报 | `test_funnel_separates_attempts_from_jobs` | 只报 14 不报 7 时会红 |
| 这条命令不许有改状态的开关 | `test_no_status_mutation_flags` | 后人加 `--mark-abandoned` 时会红 |
| 筛过的表要在标题里写明筛了什么 | `test_filtered_title_says_it_is_filtered` | 标题不带筛选条件时会红 |
| 空表要明说「没有」 | `test_empty_says_so` | 打一张空表框时会红 |

**这三条「做一半会红」的用例，都用变异测试验过它真会红**（不是写完就信）：

| 变异 | 结果 |
|---|---|
| `LEFT JOIN` → `JOIN` | `test_orphan_application_still_listed` + `test_orphan_shows_external_id` 转红 |
| `if unknown:` → `if False:`（等价于删掉未知状态告警）| `test_unknown_status_is_surfaced` 转红 |
| 把 `duplicate`/`closed` 并进失败档 | `test_funnel_buckets_all_statuses` 转红 |

变异后都还原并复跑到全绿。**没验过的守卫不算守卫** —— 这三条恰好是
「代码写对了看不出差别、写错了也全绿」的那种，不做变异测试就等于没写。

### 11. 方案和实现差在哪

### 12. 实现中踩到的坑

- **方案里两处事实是错的，而且都是我自己没去查就写下的。** ①「14 条全部
  停在登录门」——真去 `SELECT` 一下就知道有 4 条是「未找到申请按钮」。
  ②「`job_id` 没有 FK」——`schema.sql:104` 明写着 `REFERENCES jobs(id)`。
  两处都是**在方案的 §3「已核实 vs 我猜的」里被归进了「已核实」**，
  但实际只核实了「有 14 条」和「两种连法条数一致」，没核实原因构成和约束。
  §3 那张表的价值取决于填表时的诚实度，填错了它比不填更危险。

- **孤儿行插不进去，测试直接挂在 `FOREIGN KEY constraint failed`。**
  这个失败是好消息：它证明了正常路径下没有孤儿。但它也意味着
  「造一条孤儿行」这个测试动作必须显式 `PRAGMA foreign_keys=OFF`，
  而那句 `PRAGMA` 本身就是这条测试在模拟什么的说明。

- **`PRAGMA foreign_keys=OFF` 会泄漏到同一连接的后续用例。**
  fixture 是整个连接复用的，关掉不开回去，后面的用例就在没有 FK 的库上跑，
  于是「别的地方 FK 失效了」这类问题永远测不出来。插完立刻开回 `ON`。

- **测试 helper 默认造孤儿，把 13 条用例全变成了孤儿测试。**
  第一版 `app_row(job_id=None)` 表示孤儿，而 `job_id` 又是默认参数，
  结果每条用例都在测孤儿路径。改成 `orphan=True` 显式开启，
  默认路径顺手建一条真的 `jobs` 行。**默认值应该是正常形状，不是特例形状。**

- **同一个 `ext_id` 插第二条时撞 `UNIQUE(source_key, external_id)`。**
  而「一个岗位被投了多次」恰好是真实形状（腾讯那个岗位 7 次），
  所以 helper 要先查再插，不是无条件插。

- **`test_no_status_mutation_flags` 被自己的 docstring 骗了。**
  它 `grep` `--help` 输出里有没有 `--mark`，而命令的 docstring 里就写着
  「`--mark-abandoned` 之类都没有」——`--help` 会把 docstring 打出来，
  于是这条用例在「代码完全正确」的情况下报红。改成检查 typer 真正注册的
  参数名。**扫渲染后的文本来判断结构，会被解释性文字骗到。**

- **rich 的 `max_width` 不等于「一行内截断」。** 它先按空格断词再套宽度，
  所以中文长句照样会撑成三四行。要 `no_wrap=True` + `overflow="ellipsis"`
  才是截断。另外中日韩字符是双宽，按字数截断压不住列宽。

- **窄终端下 rich 按比例压所有列，`#` 和 `状态` 会被压成 `…`。**
  管道输出时 rich 认 80 列，于是这两列（照着 `#` 找截图、照着状态判断
  该不该重投的定位信息）先没了。给它们 `min_width`，宁可挤岗位名。

### 13. 如果重来，方案里该提前写上哪句话

**「§3 填『已核实』之前，把那句话本身当成 SQL 跑一遍。」**

这次两处错都不是推理错，是**没查就填了「已核实」**。
「14 条全 `blocked`」我查了，于是顺手把「14 条全部卡在登录门」也写成了已核实——
可后半句要的是 `SELECT error, COUNT(*) ... GROUP BY`，我一次都没跑。
「`external_id` 用于 jobs 行被重建也能追溯」这句注释我读了，
于是把「所以孤儿行是常态」也写成了已核实——可那要的是看一眼 `schema.sql:104`。

**两次都是：核实了一句窄的，把从它外推出来的宽的也标成了已核实。**
这和 011 那次「窄命题被读宽」是同一个动作，只是这回外推的人是我自己、
而且发生在方案阶段而不是读方案阶段。所以 §3 的表头该改成一句要求：
**「这一行的『已核实』，对应的是哪条能复制粘贴去跑的命令？填不出来就归『我猜的』。」**

配套的一句：**「拦截原因不是一个数，是一个分布，而且分布里有历史。」**
14 条 `blocked` 看着是一个卡点，其实是两个原因、其中一个已经修好了。
任何「卡在哪」的汇总都要**带上每档最近一次的时间**，
否则读的人会把已经解决的问题当成现存障碍继续投入。
