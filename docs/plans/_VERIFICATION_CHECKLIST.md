## 6. 与现有实现的一致性

| 检查项 | 结果 | 问题描述 |
|--------|------|----------|
| 方案引用的代码位置是否存在 | ☐ 通过 ☐ 失败 | |
| 方案描述的行为和当前代码一致 | ☐ 通过 ☐ 失败 | |
| 是否与 SPEC.md 冲突 | ☐ 无冲突 ☐ 有冲突 | |
| 是否与其他 plan 的 §11/§12 冲突 | ☐ 无冲突 ☐ 有冲突 | |
| **字段从生产端跟到消费端，键名/类型/顺序口径一致** | ☐ 通过 ☐ 失败 | |
| **存量数据用的是哪套口径**（改哪一端不会造成孤儿数据） | ☐ 查过 ☐ 没查 | |

**「这段代码够不到，所以不用管」不算验完。** 够不到的原因本身可能是另一个 bug，
而一旦上游修好，这段死代码就活了 —— 它带的错会跟着一起活过来。
判定某段是死代码时，要顺手回答两个问题：

1. 它为什么够不到？（是有意的门槛，还是上游漏了？）
2. 如果上游修好了，它是对的吗？

反例（2026-08-07 三方验证漏掉的那条）：三方都认定 `cli.py:248-249` 是死代码 ——
判断没错，但没人回答第 2 问。那两行用的键名是错的，而且隔壁 `:243`/`:245`
用着同一套错键、且**够得到**。库里 106 条事件有 88 条走那条路。

## 7. 测试覆盖

| 检查项 | 结果 | 问题描述 |
|--------|------|----------|
| 方案 §10 列出的测试点覆盖上述边界 | ☐ 是 ☐ 否 | |
| 是否有「认不出就兜底」这类违反 SPEC §6 的逻辑 | ☐ 无 ☐ 有 | |
| 失败路径是否有测试（不只测 happy path） | ☐ 是 ☐ 否 | |
| **跨模块的契约，测试是否两端都在场**（不是手搓一个负载喂给单边） | ☐ 是 ☐ 否 | |
| **本次要改的代码，现在有没有真实覆盖**（`print` 不算断言） | ☐ 查过 ☐ 没查 | |

手搓负载测出来的是「我以为对方写什么」。契约类的 bug 恰恰出在两端各有各的以为，
所以这种测试必须让真实生产端造数据、真实消费端读数据。

## 8. 报告/方案没提、但应该查的

前七项验的是「方案说的对不对」。这一项验的是「方案漏了什么」——
两件事，得分开做，不然就会出现七项全过、隔壁几行还躺着更严重的问题。

| 检查项 | 结果 | 问题描述 |
|--------|------|----------|
| 问题所在函数的**上下游各读一遍**，不只读被点名的那几行 | ☐ 做了 ☐ 没做 | |
| 同类代码的其他实例（一个适配器有的坑，另一个是否也有） | ☐ 查了 ☐ 没查 | |
| 被点名的问题**是不是最严重的那个**（同一条路径上还有没有更糟的） | ☐ 判过 ☐ 没判 | |
| 关键结论有没有**跑一遍**验过（不是读代码推出来的） | ☐ 跑了 ☐ 只读了 | |
| 涉及存量数据的判断，有没有**查库**看真实规模 | ☐ 查了 ☐ 没查 | |

**三方结论完全一致时，先别当成「验充分了」。** 如果三方读的是同一份报告、
按同一个清单核，高一致度更可能说明大家都在验报告、而不是都在验代码。
出现七项全过零分歧时，至少一方应该放下报告，只按本节这五条重走一遍。
