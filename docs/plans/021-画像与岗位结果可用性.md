## 一、产品设计

### 1. 为什么现在做

当前发现闭环已经能自动采集岗位，但用户还会遇到四个断点：画像文件缺失、
筛选列表全空或 intent 字段拼错时，系统都可能把所有岗位当成命中；示例画像与真实读取格式
曾经不一致；AI 工具的未知参数已能拒绝，但负数数量和非法日期仍会被包装成正常答案；
命令行结果原先不展示可用于下一步操作的来源和岗位编号。继续观察只能证明“抓到了”，
不能证明“用户能正确筛选并继续操作”。

### 2. 用户会看到什么

```text
复制并填写统一格式的画像 → 用 --matched 查看 → 缺失、全空或拼错时看到明确错误
AI 传入不存在或值不合法的参数 → 工具明确报错，不再返回看似正常的结果
查看岗位/摘要/投递记录 → 同时看到来源和岗位编号 → 能准确定位岗位
```

### 3. 哪些是已核实的，哪些是我猜的

| 事实 | 怎么核实的 |
|---|---|
| 缺画像时 MCP `matched=True` 返回全部岗位且无提醒 | 当前主线临时库复现 |
| `grad_year` 等未知 MCP 参数被静默忽略 | 当前主线真实 MCP Client 复现 |
| `profile.yaml.example` 是扁平格式，README 是嵌套格式 | 逐字读取两文件 |
| CLI `jobs`/`digest` 未展示来源和岗位编号 | 逐字读取 `jobagent/cli.py` |
| 空列表 intent 与仅含拼错 key 的 intent 都被判为 `hit` | 直接调用 `match.classify()` 复现 |
| `limit=-1` 与 `since="not-an-iso-date"` 未被 MCP 拒绝 | 真实 MCP Client 调用复现 |
| MCP 画像错误包含本机绝对路径 | 读取 `list_jobs` / `explain_match` 错误翻译分支 |

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|
| 显示 `source_key + external_id` 足以定位下一步操作 | 用户仍无法准确执行 apply | CLI 输出测试与 README 命令示例一起验证 |
| MCP 中间件能在工具函数运行前拒绝未知参数 | 仍可能静默执行 | 使用真实 MCP Client 做反向测试 |

## 二、具体实现

### 4. 数据长什么样，空值怎么办

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| 画像 intent | 统一解析嵌套或旧扁平格式，只接受六个已声明 key | 缺文件、全空 intent、拼错 key 明确失败 | 是 |
| source_key | 展示并传给 `apply --source` | 仅历史孤儿记录按原值展示 | 是 |
| external_id | 展示原始岗位编号 | 不伪造编号 | 是 |
| MCP 参数 | 只接受工具 schema 中列出的键；`limit` 必须为正整数，`since` 必须为含时区 ISO 时间 | 未知键或非法值返回错误 | 是 |

### 5. 硬约束在哪一行

- MCP 未知参数在请求进入工具函数前由严格参数中间件拒绝，不依赖提示词。
- 工具参数的值在 MCP 工具入口统一校验，不把负数或错误日期交给 SQLite 解释。
- 匹配命令只通过单一 `load_intent()` 入口读取求职意图；缺文件、全空列表或未知 key 不再退化为空画像。
- 只传 intent 白名单，姓名、手机号等身份信息不进入 MCP。
- MCP 只返回“画像不可用”与可操作提示，不返回画像绝对路径或用户名。

### 6. 判据的粒度

本轮不改变岗位匹配规则，只修“画像有没有正确读到”和“参数有没有被接受”。来源与岗位
编号按 `(source_key, external_id)` 这一对展示，不能只显示可能跨来源重号的 external_id。

### 7. 数字的口径

本轮不新增产品统计数字。测试条数只作为代码回归证据，不代表发现闭环验收。

### 8. 这次明确不做什么

- 不改数据库 schema、真实数据库或定时任务，因为三工作日观察必须保持原运行版本。
- 不改岗位分类词或匹配规则，因为会改变观察期间的产品口径。
- 不做投递状态机与登录浏览器能力，因为属于 #27–#29 的独立安全边界。
- 不部署到当前观察 runtime；本轮只发布代码候选和 draft PR。

## 四、复盘（实现完回填，不是写方案时填）

### 11. 方案和实现差在哪

| 方案里写的 | 实际做成什么样 | 为什么改了 |
|---|---|---|
| 投递记录增加来源和编号 | 表格岗位单元格显示引用，并在表后追加完整可复制清单 | 单独加两列会挤掉旧的排序与状态信息 |
| MCP 严格拒绝未知参数 | 使用 server 请求中间件按注册表 schema 校验所有工具 | 当前 MCP SDK 生成的参数模型默认忽略额外键，没有现成 strict 开关 |
| intent 未知 key 在 MCP 再过滤 | 由共用 `match.load_intent()` 直接拒绝，MCP 白名单仍作隐私兜底 | CLI 和 MCP 必须共用同一个“画像可用”判据 |
| MCP 直接把底层画像错误返回对话 | 对话仅返回通用错误和 `profile.yaml` 修复提示 | 底层错误含绝对路径，对 CLI 有用，对 MCP 对话则是环境信息泄露 |

### 12. 实现中踩到的坑

- **现象**：中间件返回的错误内容在真实 Client 上不能解析。
  **原因**：当前 MCP 协议响应除 `isError` 外还要求 `resultType=complete`。
  **修法**：严格参数错误使用完整协议响应形状。
  **钉住它的测试**：`test_unknown_tool_argument_is_rejected_before_the_tool_runs`。
- **现象**：投递表增加独立引用列后，窄终端把岗位编号截断，旧排序测试也看不到编号。
  **原因**：Rich 表格总宽度增加后按列压缩。
  **修法**：引用放在岗位单元格第二行，并在表后输出完整可复制清单。
  **钉住它的测试**：`test_lists_source_and_external_job_id` 与旧排序测试。
- **现象**：最初的 MCP 白名单会静默丢掉未知 intent key。
  **原因**：白名单只考虑了隐私外泄，没考虑拼错 key 被洗成空 intent 后的伪命中。
  **修法**：`load_intent()` 先拒绝未知 key、非列表值和全空列表。
  **钉住它的测试**：`test_unknown_intent_key_is_rejected_instead_of_becoming_a_hit`、`test_scalar_intent_value_is_rejected_instead_of_iterating_characters`。

### 13. 如果重来，方案里该提前写上哪句话

凡是给终端表格新增定位字段，必须同时测试默认窄宽度和“完整值可复制”，不能只在宽终端截图里验。

凡是用白名单丢掉未知输入，必须分开回答“敏感数据能不能过边界”和“用户拼错时是否能看见”；
隐私默认拦截不能通过静默忽略来实现。
