**过方案时改掉的七个判断**（详见 §3、§4、§5）：

1. 改动面比方案原来假设的小得多 —— 不存在「散落在各处的调用方」，
   `commit` 参数只被 `ingest.sync()` 自己传，去参数是一处内部重构。
2. 「`start_run` 用独立连接」从**可选**变成**必须**。原方案写的是
   「需要留崩溃痕迹的话」，实际上现在 `start_run(commit=True)` 在真跑路径上
   是立刻落盘的，崩溃痕迹**已经存在**。一旦把整个 sync 收进一个事务并在异常时
   rollback，这行痕迹会跟着被回滚掉 —— 那是**功能倒退**，不是重构。
   痕迹是刚需的原因在 `cli.py:308-310`：`cli status` 每个源只读最近一条 run，
   没有 `running` 那行，崩溃的一次同步会显示成上一次的 `ok`，等于报假账。
3. §3 引的行号是错的，已改。`commit=` 三个形参在 `db.py:137`（`register_source`）、
   `:162`（`start_run`）、`:188`（`finish_run`），不是原来写的 `:44/:64/:83`
   —— 那三行分别是 `PRAGMA foreign_keys=ON`、一个 `for` 循环、一句 `return done`。
4. 「独立连接不会和主连接抢 SQLite 写锁」这条假设**是错的，实测会抢**。
   于是 §4 多出一节「独立连接的三条硬顺序」：先 `register_source` 提交（否则新源
   首次跑 `FOREIGN KEY constraint failed`），再 `start_run` 提交，然后才开主事务，
   `finish_run` 必须等主事务 `commit`/`rollback` 之后（否则 `database is locked`）。
   §5 原来那段骨架按原假设写的，**会死锁**，已整段换掉。
5. `register_source` 也必须走侧连接，不能走主连接。原方案只点了 `start_run`。
   走主连接的话 dry-run 会把 `sources` 那行留下来 —— 就是 `ingest.py:69-72`
   注释里记的那个旧 bug，等于原地踩回去。
6. §3 的假设「收拢后 6 个 `test_dry_run_*` 仍然全绿」**是错的，4 条红**。
   去掉 `commit=` 形参后 dry-run 下 `side is conn`，那两句无条件 commit 落在
   主连接上，结尾 `rollback()` 无事可回，留下 `sources` 一行 + `runs` 一行
   `running`。**方案要的目标本身没问题**，但需要多一层 `_NoCommit` 包装
   （见 §5），加上之后 351 全绿。§5 原来那张三条路径表的 dry-run 行是在
   还没去掉形参的代码上测的，不成立，已重测改掉。
7. §5 骨架里的 `db.connect()` 不能是裸的 —— 它打到 `db.DB_PATH`，也就是
   `data/jobagent.db` 那个 85 MB 真库。仓库里没有 conftest.py、没有任何地方
   monkeypatch `DB_PATH`，照骨架字面量实现再跑测试，测试数据会往真库里写。
   改成从主连接的 `PRAGMA database_list` 取库文件路径。
   另外侧连接从不 `close()`，`sync all` 五个源每轮泄 5 个，包成常驻进程会累积。

## 一、产品设计

### 1. 为什么现在做

**不做会发生什么：** 反馈报告已复现一例事务污染 bug（问题 2），且 `db.py` 和 `ingest.py` 里的大段注释说明这个雷已经踩过至少三次。当前架构下，每加一个写库点都要记得正确传 commit 参数，这类 bug 会反复出现。

**触发条件（已复现）：**
1. 同一批抓取里出现重复的 external_id（翻页期间岗位池变动时会发生）
2. 插入撞唯一约束抛 IntegrityError
3. `ingest.sync` 的 try 只包了 fetch()，没包写库循环
4. 异常抛到 CLI，CLI 捕获后 continue 处理下一个源
5. 下一个源的第一次 commit 把失败源留在事务里的半截数据一起提交

**结果：** 残留半批 jobs 和 snapshots，run 状态永远停在 running。

**根治方案：** 事务边界收拢到 `ingest.sync()` 一处——入口开始、成功提交、任何异常回滚。把散在 `register_source`、`start_run`、`finish_run` 里的 commit 参数全部去掉。

### 2. 用户会看到什么

**修复前（当前行为）：**
```
用户执行 `sync all`
→ 第一个源抓取到重复 id，写库失败
→ CLI 打印 "[red]失败[/red] source1: UNIQUE constraint failed"
→ 继续处理第二个源
→ 第二个源成功，commit
→ 用户看到第二个源成功，但不知道第一个源的半截数据已经混入库
→ 数据库里：第一个源的 run 状态永远 running，部分 jobs 已写入
```

**修复后：**
```
用户执行 `sync all`
→ 第一个源抓取到重复 id，写库失败
→ CLI 打印 "[red]失败[/red] source1: UNIQUE constraint failed"
→ 第一个源的所有数据库操作全部回滚，库里没有任何痕迹
→ 继续处理第二个源
→ 第二个源成功，commit
→ 用户看到：第一个源失败、第二个源成功，数据库状态干净
```

**对 dry-run 的改进：**
修复后，dry-run 模式下整个事务由 `sync()` 统一 rollback，调用方不需要关心每个写函数的 commit 参数。

## 二、具体实现

### 4. 数据长什么样，空值怎么办

本次重构不改数据形状，只改事务边界。但需要明确一个状态：

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| run.status | "running" / "success" / "failed" | 不会取不到（建表时有默认值） | N/A |
| run.error | 错误信息字符串 | `NULL` | 是 —— NULL 表示无错误 |

**关键点（过方案时改掉了原来的写法）。**

原方案这里写的是「事务回滚后，run 表里**不应该有任何记录**」。这句是错的，
照它做会造成功能倒退：

现在真跑路径上 `start_run(commit=True)` 是立刻落盘的（`db.py:177-178`），
所以进程被杀、写库炸掉之后，库里留得下一行 `running` —— 这正是
`db.py:165-166` 那条注释要的东西：「崩一次也留得下『这轮开过、没收尾』的痕迹，
否则崩一次就查不到崩在哪」。

把整轮收进一个事务、异常时 rollback，会把这行痕迹一起回滚掉。
于是排查手段从「库里有一行 running，知道崩在哪个源」退化成「什么都没有」。

**所以 run 那一行必须用独立连接写，这是必须项不是可选项：**

| 写的东西 | 用哪个连接 | 异常时 | 为什么 |
|---|---|---|---|
| `runs` 开头那一行 | **独立连接**，单独 commit | **留着** | 崩溃痕迹，回滚了就查不到崩在哪 |
| `runs` 收尾（finish_run） | 独立连接，单独 commit | 写 `failed` + error | 让 `cli status` 说真话，不停在 running |
| sources / jobs / snapshots / events | 主连接，`sync()` 统一提交 | **全部回滚** | 这些是业务数据，半截的比没有更糟 |

dry-run 例外：dry-run 下 run 那一行**也不落盘**。现有 6 个 `test_dry_run_*`
钉的就是这个（`:289 test_dry_run_leaves_no_running_row`、
`:300 test_failed_dry_run_leaves_nothing_either`），所以独立连接只在
`write=True` 时启用，dry-run 仍然走主连接 + 最后 rollback。

**独立连接的三条硬顺序（2026-08-07 过方案时补，原方案缺这一段）。**

上面那张表只说了「哪个写用哪个连接」，没说**顺序**。顺序是硬的：照 §5 那个
骨架直接写会死锁。SQLite 单写者，同一个库文件两个连接同时持写事务必然有一个
失败（3.50.4 / 3.53.1 两个版本实测一致，不是版本问题）：

| # | 约束 | 违反时的实测报错 |
|---|---|---|
| 1 | `register_source` 必须**先单独提交**，才能 `start_run` | 两种报错都真实，看主连接当时有没有持写锁：<br>· 主连接持着未提交的 `sources` 行 → 先撞 `OperationalError: database is locked`（锁在外键检查之前）<br>· 无锁争抢、源确实没注册 → `IntegrityError: FOREIGN KEY constraint failed`（`runs.source_key REFERENCES sources(source_key)`，`schema.sql:28`）<br>（原来这行只写了外键那个，2026-08-07 补上锁那个 —— 按方案描述的场景实际先看到的是锁） |
| 2 | `start_run` 的侧写必须在**主事务开写之前**做完并提交 | `OperationalError: database is locked` |
| 3 | `finish_run` 的侧写必须在主连接 `commit`/`rollback` **之后** | `OperationalError: database is locked` |

跑通的顺序：

```
register_source(主) + commit → start_run(侧) + commit → 主事务写业务数据
  → 成功：主 commit    → finish_run(侧, ok)
  → 失败：主 rollback  → finish_run(侧, failed + error)
```

这个顺序实测走通：`runs` 留下 `('new_src', 'failed', 'boom')`，`jobs` 回滚到 0 行 ——
崩溃痕迹留住了，业务数据全退了，两个目标同时满足。

**约束 1 和 §5 的目标冲突，按这里的写。** §5 原来说「去掉所有 commit 参数，
事务管理只在 `sync()` 一处」，但约束 1 要求 `register_source` 保留独立提交。
准确说法是：**去掉 `commit=` 这个形参**（调用方不再控制提交时机），
三个 runs/sources 相关函数各自在独立连接上提交，`sync()` 只拥有业务数据那**一个**事务。

### 5. 硬约束在哪一行

**事务边界是硬约束，通过代码结构强制。**

原来这里画的骨架是「整个函数体进一个 try，`except` 里 rollback」。
那个骨架**会死锁**：它没有位置放侧连接的写，而 `finish_run` 一旦落在
主连接 rollback 之前就撞写锁（见 §4 约束 3）。真正能跑的形状是这样：

```python
class _NoCommit:
    """dry-run 用：记账照写主连接，但把 commit 吞掉，留给结尾那句 rollback。

    这是去掉 `commit=` 形参的代价所在，也是它比形参强的地方：
    「要不要提交」只在 sync() 这一处决定，调用方不用逐个记得传，
    忘了传也不会静默落盘。
    """

    def __init__(self, conn):
        self._conn = conn

    def __getattr__(self, name):
        return getattr(self._conn, name)

    def commit(self):
        pass


def sync(conn, adapter, *, dry_run: bool = False) -> dict:
    write = not dry_run
    # 侧连接必须跟随主连接的库文件。**不能写 bare db.connect()** ——
    # 它解析到模块全局 db.DB_PATH，也就是 data/jobagent.db 那个真库。
    # 仓库里没有 conftest.py、没有任何地方 monkeypatch DB_PATH，
    # 测试的 fixture 是 db.connect(tmp_path/"test.db")，所以 bare connect
    # 会让测试一边连临时库一边往真库写。
    dbfile = conn.execute("PRAGMA database_list").fetchone()[2]
    side = db.connect(Path(dbfile)) if write else _NoCommit(conn)
    db.register_source(side, ...)           # 记账连接，自己提交（§4 约束 1）
    run_id = db.start_run(side, ...)        # 记账连接，自己提交（§4 约束 2）

    try:
        jobs = adapter.fetch()
        ...                                 # 业务数据全部写在 conn 上，一次不提交
        conn.commit()                       # 只有这一个事务边界
    except Exception as exc:
        conn.rollback()                     # 先退业务数据
        db.finish_run(side, run_id, "failed", 0, str(exc))   # 再写痕迹（§4 约束 3）
        raise
    finally:
        if write:
            side.close()                    # 常驻进程里不关就是每轮泄一个连接
    db.finish_run(side, run_id, status, len(jobs), err)
    return stats
```

（`side.close()` 的位置还要再排一次：`finally` 里关掉之后，成功路径上那句
`finish_run(side, ...)` 就没连接可用了。实现时把成功路径的 `finish_run`
挪到 `try` 的末尾、或者改用 `try/except/else` —— 这一处骨架还没跑过，
不要照抄。已跑过的是下面那张三条路径表对应的版本，它没有 `close()`。）

三点和原骨架不一样，都是实测逼出来的：

- `register_source` / `start_run` 在 `try` **外面**，因为它们必须先于主事务提交
- `finish_run` 在 `rollback` **后面**，不是 `except` 块开头
- `fetch()` 收进了同一个 `try` —— 现在它有自己的 try（`ingest.py:97-103`），
  合并之后 fetch 失败和写库失败走同一条清理路径
- `register_source` 走的是 `side` 不是 `conn`。**这一处如果写成 `conn` 且无条件提交，
  dry-run 就会漏一行 `sources`** —— 正是 `ingest.py:69-72` 那段注释记录的旧 bug
- dry-run 的 `side` 是 `_NoCommit(conn)`，不是裸的 `conn`。**这一条是 2026-08-07
  实测补的，原来写的「dry-run 走主连接 + 最后 rollback」不够**，见下面。

**为什么 dry-run 必须包一层，不能直接把 `side` 设成 `conn`。**

去掉 `commit=` 形参之后，`register_source`/`start_run` 变成无条件提交。
dry-run 下 `side is conn`，于是这两句 commit 落在主连接上，结尾那句
`rollback()` 无事可回。实测（把方案实现出来跑仓库自己的测试）：

```
真仓库基线                      : 351 passed
side = conn（原方案写法）        : 4 failed / 347 passed
side = _NoCommit(conn)          : 351 passed
```

4 条失败全在 `TestDryRunWritesNothing`：`test_dry_run_leaves_every_table_untouched`、
`test_dry_run_does_not_leak_a_new_source`、`test_dry_run_leaves_no_running_row`、
`test_failed_dry_run_leaves_nothing_either`。落盘结果是 `sources=1` +
`runs=[('running', None)]` —— **就是 `db.py:166-171` 注释里记着的那个「`cli status`
说假话」的 bug 原地踩回去**。

原方案 §3 把「收拢后 6 个 `test_dry_run_*` 仍然全绿」列为唯一有回归风险的地方，
方向对，结论反了：不加 `_NoCommit` 就是 4 条红。

还有一个绕不过去的约束：**dry-run 不能跳过 `start_run`**。
`snapshots.run_id` 是 `NOT NULL REFERENCES runs(id)`（`schema.sql:40`），
而 `ingest.py:136-148` 每条路径都写 snapshots，所以 `runs` 那行必须真的 INSERT、
拿到 id，只是不许提交。这就排除了「dry-run 干脆不记账」这个更省事的形状。

**dry-run 下 `finish_run` 是空操作，这是对的，别当成 bug 去"修"。**
dry-run 时 `rollback()` 已经把 `start_run` 那行 INSERT 退掉了，
后面那句 `UPDATE runs ... WHERE id=?` 命中 0 行（实测 `rowcount == 0`），
所以不写任何东西、也不会被下一个源的 commit 带进库。四条路径实测
（`side = _NoCommit(conn)` 那版，每次都用一条新连接只读已提交状态）：

| 路径 | sources | runs | jobs |
|---|---|---|---|
| 真跑成功 | 1 | `[('ok', None)]` | 1 |
| 真跑失败 | 1 | `[('failed', '…拒绝按「全部关闭」处理')]` | **0** —— 痕迹留住、业务全退 |
| dry-run 成功 | 0 | `[]` | 0 —— 6 个 `test_dry_run_*` 钉的就是这个 |
| dry-run 失败 | 0 | `[]` | 0 |

（原来这张表只有三行，dry-run 那行写的 `0 / [] / 0` 是**在还没去掉 `commit=` 的
代码上测的**，不成立。去掉形参之后按原骨架实测是 `1 / [('running', None)] / 0`。
2026-08-07 重测改掉。）

**不能靠调用方传参：** 去掉所有 `commit=True/False` **形参**，调用方不再控制提交时机。
但这不等于「只剩一个 commit」：`sync()` 只拥有**业务数据**那一个事务，
`sources` 和 `runs` 各自在自己的连接上提交（原因见 §4）。

| 空结果仍然拒绝按全部关闭处理 | 已有 `test_empty_fetch_raises_not_closes_everything`、`test_empty_fetch_ok_when_adapter_says_so`、`test_authoritative_empty_does_not_mass_close` | 同左（回归） |

**这次「做一半」的形状是明确的，值得单独写下来。**

收拢事务是一个改动，run 留痕用独立连接是另一个改动。只做前一半的话：
业务数据回滚正确、报告那例 bug 也修好了、`test_dry_run_*` 全绿，
**唯一挂的是 `test_run_row_survives_write_failure`**。
没有这条测试，这个半成品会看起来完全正常，而代价是排查能力静默退化
（本仓库 001 §12 那个「索引两边都留」的坑是同一个形状：常见路径全绿）。

**反向用例（必须）：** `test_transaction_isolation_on_error` 模拟：
1. 第一个源写到一半抛异常
2. 验证数据库里该源的**所有记录**都不存在（包括 run / jobs / snapshots）
3. 第二个源正常完成
4. 验证第二个源的数据完整，不受第一个源影响

**如果做一半会怎样：**
- 去掉了 commit 参数但没有在 sync() 里加 try-commit-rollback → 所有写操作不提交，测试全挂
- 只改了部分写函数 → 有遗漏 commit 的函数会 TypeError，pytest 立刻报错
