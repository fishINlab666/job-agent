## 一、产品设计

### 1. 为什么现在做

不是「这个功能听起来有用」，而是**不做会发生什么**。
如果说不出「不做的后果」，这条大概不该现在做。

### 2. 用户会看到什么

按时间顺序写一遍真实场景，不用术语。
一个不懂技术的人读完应该能说出「所以我点了这里，然后屏幕上出现那个」。

```
用户做了什么 → 系统做了什么 → 屏幕上出现什么
```

### 3. 哪些是已核实的，哪些是我猜的

分两栏列。**猜的那一栏是这份方案里最重要的部分**——
它决定了哪些结论下游可以直接用，哪些必须先验证。

| 事实 | 怎么核实的 |
|---|---|
| | 命令 / 实测输出 / 文件行号 |

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|

## 二、具体实现

### 4. 数据长什么样，空值怎么办

**这一栏是本项目的头号 bug 来源，不许留空。**

每个字段都要回答：取不到值时是什么？「没有值」和「值不匹配」会不会走进同一个分支？

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| | | `None` / `[]` / `""` | 是 / 否 —— 否就是 bug |

> 踩过的原型：`grad_year=None` 碰上 `None not in ["26","27"]` 判否，
> 岗位被静默丢掉，用户永远不知道它存在过。
> 现实里这个字段是「2026-2027年毕业」或者干脆空着。
> 凡是「没有值」会被当成「不合格」的地方，都要写成三态。

### 5. 硬约束在哪一行

区分两种约束，写清这次用的是哪种：

- **软约束**：提示词里写「请先向用户确认」。模型可能不听。
- **硬约束**：做成 API 形状——没有 `confirm_token` 就调不到下一步。

> 凡是「错了会造成不可撤销后果」的地方（代投、删除、外发），
> 必须是硬约束。软约束只能用在「错了顶多难看一点」的地方。

### 6. 判据的粒度

如果这次要「认出某个东西」（识别厂商、判断岗位类型、匹配城市），
写清判据是**哪一级**的，以及差一级会命中什么。

> 踩过的原型：拿品牌域名 `feishu.cn` 当招聘系统的判据，
> 结果一篇飞书文档被判成「某公司的招聘入口」。
> 品牌级 ≠ 产品级，差这一级命中的就不是同一件事。

### 7. 数字的口径

如果这次要产出任何数字（覆盖率、命中数、成功率），逐个写清：

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|

> 踩过的原型七次，全是同一类错：
> 「有响应」不等于「有内容」，「本机排不上队」不等于「那个站连不上」，
> 「页面上有个串」不等于「这家在用这个系统」，「一行」不等于「一家」，
> 「这三轮」不等于「一直」。
> 最后一条特别提醒：会动的量要报**区间**并写清上下界差在哪，不要钉一个快照。

### 8. 这次明确不做什么

比范围更要紧的是边界。每条写上不做的理由。

- 不做 X，因为 —— （不是「以后再说」，是「现在做等于编」）

## 三、怎么验

### 9. 验证命令

每条结论对应一条能跑的命令。跑不起来的验证方案等于没有。

```bash
uv run pytest tests/test_xxx.py -q
```

### 10. 测试钉的是哪几条

不是「加了 N 个测试」，是「哪个结论被哪个测试钉住了」。
尤其是：**反向用例**（不许把不该命中的洗成命中的）和**输出用例**
（字段判对了但打印错了，等于白判）。

还要问一句：**如果这个修法被做了一半，哪条测试会红？**
「加到了新地方、没从老地方删掉」这种半成品不会自己暴露——
两边都在的时候，常见路径照样全绿，只有边缘路径会挂。
这种情况需要一条专门守归属的测试，而不是守行为的测试。
（真实案例见 001 §12 补记：索引同时留在 `schema.sql` 和 `migrate()` 里，
新库全绿，老库整个 `init()` 挂掉。）

| 结论 | 测试 | 做一半会红的那条 |
|---|---|---|
