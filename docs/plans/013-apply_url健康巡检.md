## 一、产品设计

### 1. 为什么现在做

不做的后果已经发生过一次，代价是**三个月的产出不可核对**。

2026-08-10 发现库里 8594 条飞书 `apply_url` 全是死链（`plans/010`）：
链接少了 `/detail` 后缀。这批链接从采集第一天就是坏的，中间没人发现，
因为**它坏得很安静** —— HTTP 回 200，body 有 200KB，只有渲染出来才是
「您正在寻找的页面不存在」。当初的验证只看状态码就收了。

`apply_url` 的唯一用途是「点开就是官网那一页」拿去人工核对。链接死了，
整条筛选链（采集 → 归一 → 匹配 → 推送）的产出**全都没法核对** ——
不是少了一个功能，是上游所有工作都失去验证手段。

第二个原因：这类失效**只会再来**。链接形状由源站决定，源站改版不通知我们。
`plans/010 §12` 已经写过「判死活看渲染后的正文，不看状态码」，
但那只是一次性修复 + 一句文档；没有任何东西在**持续**看着它。

### 2. 用户会看到什么

```
用户每周跑一次 jobagent health
  → 系统按源抽样，真开浏览器打开抽中的岗位页
  → 屏幕上按源列出：这个源抽了几条、活着几条、死了几条、死的长什么样
```

死链出现时要能一眼看出**是整源坏了还是零散下架**，因为这两件事的处置完全不同：
整源坏了是我们的 bug（去修适配器的链接拼装），零散下架是正常业务
（那条岗位该标 `closed_at`）。

一次真实场景，`health` 报出整源异常时：

```
$ uv run python -m jobagent.cli health --source feishu:nio:campus
feishu:nio:campus  抽 20 条 · 活 0 · 死 20
  ⚠ 整源异常：抽中的 20 条全死，不像零散下架
  死法分布：链接形状坏了 20
  下一步：核对 adapters/feishu.py 的 _position_url()，别逐条改库
```

## 二、具体实现

### 4. 数据长什么样、空值怎么办

输入只有一张表的四列，抽样范围是「开放岗位」：

| 列 | 用途 | 空/异常时怎么办 |
|---|---|---|
| `apply_url` | 要打开的那个 URL | **空值就报错退出，不是跳过。** 今天是 0 条（§3 已核实），真出现了说明采集侧漏了拼装 —— 那正是这个巡检要抓的事故，静默跳过等于把它藏起来 |
| `source_key` | 按源分组抽样、对应钉住的形状 | 不会为空（主键的一半）。库里出现巡检不认识的源 → 见 §5 白名单那条 |
| `closed_at` | 只抽 `IS NULL` 的行 | 非空的行**不抽**：已知下架的岗位打开当然是死的，把它算进死链数是自己制造噪音 |
| `external_id` | 只用来在报告里指认是哪条 | 不会为空（另一半主键） |

判定结果的取值域是**白名单，只有五个**：

| 判定 | 触发标记 | 是不是我们的 bug | 报表里算哪一栏 |
|---|---|---|---|
| `healthy` | 正文有内容且**不含** `undefined` | — | 活 |
| `broken_route` | `您正在寻找的页面不存在` | **是**，去修 URL 拼装 | 死 · 链接形状坏了 |
| `gone` | `undefined`，或 `该职位已下线`（后者未实测，§3） | 不是，源站的业务事件 | 死 · 岗位没了 |
| `unknown` | 轮询到超时都没判出来 | 不知道 | **单独一栏，不算活也不算死** |
| `error` | 导航抛异常（超时、DNS、连接断） | 不知道 | 同上 |

为什么要白名单而不是「不是 healthy 就算死」：库里的源会长（`kb/company-portals.md`
一路在加），判据是字符串级的、会换季失效。**`unknown` 必须是一个显式取值。**
把「判不出来」并进「死」，慢租户每轮全红；并进「活」，判据失效那天巡检安静地全绿 ——
后者就是 2026-08-10 那次事故的形状。

### 5. 硬约束在哪一行

五条，每条都要能指到具体位置，不是「注意一下」：

**① 钉死每个源的 URL 形状 —— 用字面量，不是数形状个数。**
新建 `jobagent/health.py` 里一张 `EXPECTED_SHAPE: dict[str, str]`，
pytest 拿真库比对（`tests/test_health.py`，不联网）：

```python
EXPECTED_SHAPE = {
    "feishu:bytedance:campus": "https://bytedance.jobs.feishu.cn/campus/position/<ID>/detail",
    "feishu:nio:campus":       "https://nio.jobs.feishu.cn/campus/position/<ID>/detail",
    # 自定义域名。方案第一版按 `<tenant>.jobs.feishu.cn` 猜，猜错了，见 §11 ④
    "feishu:sensetime:edu":    "https://hr-jobs.sensetime.com/edu/position/<ID>/detail",
    "feishu:xiaopeng:campus":  "https://xiaopeng.jobs.feishu.cn/campus/position/<ID>/detail",
    "tencent_join":            "https://join.qq.com/post.html?pid=<ID>",
}
```

**为什么必须是字面量：数形状个数在事故当天是绿的。** 拿事故期的库副本验过：

```
=== jobagent-5.db（事故期）===        === jobagent.db（修好后）===
feishu:bytedance:campus 形状=1        feishu:bytedance:campus 形状=1
  .../campus/position/<ID>              .../campus/position/<ID>/detail
```

8433 条全坏时，「每个源只有 1 种形状」这个不变量照样成立。
换句话说，`count == 1` 这种写法**在它唯一要防的那次事故里不会报警**。

**② 归一化正则要认负号。** 腾讯有 `pid=-2`~`-6`（源站自己的数据，§3）。
`re.sub(r'[0-9]{4,}', '<ID>', u)` 这种写法下负 pid 每条自成一形状，
腾讯会报 6 种形状。要用：

```python
_norm = lambda u: re.sub(r'(?<==)-?\d+', '<ID>', re.sub(r'/-?\d+(?=/|$)', '/<ID>', u))
```

实测：腾讯 6 → 1，四个飞书源保持 1。

**③ 新源必须显式登记。** 库里出现 `EXPECTED_SHAPE` 里没有的 `source_key` →
测试**失败**，不是跳过。源是 f-string 拼出来的（`feishu:<tenant>:<portal>`，
[feishu.py:244](jobagent/adapters/feishu.py:244)），数不出全集，所以只能白名单。
漏登记的方向必须是「报错」而不是「不检查」。

**④ 轮询，不许固定等待。** 正常页首现最慢 15.9s、坏路由 1.4s（§3）。
固定 3.5s 会把 6/8 正常页判成 unknown。超时预算 20s，
判出来就停 —— 坏页平均 1.5s 返回，所以坏得多的时候反而更快。

**⑤ 复用一个 browser + 一个 page。** 每条新开浏览器把 6.9s/页翻几倍（§7）。

### 6. 判据的粒度

判据只认**渲染后正文里的整串标记**，判定顺序是固定的：

```
1. 有 您正在寻找的页面不存在  → broken_route   ← 先判，它最明确
2. 有 该职位已下线            → gone
3. 有 undefined               → gone
4. 正文非空且不含以上          → healthy
5. 20s 到了还没判出           → unknown
```

三条粒度上的取舍，每条都有被推翻的前身：

**不用 title、不用 `- 租户名` 切分。** 上一版方案打算按 title 的
「岗位名段为空」判死，实测 4/4 假 id 判不出来 —— `- 蔚来校招` 前面**没有空格**，
` - ` 根本不是它的子串，`split(" - ")[0]` 恒等于原串。这条判据是 100% 的空操作，
写下来会得到一个永远绿的巡检。

**不用 `职位描述` 当健康标记。** 假 id 页也渲染这个**标签**（4/4 命中），
只是标签底下没内容。拿标签判健康，等于拿「页面框架加载出来了」判「岗位存在」。

**不用正文长度。** 分得开（正常 294–1299 vs 假 id 46–127），但阈值定在哪都是编的：
xiaopeng 正常页 294 字，离 127 只差一倍多。这种判据坏起来是渐进的、没有报警点。

**`undefined` 要配对照组。** 它是这五条里最脆的一条 —— 源站前端换个框架，
空值不再渲染成字面量 `undefined`，判据静默失效、假 id 全判 healthy。
所以每轮固定多打一条**已知不存在的 id**（形状对、id 是 19 个 9），
它必须判出 `gone`；判不出就在报告顶部写「判据可能已失效」。
这条对照组是判据的体检，不占抽样配额。

### 7. 数字的口径

| 这个数 | 分子数的是什么 | 分母数的是什么 | 会不会随时间动 |
|---|---|---|---|
| 「活着」条数 | 抽中且渲染后判为活的岗位行数 | **抽中的行数**，不是源的总行数 | 会（每轮重抽） |
| 源的健康率 | 同上 | 同上 | 会 |
| 覆盖率 | 累计抽查过的**不同岗位**行数 | 该源开放岗位行数 | 会（分母随采集动） |

**抽样量买到的是区分度，不是发现率。** 这条反直觉，但算出来很干净。

单页成本 **≈ 轮询预算 20 秒**，不是「平均渲染耗时 6.9 秒」。这两个数差一倍多，
差在哪值得写清楚：判成 healthy 必须等满预算（§6 的不对称），而抽样打的
绝大多数就是健康页。第一版按 6.9s/页 估，实测 24 页跑了 **7 分钟**、估的是 2.8 分钟。

坏页照样秒返回（1.4–2.1s），所以这个上限只在「一切正常」时用满 ——
巡检跑得慢反而是好消息。飞书 8594 条全扫 **47 小时**，必须抽样。

| 抽法 | 打开次数 | 最多耗时 | 对「整源全坏」 | 对「30 条零散下架未标」 |
|---|---|---|---|---|
| 每源 5 条 | 20 + 4 对照 | 8 分钟 | 必然全红 | 命中率 **21.6%** |
| 每源 10 条 | 40 + 4 对照 | 15 分钟 | 必然全红 | **38.6%** |
| 每源 20 条 | 80 + 4 对照 | 28 分钟 | 必然全红 | **62.6%** |

整源全坏时**抽 1 条就能发现** —— 2026-08-10 那次事故属于这一类。
加大 n 不提高发现率，只是把「零散下架」和「整源坏」分得更开
（n 越大，「全红」这个结论越不可能是巧合）。

由此得到两条设计结论：

- **默认每源 5 条**（最多 8 分钟），`--sample` 可调。原本定的是 10 条，
  按 6.9s/页 算是 4 分钟；换成真实的 20s 预算后那是 15 分钟 —— 一个「每周手动跑」
  的命令跑一刻钟，人就不跑了。选 5 是为区分度：**整源全坏抽 1 条就能发现**，
  而 5 → 10 只把零散下架的命中率从 21.6% 提到 38.6%，两个数都低到不能宣称覆盖
  （见下一条），多花的 7 分钟买不到结论。
- **巡检不许宣称能发现零散下架。** 每源 20 条、库里积 30 条未标下架时命中率
  只有 62.6%，抽空了也是常事。输出里不写「未发现下架岗位」这种话 ——
  那是把 37% 的漏检说成了阴性结论。

三条必须写进输出的口径提醒：

- **「抽 20 条全活」不等于「这个源 634 条都活着」。** 抽样只能证伪不能证明。
- **分母是「抽中的」不是「源里全部的」。** 这两个数差一个数量级，
  混了就会把「抽 20 活 20」说成「634 条全活」。
- **`-2`~`-6` 这类源站占位卡片会被判成死链，这是对的。** 但它们**不是我们的 bug**，
  报表里要和「链接形状坏了」分开计，否则每轮都有 5 条固定假警报稀释信号。
  （腾讯这一版根本判不出死活，§8，所以这 5 条实际会落在 `unknown` 栏。）
- **`unknown` 单独出栏，不许并进活或死。** 慢租户 + 20s 预算下它会常态非零
  （nio 有正常页 15.9s 才首现）。并进「死」每轮假红，并进「活」是把
  「判不出来」说成了「是好的」。

### 8. 这次明确不做什么

- **不做腾讯侧的死活判据。** 现在做等于编：渲染后三种 pid 完全同形（§3 已核实），
  已复验到底：真 pid（104437）/ 负 pid（-6）/ 假 pid（999999999）三条渲染出
  **逐字节相同**的正文（875 字，title `岗位投递 | 腾讯校招`，无 `职位描述`、无 `不存在`）。
  `post.html?pid=` 是列表页，详情不登录不渲染。
  所以腾讯 808 条**全部落 `unknown` 栏**，报表里写明「腾讯无判据」，
  **不假装这 808 条被覆盖了**。腾讯侧唯一被守着的是 §5 的 URL 形状不变量。
- **不清理那 6 条脏数据。** 那是动真库，要人先批；`-2`~`-6` 删了下轮 sync 可能还回来，
  该在采集侧拦还是查询层拦是独立判断题（另一个 subagent 在评）。
- **不自动改库。** 巡检**只报告**，不给自己写 `closed_at` 的权力。
  发现死链就自动标关闭，等于让一个抽样判据去删用户的岗位池 ——
  判据换季失效时（`kb/job-fields.md` 已警告过字符串级判据会失效），
  错的方向是「把活岗位标成关闭」，而这个动作没有回滚。
- **不做定时器 / 后台常驻。** 「周期性」这一版靠人手跑或系统 cron，
  进程常驻会带来「它到底还在跑吗」这个新的静默失效面。
- **不进 MCP 只读层。** 它要开浏览器、几十秒、且会对外发请求；
  只读层的边界是「不对外」（见 `mcp_server.py` 模块头）。
- **不判正文长度、不判 title。** 都试过、都被实测打死了，理由在 §6。
  写进「不做」是为了下一个人不再捡回来。

### 9. 验证命令

形状不变量（不联网，秒级，进 CI）：

```bash
cd "$(git rev-parse --show-toplevel)" && PYTHONDONTWRITEBYTECODE=1 .venv/bin/pytest tests/test_health.py -q -p no:cacheprovider
```

真打一轮（联网，开浏览器，**实测 7 分钟** —— 健康页要等满 20s 预算，§7）：

```bash
cd "$(git rev-parse --show-toplevel)" && .venv/bin/python -m jobagent.cli health
```

Bash 工具的单次调用上限是 2 分钟，所以从工具里跑要挂后台再读日志：

```bash
cd "$(git rev-parse --show-toplevel)" && nohup .venv/bin/python -m jobagent.cli health > /tmp/health_run.log 2>&1 &
```

单源 + 小样本（调判据时用，约 2 分钟）：

```bash
cd "$(git rev-parse --show-toplevel)" && .venv/bin/python -m jobagent.cli health --source feishu:nio:campus --sample 5
```

**证明形状不变量真的能红** —— 这条最关键，把 `EXPECTED_SHAPE` 里
bytedance 那行的 `/detail` 删掉再跑，必须失败（复现 2026-08-10 那次事故）：

```bash
cd "$(git rev-parse --show-toplevel)" && cp jobagent/health.py /tmp/health.bak && .venv/bin/python -c "import pathlib; p=pathlib.Path('jobagent/health.py'); s=p.read_text(); old='bytedance.jobs.feishu.cn/campus/position/<ID>/detail'; assert old in s, '改坏目标串不存在，这次改坏是空操作'; p.write_text(s.replace(old, old[:-7]))" && PYTHONDONTWRITEBYTECODE=1 .venv/bin/pytest tests/test_health.py -q -p no:cacheprovider; cp /tmp/health.bak jobagent/health.py && PYTHONDONTWRITEBYTECODE=1 .venv/bin/pytest tests/test_health.py -q -p no:cacheprovider | tail -1
```

**改坏验证有两个自己的坑，都是这次踩到的。**

**① 不用 `sed` 做改坏。** 第一次跑这条时用的是 `sed`，它没匹配上
（模式带了行尾锚，而那行结尾是逗号），文件没变、测试照常绿 ——
而我差点把这个绿当成「守卫失效」记下来。改坏验证失手的方向是**假绿**，
和被验对象的失效方向一样，所以改坏本身也要有守卫：
**先 `assert old in s`，再替换。** 这一版 17 处改坏里有 2 处是这样被发现是空操作的。

**② 不用 `git checkout` 还原。** `health.py` 是这一版新增的文件，
提交前它是 untracked，`git checkout jobagent/health.py` 对它**无效** ——
它会报错退出，而命令里那个 `;` 把错误咽掉了，结果：测试如期变红、
看起来验证成功，但**改坏的代码留在文件里**。这个状态下接着 `git add` 就把
一个「登记值少了 `/detail`」的守卫提交进去了，而它守的正是这件事。
所以还原要用 `cp` 备份回滚，并且**还原之后再跑一遍确认回绿** ——
改坏验证不是「见到红就完事」，是「红过之后必须能回到绿」。

全量套件（当前基线在 §0，加完这组应更多且全绿）：

```bash
cd "$(git rev-parse --show-toplevel)" && PYTHONDONTWRITEBYTECODE=1 .venv/bin/pytest -q -p no:cacheprovider
```

### 10. 测试钉的是哪几条

`tests/test_health.py`，不联网 —— 网络那部分靠 §9 的真跑命令验，
**判据函数本身用固定正文串喂**，这样它可以进 CI 且不会因为源站抖动假红。

| 钉住的行为 | 改坏什么会让它红 |
|---|---|
| 每个源的 URL 形状等于 `EXPECTED_SHAPE` 里的字面量 | 删掉 `/detail`（= 复现事故） |
| 库里出现未登记的 `source_key` → 失败 | 加一个源不登记 |
| `EXPECTED_SHAPE` 非空 | 表清空后上面两条会**一条都不收集**，pytest 报 no tests ran —— 在 CI 里和通过没区别 |
| 归一化认负号：`pid=-2` 和 `pid=104437` 归一成同一形状 | 换回 `[0-9]{4,}` 那版 |
| 归一化不吞掉路径段：`/campus/` 不变成 `/<ID>/` | 正则写宽 |
| `您正在寻找的页面不存在` → `broken_route` | 判据串写错一个字 |
| `undefined` → `gone` | 漏掉这条分支（= 假 id 假绿） |
| 含 `职位描述`/`职位要求` 但也含 `undefined` → `gone` 不是 `healthy` | 把「有职位描述」当健康标记（实测 4/4 会假绿） |
| 判定顺序：正文同时含「页面不存在」和 `undefined` → `broken_route` | 顺序颠倒，我们的 bug 被归成业务事件 |
| 正文空/超时 → `unknown`，既不是活也不是死 | 把兜底判成 healthy 或 broken |
| 判定取值域是那五个之一（白名单） | 返回一个新字符串而报表不认 |
| 统计的分母是「抽中的条数」不是源的总行数 | 拿 `COUNT(*)` 当分母（= §7 那条口径） |
| `closed_at IS NOT NULL` 的行不进抽样池 | 抽样 SQL 漏掉这个条件 |
| 巡检不写库：跑完 `jobs` / `runs` / `events` 行数不变 | 顺手给自己加写 `closed_at` 的权力（§8） |

另有六条钉轮询的终止条件（实现时才发现需要，原因见 §11）：

| 钉住的行为 | 改坏什么会让它红 |
|---|---|
| 像 healthy 的中间态**不许**提前返回 | 把 `healthy` 加进 `_EARLY_EXIT`（= 复现实测抓到的真 bug） |
| 「坏」的判定要立刻返回 | `_EARLY_EXIT` 清空（否则每条都拖满预算，一轮翻倍） |
| 等满预算没坏标记 → healthy | 兜底改判 `unknown`（正常岗位全进「判不出」栏） |
| 正文一直空 → unknown | 兜底改判 healthy |
| 读正文抛异常时继续轮询 | 异常不吞（一页崩掉整轮） |
| 导航失败 → error，不算死链 | 判成 `broken_route`（网断了每轮假红） |

每条都要**单独改坏跑一遍**确认它真的会红 —— 只验绿等于没验。
`-k` 匹配不到任何测试算失败，不算通过。

**这组测试的时钟是假的**（`fake_clock` fixture）。不是为了跑得快 ——
是因为它们验的就是「提前退出」：真时钟下提前退出被改坏时，测试不会失败，
它会**挂到预算耗尽**。第一次跑改坏验证时 `budget=999` 让 pytest 卡了两分钟被杀，
而「用超时表达的失败」在 CI 里读起来像环境问题，不像守卫报警。

## 四、复盘

### 11. 方案和实现差在哪

**① 判据的正确性和「什么时候算判完」是两件事，方案只写了前者。**
`classify` 的五条分支实测全对，但第一版 `probe_one` 一见 `healthy` 就返回，
4 条对照组里 **3 条被判成活的**。把 nio 那条的时间线摊开就看明白了：

```
 2.2s  正文 0 字            → unknown
 6.2s  正文 20 字           → healthy   ← 第一版在这里返回了
11.3s  正文 49 字 undefined → gone      ← 真判据 5 秒后才到
```

页面框架（导航栏、登录按钮）先渲染，`undefined` 后到。而 `healthy` 的定义是
「正文非空且**没有**坏标记」—— 一个还没渲染完的页面天然满足它。
**`healthy` 不是一个能被观测到的正标记**，它是「等满了也没等到坏的」。
所以只有「坏」能提前退出，`healthy` 必须等满预算。

方案 §5 ④ 写了「轮询，不许固定等待」，这条是对的但不够 ——
它防的是「等太短」，没防「见到中间态就收」。

**② 对照组是这一版唯一真正抓到 bug 的东西。** 20 条抽样全绿、形状全对，
只有 4 条对照组红了。如果没设计它，这个巡检会带着 75% 的假绿率上线，
而且**它报的绿看起来比真的还漂亮**。

**③ 单页成本估错一倍多。** 方案 §7 写 6.9s/页（实测平均渲染耗时），
但改成「healthy 等满预算」之后每条健康页都是 20s。24 页实跑 7 分钟、估的 2.8 分钟。
连带默认抽样量从 10 降到 5：15 分钟的手动命令没人会每周跑。

**④ sensetime 的域名我按 `<tenant>.jobs.feishu.cn` 猜，猜错了。**
实际是自定义域名 `hr-jobs.sensetime.com`。这条恰好证明了 §5 ① 为什么要钉字面量：
如果只数「形状有几种」，我这个写错的域名根本不会被发现。

**⑤ `inner_text` 会超时抛异常。** sensetime 的哨兵页上撞到 30s 超时，
把整个探测脚本崩了。一轮巡检打几十页，一页的异常不该带走其余几十页的结果。

**⑥ 改坏验证这个动作本身失手过两次，两次都是假绿。** 方案 §9 只写了
「把 `/detail` 删掉必须红」，没写这条命令自己怎么保证有效：

- `sed` 的模式没匹配上（行尾是逗号），文件没动、测试照常绿。
- `git checkout` 还原不了 `health.py` —— 它是新文件、untracked，
  命令里的 `;` 把 git 的报错咽了，于是**改坏的代码留在了文件里**，
  而下一步就是 `git add`。

两次的表现都是「看起来验证通过了」。改坏验证和它要验的守卫**失效方向相同**，
所以它也得有守卫：改之前 `assert old in s`，还原之后**再跑一遍确认回绿**。
「见到红就完事」不够 —— 红过之后要能回到绿，这两件事都要在同一条命令里。

### 13. 重来该提前写上哪句话

- **「判据对不对」和「什么时候算判完」要分开设计。** 这次判据五条全对，
  但终止条件错了，结果 75% 的对照组假绿 —— 一个正确的判据在错误的时刻取样，
  和判据写错没有区别。
- **每条判据都要有一个「必须判出非健康」的对照组。** 抽样只能证伪，
  所有抽样都绿的时候，唯一能告诉你「判据还活着」的就是这个对照组。
  它不占配额，但它是这一版里唯一真正报警的东西。
- **耗时估算要用「终止条件的上界」，不是「平均耗时」。** 差一倍多，
  而这个数直接决定默认抽样量，也就直接决定人还愿不愿意跑它。
- **测「提前退出」的测试必须假掉时钟。** 否则守卫失效的表现是挂起，不是报错。
- **改坏之前先断言目标串存在，还原之后再跑一遍确认回绿。** 这两句各对应一次
  真实的失手：`sed` 没匹配上（文件没动、测试照常绿），
  `git checkout` 还原不了 untracked 的新文件（改坏的代码留在了文件里，
  而验证看起来是通过的）。改坏验证和它要验的守卫失效方向相同 ——
  都是假绿、都长得像好消息，所以它自己也需要守卫。
- **猜出来的字面量要拿真库对一遍再写进方案。** sensetime 的自定义域名
  就是这么被抓到的 —— 也顺带证明了钉字面量比数形状有用。
