## 一、产品设计

### 1. 为什么现在做

当前自动任务已经按时启动，但第一次定时运行就因一个公开接口的短暂读超时整轮失效。
同时，成功或失败只写进终端日志，用户仍要主动来问；官网真值则要求逐轮逐公司手写
JSON，三工作日最多需要 45 份输入。保持现状只是在验证“后台会启动”，不能验证
“用户不用巡检官网”。

### 2. 用户会看到什么

```text
定时任务启动
  → 某个公开接口短暂超时：系统只再试一次
  → 仍失败：明确记录失败并发 macOS 通知
  → 全部成功且有岗位变化：发一条变化通知
  → 20:30 且当天三轮全部成功、当前无变化：发一条当日完成通知
  → 20:30 发现当天少轮次：改发当日观察不完整通知
  → 同期由独立取数路径保存官网岗位编号候选
  → 用户每天只看一份汇总并明确确认，不再手写 15 份 JSON
```

本轮不会自动把候选证据写成“已核验”。独立快照只是待审材料；只有带 `--accept`
的人工确认命令才把当天三轮证据一次性写入最终真值表。

### 3. 哪些是已核实的，哪些是我猜的

| 事实 | 怎么核实的 |
|---|---|
| observation #2 的字节源抛出 `httpx.ReadTimeout` | 本机 `observe.log` 与真实数据库 observation #2 |
| `ReadTimeout` 发生在 Adapter `fetch()`，`ingest.sync()` 在其外层记录失败 run | `jobagent/adapters/feishu.py::fetch`、`jobagent/ingest.py::sync` |
| 当前没有 Notification Center 调用 | 全仓搜索 `osascript` / notification / webhook 无实现 |
| 当前最终真值证据行数为 0 | 真实库只读查询 `observation_truth_evidence` |
| 腾讯与飞书的公开接口都能给出稳定源站岗位 ID | 现有 Adapter 已用 ID 建立 `(source_key, external_id)`；首轮五源真实抓取成功 |

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|
| 一次额外尝试足以吸收偶发读超时 | 仍有批次失败 | 失败保持可见，不再扩大次数；三工作日实测决定是否调整 |
| macOS Notification Center 是当前最小可用通道 | 用户看不到通知 | `osascript` 返回码落库；失败使该轮不具备正式验收资格 |
| 独立的“只取官方 ID”实现能作为 Adapter 之外的官方快照 | 独立路径也可能随官网变更失败 | 候选失败不代签真值；每日汇总拒绝确认并展示具体源 |

## 二、具体实现

### 4. 数据长什么样，空值怎么办

新增两张表，不给既有 `observation_batches` 强塞第二套状态：

```sql
observation_notifications(
  observation_id PRIMARY KEY,
  policy, status, attempted_at, error
)

observation_truth_candidates(
  observation_id, source_key,
  status, official_url, captured_at,
  official_ids_json, official_ids_sha256, error,
  PRIMARY KEY(observation_id, source_key)
)
```

| 字段 | 有值时 | 取不到时 | 空值和不匹配分开了吗 |
|---|---|---|---|
| notification `status` | `sent / skipped / failed` | 不允许缺行 | 是；`skipped` 是策略明确不发，`failed` 是应发未发 |
| truth candidate `status` | `captured / failed / skipped` | 不允许缺行 | 是；源失败时 `skipped`，独立取数失败时 `failed` |
| `official_ids_json` | 完整、去重、排序后的字符串 ID | 失败/跳过时为 `NULL` | 是；空清单只有官网明确返回 count=0 才合法 |
| `error` | 失败原因 | 成功时 `NULL` | 是 |

候选表每个源每轮只写一次，不覆盖、不自动重试。最终
`observation_truth_evidence` 仍是唯一验收真值，候选不能代签。

### 5. 硬约束在哪一行

- `network.retry_timeouts()` 只捕获 `httpx.TimeoutException` 与内建 `TimeoutError`；
  总尝试次数固定为 2，第二次失败原样抛出。HTTP 状态错误、JSON/业务错误、数据库错误
  一律不重试。
- 自动观察通过一个只改 `fetch()` 的 Adapter 包装层调用 `ingest.sync()`，因此两次
  fetch 仍属于同一个 run，不制造“先失败、后成功”的两条底层事实。
- 本机通知使用固定 `/usr/bin/osascript` 参数数组，不经过 shell，不拼接脚本正文。
- 官网快照模块不得 import `jobagent.adapters`、`ingest`、`normalize`、`match` 或
  `queries`；它只按固定目标源读取官方 API 的原始岗位 ID。
- 每日 `--accept` 前必须同时满足：三个准点时段、五个源、数据同步成功、通知策略执行
  成功、独立候选完整、候选 ID 与系统 snapshot ID 相等。15 组证据在一个数据库事务
  内写入；任一失败全部回滚。

### 6. 判据的粒度

- “可重试”按异常类别，不按错误文字：只认 timeout 类型。
- “通知成功”按 `osascript` 进程退出码；进程启动不等于通知成功。
- “官网一致”按 `(observation_id, source_key)` 的完整 ID 集合，不按数量相等。
- “每日汇总可确认”按工作日内三个固定 slot × 五个固定 source 的 15 个格子，不按
  “今天有几条记录”。

### 7. 数字的口径

| 数字 | 分子 | 分母 | 会随时间动吗 |
|---|---|---|---|
| 重试次数 | 首次 timeout 后的额外 fetch | 每个源每轮最多 1 | 否，策略固定 |
| 通知中的变化数 | 本轮四类真实岗位事件之和 | 不设分母 | 会，按轮变化 |
| 每日汇总格子 | `3 slots × 5 sources` | 固定 15 | 目标池/时段变更才变 |
| 漏报/误报 | 官方 ID 与系统 snapshot ID 的集合差 | 官方/系统完整 ID 集合 | 会，按轮变化 |

### 8. 这次明确不做什么

- 不做网页后台；当前只补主动通知和可读汇总，避免再次扩大产品面。
- 不做云端、IM、邮件或 webhook；它们都引入账号、secret 或外部写权限。
- 不自动确认官网真值；“独立抓到了”不等于“人审过了”。
- 不修改 #25/#26 画像语义，也不修改分类、匹配、岗位指纹或通知筛选规则；否则会把
  当前观察可靠性修复和另一条产品线混成一个不可归因候选。
- 不更新 live LaunchAgent、真实数据库或 GitHub；本轮止于本地 commit。

## 四、复盘（实现完回填）

### 11. 方案和实现差在哪

原方案把“独立取数”和“最终证据写入”都放在 `official_truth.py`。实现时发现这样会让
独立模块反向导入 `observation.py`，间接加载产品采集编排。最终把固定时段提到
`targets.py`，官网模块只负责公开接口、候选和只读汇总；最终 15 格事务由
`observation.accept_day()` 持有。另一个调整是 20:30 的“今日完成”通知必须先查到当天
三轮都准点成功；少一轮时改发“不完整”提醒，不能只凭当前这一轮成功就报平安。

### 12. 实现中踩到的坑

1. 把重试包在整次 `ingest.sync()` 外会留下“一次失败 run + 一次成功 run”；
   `test_observation_retry_stays_inside_one_sync_run` 迫使重试只包住 `fetch()`。
2. 最后一轮成功不代表全天三轮成功；`test_last_slot_warns_when_the_day_is_incomplete`
   防止 20:30 在前两轮缺失时误报“今日完成”。
3. “岗位数一样”不能证明清单一样；
   `test_daily_review_rejects_equal_count_but_different_ids` 固定为完整 ID 集合比较。
4. 每日确认循环中途失败会留下半天真值；
   `test_accept_day_rolls_back_all_items_when_one_write_fails` 固定为单一事务全回滚。

### 13. 如果重来，方案里该提前写上哪句话

“独立证据路径不能反向依赖被核对的产品采集链；全天完成必须由全天事实证明，不能由
最后一轮推断；批量人工确认必须是全有或全无。”这些约束已写在本方案和测试中，现有
`CLAUDE.md` 的最小改动、证据优先和不重复造轮子规则足够，本轮不再新增项目规则。
