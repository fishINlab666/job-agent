## 一、产品设计

### 1. 为什么现在做

代投是这个产品里唯一**不可撤销**的动作。采集错了下次再采，匹配错了用户翻一页就过去了，
投递错了对方 ATS 里就多一条记录，撤不回来。而且撤不回来的后果落在用户的求职结果上，
不是落在我们的日志里。

不做的具体后果：模型把 A 公司的表单填了 B 岗位的信息、把实习经历填进「工作年限」、
在用户还没看过的情况下把简历发出去。这些都不需要模型「出错」，只需要它
「按自己的理解填了」。

### 2. 用户会看到什么

```
用户: uv run python -m jobagent.cli apply <job_id>
  ↓
浏览器开起来（默认非无头，用户能看见）
  ↓ 系统导航到岗位页、逐字段填表、截图
  ↓ 停在这里，不点提交
屏幕上出现:
    公司 / 岗位 / 链接
    填了哪些字段，每个字段填进去的值（敏感字段打码）
    哪些字段跳过了、为什么跳过
    页面必填但画像里没值的字段 ← 有这些就该先去补画像
    截图路径
  ↓
「以上信息确认无误，提交给对方？」(y/N)   ← 默认 N
  ↓ 用户敲 y                    ↓ 用户敲 n 或直接回车
点提交，记 submitted            关掉会话，记 abandoned
```

关键是**「停下来」这一步不是提示，是流程本身**。用户不确认，
后面那一步在代码层面就没有入口。

### 3. 哪些是已核实的，哪些是我猜的

| 事实 | 怎么核实的 |
|---|---|
| 腾讯 join.qq.com 的表单字段和选择器 | 实测填过，`tencent_join.py` 里逐个对应 |
| 提交结果能从页面判出四态（成功/重复/关闭/需登录） | `test_is_success` / `test_is_duplicate` / `test_is_job_closed` / `test_need_login` |
| 15 分钟内页面状态基本不变 | **不是核实的，见下表** |

| 假设 | 如果错了会怎样 | 打算怎么验 |
|---|---|---|
| 15 分钟 TTL 够用户看完一屏信息 | 太短：用户看着看着过期了，得重跑一遍 prepare。太长：页面早变了却还允许提交 | 等真实使用数据。现在这个值是拍的，`PLAN_TTL_SECONDS` 单独拎出来就是为了好改 |
| 用户会认真看确认屏 | 看串了照样点 y，闸门就白设了 | 无法用工程手段解决。能做的是把信息排短、敏感字段打码、默认值设成 N |
| 一个待确认计划跨不过进程重启是可接受的 | 用户重启后要重跑 prepare | 故意的，见 §5 |

### 4. 数据长什么样，空值怎么办

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| `confirm_token` | `secrets.token_urlsafe(24)` | **`NULL`，不是空串** | 是 —— 这一条踩过，见 §12 |
| `FieldPlan.value` | 画像里的值 | `None` → `filled=False`，进 `skipped_fields` | 是。跳过的字段会打在确认屏上，不是静默丢掉 |
| `missing_required` | —— | 页面必填但画像没值 → 单独列出来提醒补画像 | 是。这一栏空着和有值是两种展示 |
| `SubmissionPlan.status` | `ready` | `blocked`（岗位关了 / 要登录 / 找不到按钮） | 是。`blocked` 不注册会话，`is_ready` 同时查 status 和 token |

## 二、具体实现

### 5. 硬约束在哪一行

**被否掉的方案（评审明确点名的）**：在 skills 提示词里写「使用 browser use 前
需先向用户明确链接、公司、个人信息怎么填、具体岗位」。

否掉的理由，用评审的原话：模型有抽风的可能，明确的工程链路不建议这么做。
提示词是软约束——它约束的是模型的倾向，不是模型的能力。
模型仍然**能**直接调浏览器工具，只是我们请它不要。
放在不可撤销的动作上，这个强度不够。

**做成硬约束的落点**：`Submitter` 协议里**没有 `submit()` 方法**。

```python
class Submitter(Protocol):
    def prepare(self, job, profile) -> SubmissionPlan: ...   # 填表、截图，不点提交
    def execute(self, confirm_token: str) -> SubmissionResult: ...  # 必须给 token
    def discard(self, confirm_token: str) -> SubmissionResult: ...
```

想提交只有一条路：`prepare` 拿 token → 人工确认 → `execute(token)`。
中间那步跳过去，`execute` 拿不到有效 token，**物理上跑不通**。
这不是「模型应该先确认」，是「模型没有不确认的调法」。

`SessionStore.take()` 是四道检查，一道都不能省：

| 检查 | `TokenError.reason` | 挡的是什么 |
|---|---|---|
| token 存在吗 | `unknown` | 伪造的 token、换了进程 |
| 用过了吗 | `consumed` | 同一次确认提交两遍 |
| 过期了吗 | `expired` | 用户确认完放了两小时 |
| 字段摘要对得上吗 | `drifted` | 页面在确认之后变了 |

`drifted` 那道是最容易漏的：**用户确认的是「这些值填进这些字段」，不是「这个岗位」。**
值变了就等于没确认过。所以 `digest()` 把 `[selector, label, value, action]`
排序后取 sha256 前 16 位，`execute` 时重算一遍对比。

两个刻意的设计：

- **token 里不编码任何信息**，它只是个不可猜的句柄。真正的绑定关系
  （job_id、字段摘要、过期时间）留在 `SessionStore` 里。
  这样不用管签名密钥，也不存在「伪造一个 token 骗过校验」的路径。
- **`SessionStore` 只在内存里，不落盘。** 落盘会造出
  「用户几小时前确认过的计划现在还能提交」这种情况。跨不过重启是**功能**，不是缺陷。

### 6. 浏览器为什么不关

`prepare` 和 `execute` 之间挂着一个活的 `LiveSession`。

如果 `execute` 时重开页面重新填一遍，用户确认过的东西和实际提交的东西就是两回事——
中间可能岗位关了、表单改了、值填错了。所以页面不关，`execute` 只做两件事：
核对摘要，点提交。

代价是会话会泄漏浏览器。`sweep()` 清过期会话，`discard()` 在用户放弃时立刻关。

### 7. 确认之前就写库

`prepare` 成功后先落一条 `status='prefilled'`。

为什么不等提交成功再记：那样「填好了但用户没确认」这段就是黑的——
排查不了，也看不出有多少投递卡在确认环节。这个数字本身是产品信号：
如果大量投递停在 `prefilled`，说明确认屏上的信息让人不敢点 y。

### 8. 这次明确不做什么

- **不做 `--yes` 跳过确认的开关。** 提交不可逆，不提供跳过的口子。
  想批量投递也得一个一个看过去。这条写在 CLI 的 docstring 里，
  免得以后有人当成待办给补上。
- **不做 token 落盘。** 见 §5。
- **不做多岗位批量 prepare。** 会造出「一屏确认五个岗位」的界面，
  而确认的价值恰恰在于逐个看。
- **不做自动补画像。** 页面必填但画像没值时只提醒，不猜。猜出来的值会被提交出去。

## 三、怎么验

### 9. 验证命令

```bash
# 闸门本身
uv run pytest tests/test_submitter_tencent.py -q

# §12 两个坑（落库层面）
uv run pytest tests/test_db_migrate.py -q
```

### 10. 测试钉的是哪几条

23 个用例，挑出闸门相关的：

| 结论 | 测试 |
|---|---|
| 协议里根本没有一步提交的方法 | `test_no_one_shot_submit` |
| `prepare` 填表但不提交 | `test_prepare_fills_but_does_not_submit` |
| `blocked` 的计划不能被 execute | `test_blocked_plan_cannot_be_executed` |
| 确认后才能提交 | `test_execute_after_confirm_submits` |
| 四道 token 校验各挡一次 | `test_execute_rejects_unknown_token` / `_expired_plan` / `_drifted_form` / `test_token_is_single_use` |
| 放弃不会提交 | `test_discard_abandons_without_submitting` |
| 落库的字段值打码 | `test_stored_fields_are_masked` |
| 过期会话会被回收 | `test_sweep_reclaims_expired_sessions` |

`test_no_one_shot_submit` 是这组里最重要的一个：它钉的不是某个行为，
而是**「不存在这个 API」**。以后谁想图方便加个 `submit()`，这条会红。

它也是这份方案里那条**守归属**的测试（模板 §10 要求的「做一半会红的那条」）：
闸门做一半的样子就是「加了 prepare/execute，但顺手留了个 submit 走捷径」——
这种半成品在功能测试里全绿，因为 prepare/execute 那条路确实是通的。
只有一条盯着「不存在这个方法」的测试拦得住。

## 四、复盘

### 11. 方案和实现差在哪

| 方案里写的 | 实际做成什么样 | 为什么改了 |
|---|---|---|
| token 校验三道（unknown / expired / consumed） | 四道，加了 `drifted` | 写测试时发现：token 有效不代表页面还是那个页面。用户确认的是字段值，不是 token |
| `execute` 时重新导航填表 | 保留活浏览器 | 重填一遍就等于用户确认的和提交的不是同一份东西 |
| 提交成功后写库 | `prepare` 后就写 `prefilled` | 否则卡在确认环节的投递完全不可见 |

### 12. 实现中踩到的坑

- **现象**：第二条 `blocked` 记录插入时撞唯一约束。
  **原因**：`applications` 上那条唯一索引是 `WHERE confirm_token IS NOT NULL`。
  `blocked` 没有 token，我写了空串——**空串是非 NULL**，于是两条 blocked
  的 `confirm_token` 都是 `''`，参与去重，撞了。
  **修法**：`record_blocked` 里显式写 `NULL`，`record_prefill` 里写
  `confirm_token or None`。
  **钉住它的测试**：`tests/test_db_migrate.py::TestConfirmTokenIsNullNotEmpty`
  四条。其中 `test_real_token_still_dedupes` 是反向对照——少了它，另外三条
  在「索引压根没建出来」的情况下也全绿，那测的就是「什么都不去重」。

- **现象**：索引创建语句在老库上失败。
  **原因**：索引建在 `schema.sql` 里，而老库缺 `confirm_token` 这一列。
  `init()` 的顺序是先 `executescript(schema.sql)` 再 `migrate()`，所以挂掉的
  是**整个 init**，不是「索引没建上」而已。
  **修法**：索引移到 `db.migrate()` 里，在补列之后建。
  **钉住它的测试**：`tests/test_db_migrate.py::TestIndexesBuiltAfterColumns` 三条。

  **补记（2026-08）**：上面这个「修法」当时只做了一半。索引确实加到了
  `db.migrate()`，但**没从 `schema.sql` 删掉**，两边都有——而 schema.sql 里
  那条先跑。也就是说这个坑从来没真的修好，只是新库测不出来：新库的表是全的，
  索引语句不会失败，全绿。补测试的时候才炸出来。
  连带发现 `idx_apps_status` 有同样的毛病（引用 `created_at`，也是补列），
  只是没人拿老库跑过。两条索引现在都只在 `migrate()` 里，
  `test_schema_sql_declares_no_index_on_backfilled_columns` 守着这个归属。

### 13. 如果重来，方案里该提前写上哪句话

**「空值在数据库层面是 `NULL` 还是空串」这一条，方案里必须写。**

上面那个唯一约束的坑，如果 §4 那张表在动手之前填过，就不会踩——
填那张表的时候必然会问自己「`confirm_token` 取不到时是什么」，
而一旦问出这句话，`NULL` vs `''` 的区别立刻就暴露了。

所以模板 §4 现在写着「**这一栏是本项目的头号 bug 来源，不许留空**」。
匹配层那次（`grad_year=None` 静默丢岗位）和这次是同一个形状：
**都是「没有值」这个状态没被当成一个正经状态来设计。**
一次是判否，一次是撞约束，底下是同一句话没写清。

**第二句：「这个坑归谁管」得指定到一个地方，并且留一条守归属的测试。**

`idx_apps_token` 那次不是没修，是**修了一半**——加到了新地方，没从老地方删掉。
两边都有的时候，新库照样全绿，因为新库的表是全的、索引语句不会失败。
这种「修法只做了一半」不会自己暴露，得有一条测试专门盯着
「schema.sql 里不许再出现引用补列的索引」才拦得住。
所以模板 §10 那栏要问的不只是「哪条测试钉住了结论」，
还有「**如果这个修法被做了一半，哪条测试会红**」。

顺带一条流程上的收获：§12 这一栏是**回填时才发现写错的**。
当时写着「钉住它的测试：tests/test_db_migrate.py」，一核对——那个文件里
8 个用例全是 `sources.tenant` 的，`record_blocked` / `record_prefill` 零覆盖。
把测试补上之后，其中一条立刻炸出了上面那个「修了一半」的活 bug。
**填复盘这一栏本身就是一次验证动作**，不是抄写动作。
