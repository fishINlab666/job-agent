## 一、产品设计

### 1. 为什么现在做

采集这条链路现在只有腾讯一个源，而这个产品的价值取决于**岗位池的宽度**——
一个只能看腾讯的校招工具，用户没有理由用它。

不做的具体后果：中厂岗位一个都进不来。而 `ATS_RESEARCH.md` 的结论是
中厂确实在第三方 ATS 上，飞书招聘是唯一一个**现在动手不算编**的：
两个实测核实的真实租户（xiaopeng、nio），页面自称对得上公司。
Moka、大易的租户页格式还没实测，那两家现在写 `fetch()` 是凭想象写。

### 2. 用户会看到什么

```
用户: uv run python -m jobagent.cli sync --source feishu:nio
  ↓
系统打飞书的公开接口，翻页拿全量
  ↓

    同步 feishu:nio ...
```

新增的那行「判不出岗位族 N 条」是这次要加的输出。它不是调试信息，
是给用户的一句实话：这批岗位里有多少条系统没能归类，因此按族筛的时候会漏掉。

#### UA 门：不是所有客户端都能调这个接口

方案第一版这条命令用的是 `'User-Agent':'Mozilla/5.0'`，**它现在返回 405 + 空 body**。
实测（每组都紧挨着跑一次好 UA 做对照，排掉限流）：

| UA | 结果 |
|---|---|
| `Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) ... Chrome/126.0 Safari/537.36` | **200** |
| 同上，版本号改成 `Chrome/999.0` | 200 |
| 同上，平台段换成 Windows / Linux / iPhone | **405** |
| 同上，平台段截短成 `Macintosh; Intel Mac OS X` | **405** |
| `Mozilla/5.0` 裸串 | **405** |
| `curl/8.7.1` / `python-httpx/*` / 不带 UA | **405** |

**排掉了什么**：不是限流（间隔 20 秒重测同样，且 405 之后立刻换好 UA 就是 200；
MAC=200 / WIN=405 连着四轮稳定复现）；不是别的请求头（除 UA 外逐个删掉都还是 200，
只留 UA + `Referer` 也是 200）；不是简单子串规则（把 `10_15_7` 单独拿出来、
塞进垃圾串里、拼在 Windows UA 尾巴上，全是 405）。

**没排掉的**：具体按哪一项判的，不知道。也没拿真浏览器再确认一遍。
所以这条能立的结论只到「**这个串能过，那些不能**」，不到「它按 X 判的」——
口径同 `ATS_RESEARCH.md` 的 WAF 那节。

对实现的硬影响：**UA 是承重的，写成模块常量并注释说明**，
不许后人「顺手简化成 `Mozilla/5.0`」。腾讯适配器的 `_UA` 正好是这个串，直接复用。
它同时也解释了为什么这一节的复现命令必须带 UA：**「已核实」附的命令跑不过，
这一栏就是假的**——第一版那条命令今天就跑不过。

## 二、具体实现

### 4. 数据长什么样，空值怎么办

| 字段 | 有值时 | 取不到时 | 「没有值」和「不匹配」分开了吗 |
|---|---|---|---|
| `external_id` | `post["id"]` 字符串 | 跳过这条并计数。**不许 fallback 到 title**——title 会重复，撞 `UNIQUE(source_key, external_id)` | 不适用 |
| `cities` | `[normalize_city(c["name"]) for c in city_list]`，**必须过归一** | `city_list` 为 null/空 → `[]` | 是。`[]` 交给 `match` 的三态判断，采集层不判否 |
| `raw_category` | `(job_category or job_function)["name"]` | 两个都没有 → `None` | 是。原文，不参与族判定，见下 |
| `grad_year` | —— | 当前实现一律 `None`。**注意：结构化字段里没有，但标题里有一小部分**（nio 42 条 / xiaopeng 6 条带 `27届` 这类），见 §0「届别」。抠标题是另一份方案 | 是。`None`=信息不足，`parse_grad_years` 已经分了三态 |
| `job_family` | `family_from_title(title)` | 判不出 → **`None`，不许兜底成 `"other"`** | 是。见下 |
| `recruit_type` | 叶子名 `实习`→`intern`，其余→`social` | 认不出的叶子名 → `None` | 是 |
| `department` | —— | 接口只给 `department_id`，没有名字 → `None`，不编 | 是 |
| `apply_url` | `https://<tenant>.jobs.feishu.cn/position/<id>` | —— | —— |
| `apply_system` | 固定 `"feishu"` | —— | —— |

`job_family` 这条是这次唯一一个需要**违背既有写法**的地方，单独说清。

腾讯适配器写的是：

```python
family = family_from_title(title) or FAMILY_MAP.get(fam_id, "other")
```

它成立是因为腾讯的 `positionFamily` 是**站点级固定枚举**——7 个整数码，
写死在适配器里，跨所有岗位一个意思。

飞书这边的源站分类**存在**（重探修正：不是「全是 null」），但**用不了**，
两个理由：

1. **两个字段互斥，哪个有值按租户**：nio 的 2263 条走 `job_function`、
   `job_category` 一条没有；xiaopeng 全量 1630 条反过来。
   要兜底就得两个字段都读，而这只是麻烦，不是拦路的那条。
2. **分类体系是租户自己定义的**：nio 50 个取值、xiaopeng 53 个，
   交集只有 6 个（`产品经理`/`人力资源`/`法务`/`算法`/`设计`/`项目管理`）。
   `蔚来顾问`、`用户与服务`、`ONVO` 这种取值映射不到我们的族——
   要做映射就得**每接一个租户写一张表**，那就退回「一家一个适配器」，
   正是 `ATS_RESEARCH.md` 结论二要避免的事。

所以照抄那个写法会退化成 `family_from_title(title) or "other"`，
于是 1099/2265 条（nio）被打上「其他」。

**那不是「其他族」，那是「没判出来」。** 混进 `other` 之后有两个后果：
用户按族筛永远看不到这批岗位，而 `other` 这一族里真正的职能岗和没判出来的也分不开了。
这跟 `grad_year=None` 被判否是同一个形状的错：**「没有值」没被当成一个正经状态。**

所以采集层写 `None`，并且在 `sync` 的输出里报一次判不出的条数。
判不出的比例是 **48.5%（nio）/ 33.1%（xiaopeng）**，将近一半——
这个量级下那行输出不是锦上添花，是**用户不知道就会被误导**：
他按族筛出 10 条，以为这家只有 10 条对得上，实际有一半岗位压根没参与筛选。

**分类原文还是要留**，只是不拿它当判据：

```python
job_family = family_from_title(title)                  # 判不出就是 None，不兜底
raw_category = (job_category or job_function)["name"]  # 原文落库，不参与判定
```

`RawJob` 已有 `raw_category` 这个字段。留着它是为了以后扩 `TITLE_RULES` 时
有真实分布可看——上面「判不出的那批集中在 `蔚来顾问` 414 / `用户与服务` 346」
就是这么数出来的。**留原文，但不让它影响判定**，这两件事要同时成立：
一旦拿它兜底，下次想知道「哪些词该加进 `TITLE_RULES`」就没有干净样本了。

这个数字本身是产品信号：蔚来那批判不出的全是**门店/销售体系**的词汇
（`行销顾问`、`门店店总`、`服务代表`、`增值服务`），`TITLE_RULES` 里一个都没有。
扩词是另一份方案的事（§8），这次只让它可见。

### 5. 硬约束在哪一行

这次是采集，不是投递——没有不可撤销动作，不需要 API 形状的闸门。
但有两条**已经在代码里**的硬约束兜住这次的风险，写明是靠它们，不是靠我小心：

| 约束 | 在哪 | 挡什么 |
|---|---|---|
| 空结果不许当成「全部关闭」 | `ingest.sync()` `jobagent/ingest.py:96` | 接口改版返回空 → 全部岗位被判关闭 |
| 消失比例守卫 | `CLOSE_GUARD_RATIO=0.4` + `CLOSE_GUARD_MIN_COUNT=5` | 翻页挂了拿到半截 → 批量假关闭 |

**但 `count=0` 那两个真租户会踩第一条。** `luckin`/`horizon` 是活租户、接口正常、
`code=0`，只是当下没在招。现在的 `ingest.sync()` 会把它当上游异常抛 `RuntimeError`，
run 记 `failed`。这是这次要定的口径：

- 适配器返回空，**且说不清为什么** = 「我没拿到数据」→ 该抛，现有行为对
- 接口明确回了 `count=0` = 「这家现在没岗位」→ 是事实，不是故障

**做法：适配器自己区分，`ingest` 不猜。**

```python
class FeishuAdapter:
    # fetch() 返回空列表时，这个标记回答「空是不是一个可信的答案」。
    # 接口回了 code=0 + count=0 才置 True；网络失败、非 200、翻页中断一律 False。
    empty_is_authoritative: bool = False
```

`ingest.sync()` 那段判断改成：空结果时先问适配器
（`getattr(adapter, "empty_is_authoritative", False)`），
为真就正常走完（`opened=0`，run 记 `ok`），为假才抛。

用 `getattr` 带默认值是为了不动腾讯适配器——它没这个属性，取到 `False`，
行为跟今天完全一样。**新语义默认关闭，只有显式声明的适配器才享受。**

这一步改的是 `ingest` 的行为，属于 `CLAUDE.md`「需要方案」清单里
「加或改一个模块的行为」那条。

### 6. 判据的粒度

`route_key = feishu:<tenant>`。租户从 `<tenant>.jobs.feishu.cn` 抠，
`ats.py` 的 `domains` 已经收窄到 `("jobs.feishu.cn",)`，
`routing._on_vendor_domain()` 挡住拿无关链接凭空造租户。**这次不动那两处。**

新增一条这次实测才有的判据，比 HTML 探测干净：

| 现象 | 含义 |
|---|---|
| HTTP 400 + 非 JSON | 这个租户不存在 |
| HTTP 200 + `code=0` + `count>0` | 真租户，有岗位 |
| HTTP 200 + `code=0` + `count=0` | 真租户，当下没岗位 |

`ATS_RESEARCH.md` 判飞书租户真假用的是「404 + 0 字节」（HTML 层）。
接口层这个信号更强，而且顺手分出了第三态——**HTML 层分不出「没有这家」和「这家没岗位」**，
`luckin`/`horizon` 在 HTML 层都是 200 的活页面。

### 7. 数字的口径

| 这个数 | 分子数什么 | 分母数什么 | 会不会动 |
|---|---|---|---|
| 租户覆盖 | 实测通了接口的租户（4 个都通） | 已知真实租户（现在 4 个：nio/xiaopeng/luckin/horizon） | 会。新租户只能跟着公司自有入口的跳转发现 |
| 族判不出条数 | 该批次 `job_family is None` 的条数 | 该批次抓到的条数 | 会，两头都动。改 `TITLE_RULES` 动分子，岗位池自己也在动（见下） |
| 校招覆盖 | ~~按字段算 **0**~~ → **社招池里 0，校招门户里 1222**（nio 627 + xiaopeng 436 + sensetime 159，2026-08-05 全量）→ 落地后 **8618**（四家，2026-08-06，海底捞换成字节 7395）| —— | **这一行原来的口径是错的**：分子只数了社招池。带 `website-path` 才拿得到校招池，见 §0「校招」和 `003 §7`。1222 / 8618 都**不含** xiaopeng 的子门户 398875（335 条），因为它被 `campus` 完全包含。**两个数的家数和日期不同，单独引用任何一个都要带上它们** |

**族判不出的比例必须按租户报，不许合并成一个总数。** 这条上一版是预判，现在实测证实了：

| 租户 | 判不出 / 全量 | 比例 | 测于 |
|---|---|---|---|
| nio | 1094 / 2248 | **48.7%** | 2026-08-05 17:2x |
| xiaopeng | 540 / 1638 | **33.0%** | 同上 |
| haidilao | 15 / 52 | **28.8%** | 2026-08-05 17:3x |
| sensetime | 12 / 71 | **16.9%** | 同上 |

**四个租户跨了 32 个百分点（16.9% ~ 48.7%）。** 上一版只有两个租户、写的区间是
`33%~49%`，加了海底捞和商汤之后下界掉到 16.9% —— 又一次印证「两个样本量出来的
区间不是这个接口的性质」。要引用就带上是哪几个租户、测于哪天。

成因也完全不同：nio 是门店销售体系的词
（`蔚来顾问` 414 / `用户与服务` 346），xiaopeng 那 540 条是另一批词，
海底捞是餐饮门店的词（`食安审核员`、`管培生`），商汤偏技术所以最低。
合并成一个平均值不指向任何一件事，也没法用来决定该给 `TITLE_RULES` 加哪些词。
腾讯那批（801 条大厂技术岗）混进来更是把三件事平均成一个数。

**这个数不许写死进代码或文档当阈值**，两个理由：

1. 「27%」那个数就是这么错的——200 条样本上的比例，被当成了接口的性质，
   全量重算是 48.5%。同一个坑 `ATS_RESEARCH.md` 记了七次。
2. **分母自己在动**：xiaopeng 的 `count` 上一轮 1646、这一轮 1631→1630，
   同一次会话内两次调用差 1 条。岗位池是活的。

所以 `sync` 那行输出的是**这一次抓取的实际条数**，当场算，不跟任何基线比。
要报区间就写 `17%~49%`（2026-08-05，四个租户：sensetime / haidilao / xiaopeng / nio），
并写清是哪几个租户——**不写来源的区间和钉死的快照一样不可信。**
这个区间自己就演示了为什么：上一版两个租户写的是 `33%~49%`，
第三、第四个租户一进来下界就掉到 16.9%。

### 8. 这次明确不做什么

- **不做校招门户采集。** ~~它的接口我没找到，现在写等于编。~~
  **这一条当时成立、现在已解决，接口在 `003` 里。** 留着原文是因为它记的是
  「当时确实找不到」这个事实，以及找错的方向：翻了 15 个 script bundle，
  只挖到 `/api/v1/csrf/token/`、`/api/notice`、`/api/talent/note/*` 这类；
  试过 `portal_type`、`recruitment_type_id_list`、`/api/v1/campus/search/job/posts`
  等参数和路径，`count` 恒为 2265 或直接 404。
  **答案是同一个接口 + 一个 `website-path` 请求头** —— 不是新路径、不是新参数，
  而这一轮把力气全花在猜路径和猜 body 参数上，一次都没试过换请求头。
  最后是照着真浏览器的请求逐行比对才看见的（Playwright 开 `campus.nio.com`
  抓 XHR）。`portal_type` 在真请求里也有，但**它是陪跑的**，删掉数字不变。
  教训写进 `003 §13`：**猜不出来的时候，去读真实请求，别继续猜。**
- **不做 `TITLE_RULES` 扩词。** 那是改归一判据，会动腾讯已有 795 条岗位的分类，
  属于另一份方案。这次只把判不出的比例测出来、报出来。
- **不做 `source add` 命令。** `ATS_RESEARCH.md` 待办里那条：
  多租户源现在只能手写 SQL 插进 `sources`。等这个适配器落地后单独一份方案。
- **不做详情页抓取。** 理由只有一条：列表接口的 `description` / `requirement`
  已经有内容，够用。
  （这里原来写的是「`job_post_info` 全 null 说明详情在另一个接口」——**已证伪**，
  见 §3：那个对象里 `experience` / `required_degree` 等 6 个字段是有值的。
  留着这句反话会让下一个人为了一个不存在的空对象再去打一轮详情接口。）
- **不做代投。** 飞书的投递表单没实测过。采集能走接口不代表投递也能，见 §3 和 `001`。

### 11. 方案和实现差在哪

| 方案里写的 | 实际做成什么样 | 为什么改了 |
|---|---|---|
| `if not jobs:` 里 `if empty_is_authoritative: pass / else: 抛` | 取反成 `if not getattr(adapter, "empty_is_authoritative", False): 抛` | 「新语义默认关闭」比「新语义有例外」难写错。取反之后，漏声明属性的适配器走的是原来那条路，不是新路 |
| 「空 id 就跳过」 | 跳过 **并且** `self.skipped_no_id += 1` | 方案没说怎么让人知道跳了几条。静默跳过等于「抓少了但没人发现」 |
| 没提公司名怎么进适配器 | `routing.get_adapter()` 从 sources 行注入 `company` | 多租户适配器手里只有租户名（`nio`），公司名（`蔚来`）只在 sources 行里。不注入的后果不是报错，是 2266 条岗位全挂在 `company='nio'`，`jobs --company 蔚来` 一条都查不到 |
| 把 `sync --dry-run` 当验证手段 | **先修了 `--dry-run` 本身** | 它不是只读的。见 §12 第一条 |
| §3 那些计数当成接口的性质 | 全部标上测量日期 | 同一天内 nio 2265→2266、xiaopeng 1630→1633。岗位池在动 |

### 12. 实现中踩到的坑

- **现象**：`sync --dry-run` 往真库里留行。`cli status` 于是显示
  `tencent_join / 795 条开放岗位 / running / 抓取 0` —— 那个源上一轮明明真实
  `ok`、抓了 795 条。
  **原因**：dry-run 靠 `ingest.sync()` 结尾的 `conn.rollback()` 实现，
  但 `db.register_source` 和 `db.start_run` 在它之前**各自 `conn.commit()` 过**。
  commit 完的东西回滚不回来，于是 `jobs`/`snapshots` 干净、
  `sources`/`runs` 各留一行，后者永远停在 `running`，而 `status` 取的是
  `ORDER BY id DESC LIMIT 1`。
  **修法**：三个 `db` 写函数加 `commit: bool = True`，`sync()` 里
  `write = not dry_run` 一路传下去；两条失败路径（`fetch()` 抛、空结果抛）
  抛之前补 `conn.rollback()`，否则未提交的 INSERT 会挂在事务里被下一个源的
  commit 顺手带进库。
  **钉住它的测试**：`TestDryRunWritesNothing` 七条。把
  `write = not dry_run` 改回 `write = True` 复现旧行为，其中 4 条立刻红。
  **这个 bug 能活下来的全部原因是 `dry_run` 在测试里一次都没被跑过。**

- **现象**（差点踩）：改完适配器让 `fetch()` 在 `count=0` 时不抛，
  但 `sync` 照样把 run 记成 `failed`。
  **原因**：守卫在 `ingest` 那一侧，两处都得改。
  **钉住它的测试**：`test_empty_fetch_ok_when_adapter_says_so` 和
  它的反向对照 `test_empty_fetch_raises_not_closes_everything`。

- **现象**（差点踩）：`empty_is_authoritative` 是实例属性，
  上一轮 `count=0` 置真之后不复位，下一轮真的抓失败也会被放过。
  **修法**：`fetch()` 开头无条件重置。
  **钉住它的测试**：`test_flag_resets_between_fetches`。

- **现象**（差点踩）：把「空可信」当成「可以放心关闭」。
  昨天 2266 条今天 `count=0`，就会一次关掉整批。
  **修法**：标记只回答「空可不可信」，关闭仍由 `CLOSE_GUARD_RATIO` 管。
  **钉住它的测试**：`test_authoritative_empty_does_not_mass_close`。

- **现象**（差点踩）：`family_unknown` 如果在「新增」循环里数，第二轮同样的
  岗位会掉成 0，用户以为问题自己好了。
  **修法**：分母取这一轮抓到的条数，和 `fetched` 同粒度。
  **钉住它的测试**：`test_counts_all_fetched_not_just_new`。

- **现象**（差点踩）：翻页中途空批次静默返回半截数据 → diff 把没拿到的那批
  判成已关闭。
  **修法**：宁可整轮失败。
  **钉住它的测试**：`test_truncated_paging_raises`。

写测试本身也踩了两个：`_mock_client` 工厂里直接写 `httpx.Client` 会调到被
patch 的那个符号自己（`RecursionError`），所以先把真类抓在 `_REAL_CLIENT`；
`pytest.raises(Exception)` 会让 `RecursionError` 也算过，所以收窄成
`EXPECTED_ERRORS = (RuntimeError, httpx.HTTPStatusError)`。第一版就是这么假绿的。

### 13. 如果重来，方案里该提前写上哪句话

- **「`--dry-run` 也要有测试。」** 这一轮唯一一个真 bug 就在验证手段本身。
  方案把 `--dry-run` 当成检查别的东西的工具，从没检查过这个工具。
  凡是「用来验证的东西」，它自己也得有一条测试。
- **「所有计数写进方案时带上测量日期。」** 「2265 条」不是接口的性质，
  是某一刻的观测。不带日期的计数会在下一次复核时变成一条假的「已核实」——
  `ATS_RESEARCH.md`「七次口径错」第七种，这份方案上一轮刚犯过一次
  （27% → 实际 48.5%），差点犯第二次。
- **「守卫改在哪一层，就在那一层再钉一次测试。」** 适配器单测全绿但 `sync`
  照样 failed，是这类「改一半」最典型的表现，而且单测越绿越难想到去查另一侧。
